## 1. Зачем этот аудит (контекст и ставка)

Вся программа лояльности построена и лежит на проде **тёмной** (флаг `loyalty_enabled=false` → все
loyalty-роуты 404). Следующий шаг — go-live (PR-4.5) — **необратим и обращён наружу**:

- **Деньги.** Баллы = 1 сум = реальное обязательство перед клиентом. Ошибка в начислении/дедупе/гонке
  = потерянные деньги ИЛИ подорванное доверие. Откатить нельзя после первой реальной активации.
- **Нет staging.** Первый живой `flag-on` случится прямо на проде (нет пред-прод контура с ботом+
  мини-аппом). Значит: всё, что можно проверить ДО флипа, должно быть проверено ДО флипа.
- **Внешняя поверхность.** QR-коды раздаются людям; вход через Telegram; бот принимает контакты.

Цель аудита — **доказательно** ответить на один вопрос: **«Можно ли безопасно включать?»** — с
ранжированным списком того, что обязано быть починено ДО флипа, и что можно после.

Это не «ещё одно ревью». Каждый PR Этапов 0–4 уже прошёл Гейт-2 (fleet + lang-review + adversarial).
Этот аудит — **сквозной, системный, независимый** взгляд на ВСЮ собранную систему целиком, которого
не даёт по-PR-ное ревью: инварианты, которые держатся только на стыке модулей; денежный путь от QR до
баланса; полнота dark-gating; связность flag-on. Плюс прицельная атака на **известные слабые места**.

## 3. Две оси глубины (требование Капитана: масштаб + каждая мелочь)

Аудит ведётся **top-down и bottom-up одновременно, со сходимостью в середине.** Разрыв между тем, что
инвариант ТРЕБУЕТ, и тем, что код ДЕЛАЕТ — это и есть находка.

### Ось A — Макро (вся картина в масштабе)
- Архитектурная целостность; сквозной data-flow QR → бот → мини-апп → ledger → баланс → статус.
- Полный E2E пользовательский путь (оба входа: с QR и без QR).
- **Каталог системных инвариантов** (должны держаться ВСЕГДА) — см. §5.
- Trust boundaries; money-path integrity через всю систему.
- Deploy/migration safety; связность и обратимость flag-on/flag-off.

### Ось B — Микро (изнутри каждую мелочь)
- Line-by-line по КАЖДОМУ файлу скоупа: каждый эндпоинт, каждая миграция up **и** down, каждый лок,
  каждый guard, каждое событие, каждая схема, каждая ветка ошибки.
- Реальность тестов: **mutation testing** — падает ли тест, если сломать проверяемый инвариант?
- i18n-паритет ru/uz; double-submit guards; retry-логика; обработка 401/404/409/503/сети.

## 5. Каталог инвариантов (истина, против которой проверяем)

Фаза 0 строит и уточняет этот список; ниже — стартовый набор, который аудит ОБЯЗАН подтвердить или
опровергнуть на конкретных file:line + сценарии:

1. **Баланс = Σ(point_ledger)** — нигде нет второго источника истины по баллам; ledger append-only.
2. **Активация идемпотентна** — повторный `qr_<code>` / повторный `POST /qr/activate` не начисляет
   дважды (partial-UNIQUE + атомарный claim); конкурентные вызовы → ровно одно начисление.
3. **Friend-flip ровно один раз** — на 10-й lifetime-активации; +5000 однократно; повтор не флипает и
   не доначисляет.
4. **Welcome ×1.5 только на первую** активацию профиля.
5. **Dark-gating полный** — при `loyalty_enabled=false` НИ один loyalty-роут (api) и НИ один `qr_`-путь
   (bot) не даёт эффекта; ничего не пишется в БД, ничего не течёт в ответах.
6. **Flag-on связен** — при `true` весь путь (вход → согласие → анкета → активация → кэшбэк → статус)
   работает как единое целое; нет полу-включённых состояний.
7. **Consent корректен по закону РУз** — построчно, версионно (`DATA_PROCESSING_CONSENT_VERSION`),
   идемпотентно; телефон верифицируется только через бота.
8. **Телефон верифицирован ⟺ через бота** — `phone_verified_at` ставится только на подтверждённом
   контакте (`contact.user_id == from_user.id`).
9. **Цена детерминирована** — из `products.price` по `product_id` (PK/FK), не по классификатору;
   дробная/отсутствующая цена → 503, не 500, не молчаливый неверный кэшбэк.
10. **Все деньги-мутации под нужным локом** — `customer_profile FOR UPDATE`; счётчики согласованы.
11. **Миграции обратимы** — up/down/up на чистом PG без потери схемы; параллельно проду.
12. **initData неподделываем** — HMAC исключает `hash` И `signature`; истёкшие/чужие → 401.

## 6. Метод (как — максимально качественно, из лучших практик)

Пятифазный веер. Каждая находка проходит **adversarial-верификацию** прежде чем попасть в отчёт
(паттерн confidence-scorer: находку пытаются ОПРОВЕРГНУТЬ; выживает только доказанная).

- **Фаза 0 — Recon + каталог инвариантов** (1 ведущий агент, макро). Строит системную карту, E2E data-flow
  и уточняет §5. Выход = «спека истины», против которой идёт микро-фаза. Раздаёт линзам seed'ы из §7.
- **Фаза 1 — Параллельные глубокие погружения по линзам L1–L8** (fleet, свежий независимый контекст).
  Каждый агент читает свой срез line-by-line против каталога инвариантов + threat-model. Выход =
  сырые находки (file:line + сценарий отказа + предв. severity).
- **Фаза 2 — Adversarial-верификация** (по находке — скептик, пытается опровергнуть/воспроизвести).
  Дубли сливаются; выживают только находки с доказательством и confidence ≥ порога.
- **Фаза 3 — Динамическая валидация на parity-БД (НЕ на проде, флаг off):**
  - Полный прогон всех тест-сьютов (api pytest / front vitest+build / bot pytest+ruff) — зелёные.
  - Миграции `up → down → up` на чистом `postgres:17` + `alembic check`.
  - **Mutation testing ключевых guard'ов** (harness backup→mutate-prod→run→restore, уже применялся в
    PR-4.4b): сломать friend-flip порог, idempotency-guard, welcome-однократность, consent-дедуп,
    `FOR UPDATE` — убедиться, что тест КРАСНЕЕТ. Где не краснеет → находка «ложно-зелёный тест».
  - **Эмпирическая проверка dark-gating:** с флагом off дёрнуть каждый loyalty-роут → 404; убедиться,
    что ноль строк в `point_ledger`/`customer_event`/`consent` (count==0).
- **Фаза 4 — Синтез + вердикт go/no-go.** Ранжирование BLOCKER/MAJOR/MINOR/NIT; per-area readiness;
  финальный вердикт готовности к флипу; список «must-fix ДО флипа» vs «можно после».

**Принципы (best-practice, обязательны):**
- **Evidence, not assertion.** Находка = `file:line` + конкретный вход/состояние → неверный выход/сбой +
  repro + severity. «Выглядит подозрительно» без сценария отказа — не находка.
- **Независимость.** Аудитор — свежий контекст, БЕЗ истории реализации (unbiased eyes).
- **Threat-model денежного пути** (STRIDE) прогоняется явно, не «между делом».
- **Скепсис по умолчанию** + anti-sycophancy: зелёное состояние не освобождает от попытки сломать.

## 7. Seed — известные слабые места (атаковать прицельно, не переоткрывать)

Отдаю аудитору сразу, чтобы бюджет шёл в атаку, а не в раскопки. По каждому — **подтвердить, оценить
severity, дать рекомендацию** (аудитор НЕ чинит — фиксирует):

1. **`FOR UPDATE` race-тесты ложно-зелёные.** Race-тест на лок (2× `asyncio.gather`) НЕ ловит регресс
   детерминированно (наблюдалось 5/5 зелёных при СНЯТОМ локе — и у `record_consent`, и у survey). Значит
   защита от гонок держится на коде, но НЕ охраняется тестом. Задача: спроектировать детерминированный
   concurrency-тест ИЛИ явно принять+задокументировать риск (реальный бэкенд — Postgres, лок реален).
2. **`record_consent` дедуп транзитивно зависит от side-`UPDATE users`.** Сериализация consent/phone_shared
   дедупа сейчас держится в т.ч. на побочном `UPDATE users` (обновление имени) в `get_or_create_user`.
   Если это «оптимизируют» (skip UPDATE при неизменных полях) — дедуп тихо сломается без красного теста.
   Оценить хрупкость; рекомендация по укреплению (напр. явный лок-на-профиль как единственный гарант).
3. **`bot/handlers/common.py:~300` `handle_contact_received`** — отсутствует `contact.user_id ==
   from_user.id` чек (тот же класс, что чинили в `loyalty.py`), пишет **unverified** `phone`. Задача:
   доказать, пересекает ли это loyalty-границу (она на `phone_verified_at`) или нет; severity.
4. **Нет staging → первый flag-on = прод.** Оценить остаточный риск и достаточность flag-on smoke (§ PR-4.5).
5. **`useActivation` 401 → default-ветка** (retry harmless, реальный фикс = reopen мини-аппа). UX-корректность.
6. **Энтропия QR-кода ~50–60 бит.** Проверить реальную стойкость к брутфорсу/перечислению при отсутствии
   «вооружения партии» (анти-фрод снят осознанно) — есть ли rate-limit/лок-аут; можно ли перечислять коды.
7. **`orders/service.py` доверяет клиентскому `total`** (money-surface под будущую трату баллов) — forward-risk.

## 8. Must-hit checklist (обязательное покрытие — ничего не пропущено)

Аудит НЕ считается полным, пока каждый пункт не закрыт «проверено ✅ / находка 🔴»:

- **Деньги:** начисление кэшбэка (5%/8% × цена); welcome ×1.5 только первая; friend-flip на 10-й
  (порог, однократность, +5000); Decimal-округление; ledger append-only + reconciliation-снапшот;
  баланс = Σ ledger; нет пути к двойному начислению.
- **Гонки:** каждый `FOR UPDATE`; атомарный claim; partial-UNIQUE; граница 10-й под конкуренцией.
- **Идемпотентность:** повтор `qr_<code>`; повтор `POST /qr/activate`; replay после ошибки (откат→нет сирот).
- **Безопасность:** initData (hash+signature); IDOR на `/loyalty/me` и favorites; consent bypass; спуфинг
  контакта (bot); брутфорс кода; код не в логах.
- **Миграции:** 8 миграций up/down/up; enum-DROP; parity-гейт; deploy rollback.
- **Flag-gating:** каждый api loyalty-роут → 404 при off; каждый bot `qr_`-путь → обычный /start при off;
  ноль записей в БД при off; связность при on.
- **Consent/закон:** версионность, построчность, идемпотентность, привязка к верифиц. телефону.
- **Frontend:** ветки статусов активации; обработка 404/409/503/сети; i18n ru/uz паритет; double-submit;
  инвалидация кэша; редирект `?code=`.
- **Тесты:** mutation-проверка каждого критического guard'а; пробелы покрытия; E2E QR-батча реален.

## 9. Deliverable (что аудитор сдаёт)

Структурированный отчёт `.claude/reports/2026-07-XX-prelaunch-audit.md`:
1. **Executive summary** — 1 абзац + финальный вердикт: **GO / NO-GO / GO-WITH-CONDITIONS.**
2. **Таблица находок**, ранжированная по severity: `id | severity | линза | file:line | сценарий отказа |
   repro | рекомендация`.
3. **Per-area readiness** — по каждой линзе L1–L8: ✅ чисто / ⚠️ с условиями / 🔴 блокер.
4. **Must-fix ДО флипа** vs **можно после** — явные два списка.
5. **Что проверено динамически** — команды + вывод (тесты зелёные, миграции up/down, mutation-результаты).
6. **Явные «чисто»-декларации** по линзам, где находок нет (чтобы «пусто» ≠ «не смотрели»).
7. **Остаточные принятые риски** — что осознанно оставляем (напр. анти-фрод снят) + обоснование.

**Severity:** `BLOCKER` (флипать нельзя) / `MAJOR` (чинить до флипа, но не катастрофа) / `MINOR`
(можно после, трекать) / `NIT` (косметика).

## 10. Исполнение и роли

- **Аудитор — независимый Ревьюер в свежем контексте.** Кресло назначает Капитан. Метод — fleet L1–L8 +
  adversarial-верификация + динамическая фаза.
- **Инженер (я, автор кода Этапов 0–4) НЕ сижу финальной инстанцией аудита своего кода** (независимость).
  Моя роль здесь: написал ТЗ; по находкам — чиню как Инженер под отдельный Гейт-2.
- Связь Аудитор↔Инженер — только через Капитана.

**Варианты запуска (моя рекомендация первым), Капитан выбирает:**
- **(A, реко) Многоагентный Workflow-веер** под этим ТЗ: Фаза 0 recon → Фаза 1 fleet L1–L8 параллельно →
  Фаза 2 adversarial-верификация каждой находки → Фаза 3 динамика на parity → Фаза 4 синтез. Максимальная
  широта + глубина за один оркестрированный проход; бюджет пропорционален числу линз×раундов. Требует
