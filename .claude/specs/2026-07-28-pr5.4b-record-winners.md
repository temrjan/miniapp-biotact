## Goal

Жребий тянут вживую через random.org: ведущий называет номер, зал слышит. Сейчас этот результат
некуда записать — `lottery_tickets.is_winner` и `prize_rank` существуют в схеме с PR-5.1 и не
заполняются ничем. Этот PR даёт администратору внести названные номера и закрыть тираж.

Наш код по-прежнему **не выбирает победителя**: он принимает то, что назвал внешний источник, и
проверяет, что названное допустимо.

## Решения Гейта-1

### 1. Правило выигрыша — ратифицировано Капитаном 2026-07-28

```
Один человек — один приз.
Выигравший ИСКЛЮЧАЕТСЯ из последующих раундов — именно ЧЕЛОВЕК, не только его номер.
```

Уточнение было получено явным вопросом: Капитан сформулировал два правила («один человек — один
приз» и «выигравший номерок не участвует дальше»), и они расходятся для человека с двумя билетами.
Ратифицирован **человек**: иначе владелец двух билетов мог бы взять два приза, и первое правило
не выполнялось бы.

**Как это работает на эфире.** Ведущий называет номер; если номер принадлежит уже выигравшему —
система **отказывается его записать** и говорит, чей это номер. Ведущий крутит барабан снова.

⛔ **Автопропуск отклонён.** Соблазн — молча пропустить такой номер и взять следующий. Нельзя:
зал слышал названный номер, а в опубликованном результате его бы не оказалось, и объяснить это
можно только «поверьте нам». Отказ честнее: расхождение разрешается в зале, а не внутри кода.

### 1b. Список номеров — ВСЁ ИЛИ НИЧЕГО, частичной записи не бывает

`winning_numbers` — это **один список, отправляемый одним вызовом**. Любая забракованная позиция
(конфликт по §1, выход за диапазон, дубль) отменяет **весь** вызов: в БД не пишется ничего, тираж
остаётся `committed`, администратор правит список и шлёт заново.

Записано явно, а не оставлено выводиться из «одной транзакции»: формулировка «одна транзакция»
допускает и другое прочтение — первый номер записан, конфликтующий отклонён отдельным ответом.
Это тоже технически однотранзакционно, но поведение другое и для необратимой операции опасное:
администратор увидел бы 409 и не знал, записалась ли половина. Конвенция проекта — **409 значит
«не изменилось ничего»** — здесь держится буквально. (Неявность поймана Ревьюером на Гейте-1.)

### 2. Сериализатор перехода — условный UPDATE, а не `FOR UPDATE`

Два администратора могут вносить номера одновременно. Переход `committed → drawn` защищаем
условным обновлением:

```sql
UPDATE lottery_draws SET status='drawn', drawn_at=… WHERE id=:id AND status='committed'
```

Затронуто 0 строк → гонку проиграли (или тираж уже разыгран) → **409**.

Почему так, а не `SELECT … FOR UPDATE`: в PR-5.3 лок был снят как **мёртвая защита** (строка
создавалась сразу терминальной, мутация доказала — без него не краснел ни один тест). Здесь
переход состояния настоящий, и условный UPDATE — минимальная защита, которая **мутационно
проверяема**: снимаем условие `AND status='committed'` → гоночный тест обязан покраснеть. Не
покраснеет — конструкция мёртвая и подлежит сносу, как тогда.

### 3. Что проверяем на входе — и почему каждое

Номера приходят от человека, набирающего их вручную во время прямого эфира. Это граница.

| Проверка | Ответ | Почему не «лишняя защита» |
|---|---|---|
| розыгрыша нет | 404 | `draw_id` приходит снаружи |
| статус ≠ `committed` | 409 | нельзя разыграть незамороженный и нельзя переиграть разыгранный |
| пустой список номеров | 422 | «провести розыгрыш без победителей» — почти наверняка промах |
| номер вне `1..total_tickets` | 400 | опечатка при наборе вживую — самый вероятный сбой |
| номер повторяется в списке | 400 | та же опечатка, но самонакладкой |
| номер принадлежит уже выигравшему | 409 | §1, ратифицированное правило |

Сообщение последней ошибки обязано называть **номер и то, что его владелец уже выиграл** —
ведущему нужно понять причину за секунды, у микрофона.

### 4. Ранг = позиция в списке, потолка нет

Первый номер — главный приз (`prize_rank=1`), дальше 2, 3, … по порядку.

Жёсткого потолка в 4 приза **не ставим**. Докстринг модели (`models.py`) описывает «1..4» как
текущую практику, а не как правило: призовой фонд — маркетинговое решение, оно меняется от месяца
к месяцу, и зашитая четвёрка стала бы ограничением, которого никто не утверждал. Ограничение
сверху и так есть — числом билетов.

### 5. Контакт победителя — ❌ ТЕЛЕФОНА В ОТВЕТЕ НЕТ (решение Капитана 2026-07-28)

Капитан: «руками буду искать». Телефон из ответа исключён; отдельного эндпоинта «контакты
победителей» тоже не заводим.

**⚠️ Практическая загвоздка, вскрытая проверкой — не гипотеза.** Поиск в админском разделе
«Клиенты» работает **по имени или телефону** (`CustomersPage.tsx:50`), телефон виден в карточке
клиента (`CustomerCard.tsx:57-60`). А ответ этого эндпоинта несёт `user_id` — внутренний
идентификатор, по которому **искать нечем**: такого поля в поиске нет.

С одним лишь `user_id` ручной поиск физически невыполним, и решение упрётся в тупик на первом же
розыгрыше.

**✅ РЕШЕНО Капитаном 2026-07-28: возвращаем `user_id` + `first_name`.** Имя ищется существующим
поиском, дальше телефон виден в карточке клиента. Телефон в ответ API не попадает — исходное
решение соблюдено.

Новой поверхности раскрытия имя не создаёт: тот же администратор видит те же имена в своём же
разделе «Клиенты».

⚠️ Имена не уникальны. При тёзках администратор различит их по `user_id` в связке с разделом
«Клиенты». Принято сознательно: призов 1–4 в месяц, вероятность коллизии мала, а стопроцентная
однозначность стоила бы либо телефона в ответе (отклонён), либо отдельного экрана.

### 6. Публикация слепка — не код

Ратифицировано 2026-07-28: слепок печати публикуется **постом в канале** до жребия. Кода в этом
PR не требует; кнопка «скопировать текст для публикации» — вход в PR-5.7.

## Acceptance criteria — «PR готов, когда…»

- [ ] Номера от random.org помечают билеты `is_winner`, ранг = позиция в списке.
- [ ] Тираж переходит в `drawn`, проставляется `drawn_at`.
- [ ] Номер, принадлежащий уже выигравшему, **отклоняется 409** с сообщением, называющим номер.
- [ ] Человек с двумя билетами не может получить два приза ни в одном порядке ввода.
- [ ] Повторный вызов на разыгранном тираже → 409, ничего не меняется.
- [ ] **Забракованный список не пишется ЧАСТИЧНО:** после отказа ни один билет не помечен
      победителем и статус тиража остался `committed` (проверяется счётчиком, а не только кодом ответа).
- [ ] Номер вне диапазона / дубль в списке / пустой список → 400 / 400 / 422.
- [ ] Одновременный вызов двумя администраторами: ровно один успешен, второй 409.
- [ ] Хеш снимка **не меняется** после записи победителей — выгрузка PR-5.4a по-прежнему сходится.
- [ ] Доступ: без токена 401 · юзерский токен 403 · админ-типизированный токен не-админа 403.
- [ ] Каждая мутация тест-плана даёт RED, факт отката проверен после каждой.

## Test plan

**Правило одного приза (ядро PR)**
1. Участник с двумя билетами: первый выигрывает — второй номер отклоняется 409, сообщение содержит номер.
2. Тот же случай в обратном порядке ввода — результат тот же (правило не зависит от порядка).
3. Два разных человека — оба записываются, ранги 1 и 2.

**Границы ввода**
4. Номер `0`, `total+1`, отрицательный → 400.
5. Дубль номера в списке → 400.
6. Пустой список → 422.

**Состояние тиража**
7. Незамороженный тираж (`committed` отсутствует) → 409.
8. Повторный вызов на `drawn` → 409, `drawn_at` не переписан, победители прежние.
9. **Гонка:** два одновременных вызова — ровно один успех, один 409, в БД один набор победителей.

**Контракт честности**
10. **Хеш снимка не меняется** после записи: пересчёт по строкам сходится с `participant_hash`,
    выгрузка PR-5.4a отдаёт 200, а не 409. (`is_winner`/`prize_rank` в хеш не входят — это
    проверялось уже в PR-5.4a, здесь проверяется с другой стороны: запись их не ломает.)

**Доступ**
11. Без токена 401 · юзерский 403 · админ-типизированный токен не-админа 403 · админ 200.
12. `loyalty_enabled=false` → 404.

**Мутации (обязательны, RED у каждой)**
- **M1** снять проверку «владелец уже выиграл» → падает (1) и (2).
- **M2** исключать номер вместо человека → падает (1) или (2) — ловит именно подмену правила.
- **M3** снять `AND status='committed'` из UPDATE → падает гоночный тест (9) и повтор (8).
- **M4** ранг = константа 1 → падает (3).
- **M5** снять проверку диапазона → падает (4).
- **M6** `require_admin` → `verify_admin_jwt` → падает (11).
- **M7** записывать `is_winner` в поля, входящие в хеш → падает (10).
- **M8** записывать номера по одному, коммитя каждый до проверки следующего (частичная запись)
  → падает критерий «после отказа не помечен ни один билет». Стережёт §1b.

Прогон под `TZ=UTC`. Перед мутациями — всё в коммит и гард `git diff HEAD --quiet || exit`.
