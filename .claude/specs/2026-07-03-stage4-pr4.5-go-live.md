## Цель — один абзац
Включить программу «Biotact Club» для реальных пользователей: `loyalty_enabled` off→on на проде
(api + бот), после чего живыми становятся вход/согласие/анкета (4.2–4.4b) и денежная петля
активации→кэшбэк→статус «Друг» (Этапы 2–3). Это **go-live** — необратимый, обращённый наружу шаг,
поэтому он гейтится не размером диффа, а готовностью прода и явным решением Капитана.

## Механизм флипа (проверено на проде 2026-07-03)
Флаг читается в ДВУХ процессах, оба сейчас `False` по умолчанию, env не задан:
- **api** — `packages/api/src/config.py:25` `loyalty_enabled: bool = False`; гейтит ВСЕ loyalty-роуты
  (`require_loyalty_enabled` → dark-404).
- **bot** — `packages/bot/bot/core/config.py:31` `loyalty_enabled: bool = False`; гейтит `qr_`-deeplink
  (`handlers/loyalty.py:77` → иначе обычный `/start`).

Флип = задать `LOYALTY_ENABLED=true` в прод `packages/api/.env` И `packages/bot/.env` →
`pm2 restart api bot`. **НЕ менять code-default на `True`** — от `False` зависят dark-404-тесты в CI
и безопасность dev/локали; прод флипается ТОЛЬКО через env.

## 🚨 Открытый вопрос (Гейт-1, решение Капитана) — БЛОКЕР флипа
Прод: `qr_codes = 0`, `code_batches = 0`. Цены есть (56/56 товаров). Флип без кодов = вход/анкета
работают, но **активировать коробку и получить кэшбэк нельзя** (нечего). Хуже — если коробки уже
напечатаны с QR, а кодов в БД нет, каждое сканирование = 404.
Развилки (в порядке моей рекомендации): (1) коробки ещё не печатались → генерим батч CLI → печать →
флип, когда коробки в обороте; (2) коробки уже с QR → ЗАГРУЗИТЬ те же коды в `qr_codes` ДО флипа
(нужен список из типографии + загрузчик/сверка); (3) генерим батч сейчас + валидируем 1 код E2E;
(4) мягкий запуск только-вход (флип без кодов, кэшбэк инертен) — против рекомендации.
**Рекомендация: не флипать, пока go-live не цельный (вход + заработок).**

## Runbook флипа — пре-флип чеклист + точка невозврата (Гейт-1 находки)

**Пре-флип чеклист (всё ✅ ДО установки `LOYALTY_ENABLED=true`):**
- [ ] QR-коды готовы в `qr_codes` (тёмный батч сгенерирован, статус `generated`) — иначе кэшбэк-петля мертва.
- [ ] **(#5)** `webapp_url` бота на проде указывает на живой прод-мини-апп (deep-link активации
      открывает `{webapp_url}?code=<code>`; проверить `grep WEBAPP_URL packages/bot/.env` + открыть URL).
- [ ] api+bot .env готовы к правке; `pm2` видит оба процесса `online`.
- [ ] Прод HEAD = main; последний Deploy success.

**Точка невозврата (#1):** флип обратим — вернуть `LOYALTY_ENABLED=false` + `pm2 restart api bot` —
**ровно до первой реальной активации/начисления.** Как только первый живой пользователь получил
баллы (строка в `point_ledger`), откат «выключить» больше не отменяет уже начисленное (баллы = 1 сум,
обязательство перед клиентом). До этого момента данных пользователей нет → выключение чистое.

**Первый flag-on = сразу прод (#2):** пре-прод-репетиции flag-on НЕТ (нет staging-контура с ботом+
мини-аппом). Механика flag-on доказана в тестах (monkeypatch flag=True → 200) и на parity (dry-run
активации на схеме `alembic upgrade head`), но ПЕРВЫЙ живой flag-on случится непосредственно на проде.
Поэтому флип — деликатная операция под наблюдением: сразу после неё прогнать flag-on smoke (ниже) с
тест-аккаунтом ДО того, как коды раздаются пользователям.

## Тест-план
**Code PR:** api `pytest` (dark-404 тесты остаются зелёными — доказывают, что default всё ещё false),
front `vitest`/build, bot `pytest`/ruff. Мех-гейты как в CI.
**Flag-on smoke (прод, после флипа):** с валидно-подписанным initData (тест-Telegram-аккаунт):
1. `GET /api/v1/loyalty/me` → 200 (не 404) — гейт снят.
2. `POST /api/v1/loyalty/consent {source:"direct"}` → 200, `joined:true` (вступление).
3. `POST /api/v1/loyalty/survey {age:…}` → 200, `survey_done:true`.
4. Если коды готовы: бот `qr_<code>` → шеринг телефона → мини-апп `?code=` → `POST /qr/activate`
   → 200 `activated`, кэшбэк начислен; повтор → `already_activated` (идемпотентность).
5. `/health` 200, `/products` 200 (магазин не задет).
**Откат:** вернуть `LOYALTY_ENABLED=false` (или убрать строку) в api+bot .env → `pm2 restart api bot`
→ все loyalty-роуты снова 404 (тёмные). Обратимо, данные пользователей остаются (не удаляются).
