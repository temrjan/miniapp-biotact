# Спека — Модель-1: резерв → списание при оплате (частичное списание баллов)

**Создан:** 2026-07-16 · **Кресло:** Инженер · **Стек:** FastAPI/SQLAlchemy/PG · **Гейт-1:** заново
**Триггер:** live-инцидент — частичный заказ Тимура (order 75) сжёг 17300 баллов на брошенной оплате Uzum. Степпер уже спрятан kill-switch'ем (#88, на проде); Тимур восстановлен вручную (ledger `redeem_refund`).

## Цель — один абзац
Баллы за частичный заказ должны уходить из леджера ТОЛЬКО когда карта реально оплатила остаток. Сегодня они списываются при создании заказа (PR-6.3-v2) и не возвращаются ни при отказе карты, ни при abandon — **горят**. Меняем на модель «резерв → списание при успехе»: при создании частичного заказа баллы РЕЗЕРВИРУЮТСЯ (строки в леджере нет), реальное списание пишется в success-колбэке. Брошенный/сорванный заказ → строки нет никогда → **гореть структурно нечему**.

## Факты, добытые пробами (не переоткрывать)
- **Multicard на abandon НЕ шлёт вебхук** — order 75 имеет `payment_uuid`, но 0 строк в `payment_event`. Error/revert-обработчик такое не поймал бы → таймаут-очистка ОБЯЗАТЕЛЬНА.
- **Сегодня НИ ОДИН путь отказа карты не возвращает баллы** (grep refund по src/ — пусто), даже при явном error-вебхуке. (Находка Ревьюера.)
- **`DELETE /payment/invoice/{uuid}`** аннулирует **только неоплаченный** инвойс (doc §3.3). Успех → `{"success": true, "data": []}`. Если платёж уже завершён → `{"success": false, "error": {"code": "ERROR_FIELDS", "details": "Транзакция по инвойсу завершена…"}}` — **третий путь горения** (см. §money-safety ниже).
- **ФИКС ФАКТ-ОШИБКИ (Ревьюер, Гейт-1):** ресурс инвойса Multicard **не имеет поля `expiry`** — сверено по первоисточнику (doc §3.1 create-ответ, §3.2 GET-ответ: поля нет). `expiry` в доке принадлежат ДРУГИМ ресурсам (auth-токен, токен карты `yymm`, hold в минутах). Статус `active/draft/deleted` (doc:367) — из §4.2 (callback привязки КАРТЫ), не инвойса. → TIMEOUT очистки берём от **`order.created_at`** (свои часы), НЕ от несуществующего invoice `expiry`.
- `payment_event` state-machine (`_ALLOWED_FROM`, `lifecycle.py:49-53,177`) уже защищает: success/error применяются только из `unpaid`/`pending`; после `failed`/`cancelled` поздний вебхук пишется в аудит, НЕ применяется. → БД защищена; риск — только КАРТА (поздняя авторизация по неудалённому инвойсу).

## 🔒 Money-safety — закреплено явно (Гейт-1, находки Ревьюера)
> Архитектура верна; корень инцидента Тимура — «подразумевалось, не закреплено». Три механизма ниже — ОБЯЗАТЕЛЬНЫ в тексте, не подразумеваются.

**M1 — место записи `commit-redeem` (БЛОКЕР-1a).** `redeem −N` пишется ФИЗИЧЕСКИ ВНУТРИ уже существующего guarded-блока `if status == STATUS_SUCCESS:` в `lifecycle.py:188-193` — там же, где `applied_success = True`, ПОСЛЕ гварда состояния (`lifecycle.py:177`, `order.payment_status in _ALLOWED_FROM[success] = {unpaid,pending}`). Тогда поздний success на уже `cancelled`-заказе отбивается гвардом стр.177 ДО записи баллов → лишней `redeem`-строки не появится. Если списание окажется ВНЕ этого блока (отдельным шагом) — гвард его не прикроет = запрещено.

**M2 — очистка отменяет заказ атомарным условным UPDATE (БЛОКЕР-1b).** Cancel зомби-заказа = `UPDATE orders SET payment_status='failed', status='cancelled' WHERE id=:id AND payment_status IN ('unpaid','pending')` (0 строк ⇒ кто-то уже settle-нул, no-op). НЕ read-then-write. Паттерн уже канон в коде: атомарный claim `activate_code` (`loyalty/service.py:487-499`), `try_arm_payment_attempt`. Гонка «очистка против настоящего success» решается row-lock'ом на заказе (success берёт `Order FOR UPDATE`, `lifecycle.py:124`) — «кто раньше записал», без окна.

**M3 — порядок и обработка ошибки `delete_invoice` (БЛОКЕР-2).** DELETE у Multicard отказывает на уже оплаченный инвойс (`success:false`, «Транзакция завершена»). Контракт очистки:
  1. `delete_invoice(payment_uuid)` — СНАЧАЛА.
  2. `success:true` → M2 (атомарный cancel). Удалённый инвойс оплатить уже нельзя ⇒ cancel после успешного delete безопасен для КАРТЫ.
  3. `success:false` ИЛИ сетевая ошибка/таймаут → **НЕ отменять заказ**, залогировать + алерт, оставить `unpaid`/`pending`. Баллы не горят (строки в леджере нет — резерв без ledger-строки этого не касается); если платёж всё же прошёл — штатный success-колбэк settle-ит заказ нормально (M1). Никогда не отменяем заказ, чей инвойс не подтверждён удалённым.
  4. **Очистка — отдельная зафиксированная единица** (не в транзакции `create_order`): внешний side-effect `delete_invoice` не должен осиротеть при откате создания заказа. Иначе rollback create → инвойс удалён, а cancel откатан → зомби с мёртвым инвойсом. (Идемпотентность повторного delete на уже-удалённом — см. DISCOVER.)

## Скоуп PR — что входит
- **`redeem_points` → `reserve` + `commit`** (или переструктурировать): убрать запись леджера из `create_order` частичного пути.
- **`create_order` частичный:** валидировать `available = SUM(ledger) − Σ зарезервированного` под `customer_profile FOR UPDATE`; НЕ писать леджер; `points_applied=N`, заказ `unpaid`.
- **success-колбэк (`payments/lifecycle.process_payment_event`):** при `points_applied>0` и переходе в `paid` — записать `redeem −N` **внутри guarded-блока `if status == STATUS_SUCCESS:` (стр.188-193)** — см. **M1**. Резерв гарантирует достаточность; guard на негатив (M3.3 §DISCOVER).
- **Полное покрытие — БЕЗ изменений:** списывается атомарно при создании (карты нет, гореть нечему).
- **Zombie-cleanup (В ЭТОМ ЖЕ PR — условие Ревьюера):** свои `unpaid`-частичные старше TIMEOUT (от **`order.created_at`**) → `delete_invoice` → при `success:true` атомарный cancel — см. **M2/M3**. Резерв освобождён. Без возврата (баллы не уходили). Триггер — см. Развилку 2.
- **Композитный индекс `orders(user_id, payment_status)` (МИНОР Ревьюера):** подзапрос резерва фильтрует `WHERE user_id=X AND payment_status IN ('unpaid','pending')`; сейчас индекс только по `user_id` — связки нет → рост заказов = seq-scan подзапроса. Дёшево добавить, раз уже трогаем эти файлы. ⚠️ Это **schema-изменение → Alembic-миграция → гейт `Migration parity`** (CLAUDE.md; `CREATE INDEX`, round-trip up→down→up на чистом parity-PG). Индекс-only, низкий риск, но гейт обязателен.
- **Фикс стейл-докстрин** `redeem_points`/`InsufficientPointsError` (`loyalty/service.py:61-67,76-96` — описывают all-or-nothing, неверно с PR-6.3-v2).
- **Вернуть kill-switch фронта в `true`** (отдельный мелкий шаг после выката) — НЕ в этом PR (фронт), но пометить в порядке.

## 🔀 Развилки к ратификации (Гейт-1)

**Развилка 1 — учёт резерва. ✅ РАТИФИЦИРОВАНО Гейтом-1: вычислять, без новой колонки.**
`available = SUM(point_ledger.amount WHERE user_id=X) − Σ(orders.points_applied WHERE user_id=X AND payment_status IN ('unpaid','pending') AND points_applied>0)`. Резерв = ещё-не-списанные частичные заказы того же юзера. Плюс (подтверждено Ревьюером): нет derived-колонки, которую надо руками синхронизировать (ровно то, что разъехалось у докстрин); **резерв освобождается САМ**, как только `payment_status` выходит из `('unpaid','pending')` — отдельного `release`-кода не нужно (ни error/revert-ветка `process_payment_event`, ни cleanup ничего не пишут в `points_applied`). Контраргумент «запрос тяжелее» снят композитным индексом `(user_id, payment_status)` (см. Скоуп). Факт-переключатель: если заказов на юзера станут тысячи и подзапрос под локом станет узким местом → материализованный `reserved` столбец.

**Развилка 2 — чем чистить zombie-резерв. ✅ РАТИФИЦИРОВАНО Гейтом-1: только ленивая очистка своих (а). Sweep (б) — отдельный PR.**
- (а) **Лениво:** в начале частичного пути `create_order` (ДО money-лока, чтобы сетевой `delete_invoice` не держал `customer_profile FOR UPDATE`) expire СОБСТВЕННЫЕ `unpaid`-частичные старше TIMEOUT по контракту M2/M3. Резерв per-user ⇒ зомби юзера уменьшает только ЕГО available, чужих не трогает ⇒ money-safety не зависит от того, вернётся ли он.
- (б) **Периодический sweep** — гигиена (админ-отчёт PR-6.5, освобождение резерва «ушедших навсегда»), НЕ деньги. Планировщика нет (Развилка 3) → **отдельный PR, вне скоупа**.
- **TIMEOUT — от `order.created_at`** (не от invoice `expiry` — его нет, см. §Факты). Значение **[ТВОЙ ВЫБОР, Капитан]**, РЕКОМЕНДУЮ **30 минут**: одна попытка оплаты укладывается в минуты (сессия привязки карты Multicard — 15 мин, doc §4.3), 30 мин = 2× запас, не срежет платящего. Ошибка значения НЕ ведёт к горению баллов (строки в леджере нет при любом TIMEOUT) — только слишком агрессивный TIMEOUT может отменить заказ у ещё-платящего (UX-вред, не денежный); слишком мягкий — дольше держит резерв. Низкая цена ошибки.

**Развилка 3 — планировщик для sweep. ✅ РЕШЕНО фактом (2026-07-16): фонового воркера НЕТ.**
Проверено: ни APScheduler/celery/arq, ни в requirements, ни в `main.py` lifespan. → Модель-1 делает **только ленивую очистку (а)** — этого достаточно для money-safety (баллы структурно не горят; резерв освобождается при следующей попытке юзера). Sweep (б) + инфра планировщика — **отдельный PR**, НЕ в скоупе (rules #3/#5: не тащим инфру под гипотетическое). Пометить в отчёте как «Замечено, вынесено».

## Критерии приёмки
- Частичный заказ создан → **строки в леджере НЕТ**, `available` уменьшился на N (резерв), баланс (SUM ledger) не изменился.
- Success-колбэк по остатку → появляется РОВНО одна `redeem −N`, баланс уменьшился на N.
- Заказ брошен/отказ карты → строки в леджере НЕТ никогда → баланс не тронут; по таймауту инвойс удалён + заказ cancelled.
- Гонка двух частичных под один available → второй 409 (резерв не даёт overspend), баланс не в минус.
- **Late-success-after-cleanup (M1):** заказ cleanup'нут (cancelled + invoice deleted) → приходит success на его старый `payment_uuid` → НИ ОДНОЙ новой `redeem`-строки, баланс не тронут, заказ остаётся cancelled.
- **delete-invoice-already-paid (M3):** `delete_invoice` вернул `success:false` («завершена») → заказ НЕ отменён, остаётся `unpaid`/`pending`, алерт/лог записан.
- **Резерв освобождён после cleanup:** после отмены заказа A тот же юзер резервирует сумму, которая раньше не пролезла бы (её занимал A) → теперь проходит.
- Полное покрытие — как сейчас (атомарно paid + списано).
- Стейл-докстрины исправлены.

## Тест-план (строгость PR-6.3: мутации)
- **Резерв:** частичный create → 0 строк леджера, `available` учитывает резерв *(мутация: вернуть старое списание в create → красный «строк 0»)*.
- **Commit:** success-колбэк → одна `redeem −N`, баланс −N *(мутация: не писать redeem в колбэке → красный)*.
- **Abandon-no-burn:** частичный create → колбэка нет → баланс НЕ тронут *(это и есть фикс инцидента; мутация: списание в create → баланс упал → красный)*.
- **Гонка:** два частичных, сумма > available → один 409, баланс не минус *(мутация: снять учёт резерва → оба проходят → красный)*.
- **Cleanup:** брошенный частичный старше TIMEOUT → `delete_invoice` вызван + заказ cancelled + резерв освобождён (мок Multicard).
- **[Гейт-1 #1] Late-success-after-cleanup:** заказ cancelled + invoice deleted → success на старый `payment_uuid` → assert: 0 новых `redeem`-строк, баланс не тронут, заказ остаётся cancelled *(мутация: вынести запись redeem из-под гварда стр.177 → строка появится → красный)*. Это ровно сценарий, который просили оценить — тест, не только рассуждение.
- **[Гейт-1 #2] delete-invoice-already-paid:** мок `delete_invoice` → `{success:false, error:{code:"ERROR_FIELDS"}}` → assert: заказ НЕ отменён, `unpaid`/`pending`, алерт/лог записан *(мутация: отменять заказ независимо от результата delete → заказ cancelled → красный)*.
- **[Гейт-1 #3] reserve-freed-after-cleanup:** заказ A держит резерв → cleanup отменяет A → тот же юзер резервирует сумму, что раньше упиралась в A → проходит *(мутация: cleanup не освобождает резерв → 409 → красный)*.
- **Полное покрытие / карта — регресс.**

## Открытые вопросы (DISCOVER — на реализацию, не блокируют Гейт-1)
- ✅ ЗАКРЫТ: invoice `expiry` не существует → TIMEOUT от `order.created_at` (см. §Факты, Развилка 2).
- **M3.4 идемпотентность повторного `delete_invoice`** на уже-удалённом инвойсе (редкий кейс, если предыдущая очистка удалила, но её cancel не зафиксировался — исключается при «очистка = отдельная зафиксированная единица», но подтвердить ответ Multicard на double-delete). Решаем в коде: любой `success:false` от delete ⇒ НЕ отменять (консервативно, money-safe), отличать «оплачен» от «уже удалён» не требуется для безопасности.
