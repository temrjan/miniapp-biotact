# PR-5.5 — Экран «Мои билеты» (Этап 5)

> Дата: 2026-07-28 · Топик: `stage5-lottery` · Кресло: КОМАНДА (Claude=Инженер + отдельный Ревьюер)
> Родительская спека: `.claude/specs/2026-07-24-stage5-lottery.md`
> База: `main` = `5100383` (PR-5.4a на проде)

## Goal

Участник не видит своего участия в розыгрыше вообще. Билеты считаются, замораживаются и
публикуются — но человек об этом узнаёт только из маркетинга. Этот PR даёт карточку в мини-аппе:
сколько у меня билетов, за что они начислены, как получить ещё, и чем всё кончилось после
розыгрыша.

## Approach — chosen + why

**Два источника числа билетов, и разница между ними показывается честно.**

До заморозки строк `lottery_tickets` не существует — их создаёт `commit_draw`. Значит до заморозки
число считается **предварительно** уже готовой чистой функцией `compute_ticket_count(profile,
as_of=now)`, а после заморозки берётся из **замороженных строк**. Ответ несёт флаг `is_frozen`,
и формулировка на экране меняется вместе с ним: «сейчас у вас N билетов» против «вы участвуете
с N билетами».

Смешивать их в одно число молча нельзя: предварительное может измениться само (активация
выпадет из 30-дневного окна), и «2 билета», превратившиеся в «1», без объяснения выглядят как
отъём.

## Решения Гейта-1

### 1. Три состояния — по статусу последнего розыгрыша, а не по флагам на фронте

`current` = розыгрыш с максимальным `period`.

| Состояние | Что показываем |
|---|---|
| розыгрыша нет | предварительный подсчёт на ближайший период |
| `current.status == committed` | замороженное число билетов, участие зафиксировано |
| `current.status == drawn` | итог (выиграл / не выиграл, ранг приза) **плюс** предварительный подсчёт на следующий период |

Третья строка — не украшение: после завершённого розыгрыша показать голый «0 билетов» значит
сказать активному участнику, что он выбыл, тогда как он уже копит на следующий месяц.

### 1b. Форма ответа — прибита гвоздями, не на усмотрение кода

Поля перечислены заранее по тому же уроку, что дал `/check` на PR-5.4a: незакреплённая форма
рождает поля, которых никто не читает.

```
MyTicketsResponse           # «моё участие СЕЙЧАС»
  tickets:     int          # не nullable; сколько билетов показываем
  is_frozen:   bool         # true = замороженное участие · false = предварительный подсчёт
  period:      str | None   # период, к которому относится `tickets`
  prize_label: str | None   # только из БД; None ⇒ блок приза не рендерится
  result:      DrawResult | None   # «чем кончился ПРОШЛЫЙ розыгрыш»

DrawResult
  period:      str
  tickets:     int          # сколько билетов было у участника в том розыгрыше
  won:         bool
  prize_rank:  int | None   # 1..4 у победителя, None если не выиграл
  prize_label: str | None
```

Верхний блок отвечает «что у меня сейчас», `result` — «чем кончилось прошлое». В состоянии `drawn`
они несут разное: верх — предварительный подсчёт на следующий период, `result` — завершённый
розыгрыш. Поэтому `prize_label` живёт в обоих местах и это не дублирование: сверху — приз того
розыгрыша, в котором я участвую, внутри — приз того, который уже прошёл.

**Инварианты (каждый — отдельный assert, не проза):**

| # | Инвариант |
|---|---|
| И1 | `period is not None` ⟺ `is_frozen is True` |
| И2 | `prize_label is not None` ⇒ `is_frozen is True` (приз известен только из замороженного розыгрыша) |
| И3 | `result is not None` ⟺ последний розыгрыш в статусе `drawn` |
| И4 | в состоянии `drawn` верхний блок всегда предварительный: `is_frozen is False` |

| Состояние | `tickets` | `is_frozen` | `period` | `prize_label` | `result` |
|---|---|---|---|---|---|
| розыгрышей нет | предварительное | `false` | `None` | `None` | `None` |
| `committed` | замороженное | `true` | период розыгрыша | из БД (может быть `None`) | `None` |
| `drawn` | предварительное на следующий | `false` | `None` | `None` | заполнен |

### 2. Self-scope

Аутентификация — initData HMAC (`get_init_data_user`), как у всей мини-апп-поверхности лоялти.
Чужие билеты недостижимы by construction: выборка идёт по `user_id`, выведенному из подписи, а не
из параметра запроса. Тест на это обязателен.

### 3. Read-only

GET ничего не пишет. Не создаёт ни `users`, ни `customer_profile` — как `get_loyalty_summary`
(`service.py:320-341`). Неизвестный пользователь получает нулевой ответ, а не строку в БД.

### 4. Фронт — deploy-window дефолты обязательны

`api/loyalty.ts` маппит snake_case DTO → camelCase домен и **подставляет дефолты на отсутствующие
ключи** (`?? null`, `?? false`), потому что в окне деплоя фронт новее API. Конвенция уже живёт в
файле (строки 77-94) и нарушать её нельзя: `undefined`, протёкший в доменный тип, обещающий
`| null`, — это баг на проде, а не косметика.

### 5. Тексты — RU и UZ обязательно оба

`src/i18n/{ru,uz}.json`. Пропустить UZ нельзя: рынок Узбекистан, у части аудитории интерфейс на
узбекском, и отсутствующий ключ отрендерится как сырой идентификатор.

## 🔴 Две развилки Капитану

### Развилка 1 — отсчёт до эфира: **рекомендую НЕ строить в этом PR**

Эпик перечисляет «отсчёт до 1-го числа» во входе PR-5.5. Рекомендую **исключить**.

- **Почему.** Дата эфира не решена — ты сказал 28.07 прямым текстом: «сейчас не известно когда
  будет розыгрыш». А `loyalty_enabled=true` с 06.07: всё, что попадёт на экран, увидят реальные
  люди сразу. Таймер — это обещание конкретной даты, которого никто не давал.
- **И считать не от чего.** В `lottery_draws` нет колонки даты эфира (`period`, `committed_at`,
  `drawn_at` — и всё). Отсчёт пришлось бы выводить из формулы «1-е число следующего месяца, 19:00
  Ташкент», то есть зашить в код невыясненный факт.
- **Самоатака.** Карточка без таймера менее «живая», сроки подгоняют человека заполнить анкету.
  Не перевесило: неверная дата дороже отсутствующей — её увидят все, и это ударит по доверию,
  на котором построен весь Этап 5.
- **Цена ошибки, если я неправ.** Пропущенный элемент вовлечения на один-два PR. Обратимо:
  таймер добавляется отдельным маленьким PR, когда дата известна.
- **Факт-переключатель.** Маркетинг фиксирует дату/время эфира → строим таймер, и тогда же
  обсуждаем колонку `airs_at` в `lottery_draws` (миграция, деплой-гейт).

### Развилка 2 — приз: **рекомендую показывать только реальный `prize_label`**

`prize_label` заполняется при заморозке и может быть `NULL`. До первой заморозки приза в системе
нет вообще.

- **Рекомендую:** блок приза рендерится, только если `prize_label` не пуст. Никаких зашитых
  «Аэрогриль» в коде или в i18n.
- **Почему.** Приз — маркетинговый факт, он меняется от месяца к месяцу. Зашитый в код он станет
  враньём в первый же месяц, когда приз сменят, и правка потребует релиза.
- **Самоатака.** Пустой блок в первый месяц выглядит недоделанным. Не перевесило: «приз будет
  объявлен» честнее конкретного неверного приза.
- **Факт-переключатель.** Если решишь, что приз постоянный и не меняется — кладём в i18n
  как обычный текст, это дешевле.

## Acceptance criteria — «PR готов, когда…»

- [ ] Розыгрыша нет → предварительный подсчёт, `is_frozen=false`, формулировка «сейчас у вас N».
- [ ] Розыгрыш `committed` → число из замороженных строк, `is_frozen=true`.
- [ ] Розыгрыш `drawn` → итог (выиграл/нет, ранг) + предварительный подсчёт на следующий период.
- [ ] Чужие билеты недостижимы: два участника с билетами в одном розыгрыше видят каждый своё.
- [ ] GET не создаёт ни `users`, ни `customer_profile` (проверено счётчиком строк до/после).
- [ ] `loyalty_enabled=false` → 404 · без initData → 401.
- [ ] Карточка рендерит 3 состояния; ключи есть и в `ru.json`, и в `uz.json`.
- [ ] Каждая мутация из тест-плана даёт RED, факт отката проверен после каждой.

## Test plan

**API**
1. Матрица трёх состояний (нет розыгрыша / `committed` / `drawn`).
2. **Инварианты И1–И4 из §1b — отдельными assert'ами** на каждом из трёх состояний. Без них форма
   ответа держится на прозе, а не на тесте.
3. **Состояние `drawn` несёт ОБА блока:** `result` заполнен И `tickets` содержит предварительный
   подсчёт на следующий период. Проверяется одним тестом, где у участника есть свежая активация
   после завершённого розыгрыша: `result.tickets` и верхний `tickets` — разные числа, и верхнее
   не ноль. Это §1 «третья строка — не украшение», переведённое в assert.
4. Self-scope: два участника, у каждого своё число; запрос одного не видит билеты другого.
5. Read-only: `count(users)` и `count(customer_profile)` не меняются после GET неизвестным юзером.
6. **Профиля не существует вообще** (пользователь есть, `customer_profile` нет — и отдельно:
   пользователя нет вовсе): нулевой ответ без единой записи в БД. Это НЕ то же, что «анкета
   заполнена частично»; `/me` держит для этого именованную ветку `_non_member_summary`
   (`service.py`), и полагаться, что здесь оно «унаследуется само», нельзя — проверяем тестом.
7. Предварительный подсчёт совпадает с `compute_ticket_count` на той же матрице профилей
   (анкета полная/частичная × 18+ по возрасту/галке × активация свежая/старая × newbie/friend).
8. Доступ: `loyalty_enabled=false` → 404; без `X-Init-Data` → 401.

**Фронт (vitest)**
9. Три состояния карточки рендерятся; при отсутствии данных (404/загрузка) карточка скрыта,
   профиль продолжает работать — как `LoyaltySection` уже делает.
10. **Формулировка, а не только число.** Assert на ТЕКСТ: при `is_frozen=false` карточка говорит
    «сейчас у вас N билетов», при `is_frozen=true` — «вы участвуете с N билетами». Одинаковое
    число при разных состояниях не должно давать одинаковый экран — в этом весь смысл PR, и без
    текстового assert'а главное решение спеки ничем не закреплено.
11. Отсутствующие ключи DTO не протекают как `undefined` в доменный тип.

**Мутации (обязательны, RED у каждой)**
- M1 `is_frozen` всегда `true` → падает состояние «розыгрыша нет».
- M2 выборка билетов без фильтра по `user_id` → падает self-scope.
- M3 `status == drawn` трактуется как `committed` → падает состояние итога.
- M4 предварительный подсчёт заменён константой 1 → падает матрица (4).
- M5 снять `require_loyalty_enabled` → падает тест тёмного гейта.
- M6 в маппинге фронта убрать `?? null` → падает тест (11).
- **M7 убрать предварительный блок из ветки `drawn`** (верхний `tickets` → 0, `is_frozen` → `true`)
  → падает тест (3) и инвариант И4. Без этой мутации «третья строка» держится на честном слове:
  M3 ловит подмену статуса, но не потерю предварительного подсчёта внутри правильной ветки.
- **M8 сделать текст карточки одинаковым** для `is_frozen=true/false` → падает тест (10).
  Мутация проверяет не код, а то, что главное решение спеки вообще кем-то стережётся.

Прогон под `TZ=UTC`. Перед мутациями — всё в коммит и гард `git diff HEAD --quiet || exit`.
