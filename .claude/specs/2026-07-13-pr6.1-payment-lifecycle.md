# PR-6.1 — Жизненный цикл платежа (предусловие Этапа 6)

**Дата:** 2026-07-13 · **Природа:** денежный путь. Идемпотентность колбэка + вебхуки неудачи/возврата.
**Зачем сейчас:** без этого **нельзя строить трату баллов** — списанные баллы будет некому вернуть,
а дубль колбэка спишет их дважды.

## 1. Что не так сегодня (код-проверено 2026-07-13)

1. **Колбэк переобрабатывается при каждом повторе.** `payments/router.py:119` — проверяет подпись,
   находит заказ, ставит `paid` + `confirmed`, шлёт уведомление админам. **Дубль не отсекается ничем.**
   Документация Multicard прямо требует обратного: «партнёр обязан ловить дубль по `uuid` и отвечать
   успехом, не переобрабатывая» (колбэк повторяется при таймауте/зависании).
   Сегодня цена дубля — лишнее уведомление админам. **С REDEEM цена дубля — двойное списание баллов.**
2. **Вебхуков нет.** `verify_webhook_sign` (SHA1) написан в `payments/service.py:96` — и **не
   используется ни одним роутом**. Мы не узнаём о статусах `error` (оплата не прошла) и `revert`
   (деньги возвращены). Для Этапа 6 это дыра: баллы списаны, оплата провалилась → вернуть некому.
3. **Сумма колбэка не сверяется с заказом.** `callback.amount` (тийины) не сравнивается с
   `order.total * 100`. Подпись защищает от подделки, но не от рассинхрона.
4. **Гонки не защищены.** Два колбэка параллельно → две записи в тот же заказ без блокировки строки.

## 2. Факты Multicard (документация изучена)

- success-колбэк: `sign = MD5(store_id + invoice_id + amount + secret)`; **партнёр обязан ответить
  200 + `success: true`**; любой другой ответ = **отмена платежа с возвратом**; повторы возможны.
- вебхуки: `sign = SHA1(uuid + invoice_id + amount + secret)`; статусы
  `draft/progress/success/error/revert/hold`; **retry ×5**, если ответ не 2xx; источник — IP `195.158.26.90`.
- инвойс: `amount` в тийинах; `ttl` по умолчанию сутки.

## 3. Развилка — где хранить идемпотентность (предрешена)

**A. Только по строке заказа** (`payment_uuid` + `payment_status`), без миграции.
**B. Новая append-only таблица `payment_event`** (`uuid`, `status`, `amount`, `raw`, время),
**`UNIQUE(uuid, status)`** как ключ идемпотентности + миграция.

**Рекомендую B.** Почему простыми словами: одна и та же оплата присылает нам **несколько разных
событий** (`progress` → `success` → потом, возможно, `revert`). Если хранить только «последнее
состояние» в заказе, мы не сможем честно ответить на вопрос «а возврат мы уже отработали?» — а
именно на него придётся отвечать на Этапе 6, когда за каждым событием стоит движение баллов.
`UNIQUE(uuid, status)` даёт **атомарный** замок: `INSERT ... ON CONFLICT DO NOTHING` — вставка не
прошла, значит событие уже обработано, выходим. Это тот же приём, что уже доказан в лоялти
(`UNIQUE(qr_code_id, reason)` на леджере), а не изобретение.

**Самоатака:** «B — это миграция, а миграция в этом репо однажды уронила прод (#30); A даёт
идемпотентность бесплатно». Не перевесило: во-первых, деплой-гейт с тех пор укреплён и доказан на
реальной схеме **шесть раз** (включая round-trip в CI, #69). Во-вторых, A решает только сегодняшнюю
задачу и разваливается ровно там, где начинаются деньги клиента — при списании баллов A вынудит
угадывать по полю `payment_status`, было ли уже возвращено; это гадание на денежном пути.

**Цена ошибки, если я неправ:** одна лишняя таблица на 5 колонок и одна миграция (обратимая).
**Факт-переключатель:** если Капитан решит, что Этап 6 (REDEEM) НЕ будет строиться в обозримом
будущем — тогда B избыточен и берём A.

## 4. Решение (при выборе B)

1. **Миграция:** таблица `payment_event` — `id`, `payment_uuid` (String, index), `status` (String(20)),
   `amount` (BigInteger, тийины), `invoice_id` (String), `payload` (JSONB), `created_at`.
   **`UNIQUE(payment_uuid, status)`**. Ничего в `orders` не меняем (колонки остаются как есть).
2. **`POST /payments/callback` (success) — переписать:**
   - подпись MD5 (как сейчас) → иначе 400;
   - **сверка суммы:** `callback.amount != int(order.total * 100)` → **НЕ помечаем оплаченным**,
     логируем громко, отвечаем 400 (по документации Multicard это = отмена платежа с возвратом —
     правильное поведение: мы не принимаем оплату не на ту сумму);
   - **идемпотентность:** `INSERT payment_event(uuid, 'success') ON CONFLICT DO NOTHING`;
     0 строк вставлено → событие уже обработано → **сразу `{"success": true}`**, без записи в заказ
     и **без повторного уведомления админам**;
   - заказ обновляется под `SELECT ... FOR UPDATE` (гонка двух колбэков).
3. **`POST /payments/webhook` (новый) — SHA1-подпись:**
   - `success` → тот же путь, что колбэк (общая функция, не копия);
   - `error` → `payment_status='failed'`, заказ → `CANCELLED`;
   - `revert` → `payment_status='refunded'`, заказ → `CANCELLED`;
   - `draft/progress/hold` → записываем событие, заказ не трогаем;
   - **всегда 2xx** (иначе Multicard ретраит ×5), кроме неверной подписи → 400.
4. **Уведомления админам** — только при первой обработке события (внутри «вставка прошла»).

## 5. Тест-план (правило №0 + мутации)

- дубль success-колбэка (тот же `uuid`) → второй раз **200, заказ не переписан, уведомление НЕ ушло**
  (мутация: убрать ON CONFLICT-гард → тест red);
- сумма колбэка ≠ сумме заказа → 400, заказ **не** `paid` (мутация: убрать сверку → red);
- неверная подпись (MD5 и SHA1) → 400, событие не записано;
- вебхук `error` → `failed` + `CANCELLED`; `revert` → `refunded` + `CANCELLED`; повтор того же
  вебхука → 2xx без изменений;
- `draft/progress/hold` → 2xx, заказ не тронут;
- **гонка:** два одновременных success-колбэка (barrier-тест по образцу PR-A лоялти) → ровно одна
  обработка (мутация: убрать FOR UPDATE → red);
- **миграция:** `alembic check` чист + round-trip up→down→up (CI-гейт `Migration parity`, #69).
