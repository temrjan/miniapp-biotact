алерт не уходит вообще. Тот же отказ №2, только вход с другой стороны.

**Фикс** (§4 ниже): защёлкивать переход по **≥1** подтверждённой доставке, не по всем. Сообщение
дошло хотя бы одному человеку — работа сделана. Персональный отказ — не повод крутить машину, а
факт: строка в лог + строка в суточном «сторож жив» («доставка админу N не удалась: 403»).
Различать временный (429/5xx) и постоянный (403) отказ не нужно — правило «≥1» закрывает оба класса
само, без классификации причины.

## 3. Скоуп

### IN
1. `/usr/local/sbin/biotact-sentry.sh` на **bcv2**, root, 700.
2. Cron на bcv2: проверка живости **каждую минуту**; дневные проверки — **раз в сутки**, одним
   отдельным вызовом того же скрипта с флагом `--daily`.
3. Ежеминутно: `GET https://app.biotact.uz/health` (процесс+БД через `SELECT 1`) + `GET
   https://app.biotact.uz/api/v1/products?size=1` (реальная таблица через ORM — ловит сломанную
   миграцию/схему, чего `SELECT 1` не ловит; `?size=1` — та же проверка, минус лишние 27КБ). Оба —
   `--connect-timeout 5 --max-time 10`; провал = таймаут ИЛИ не-200 ИЛИ обрыв DNS, без исключений.
4. Дебаунс: **два провала подряд** → одно сообщение, **переход состояния — по ≥1 подтверждённой
   доставке** (см. §4: БЛОКЕР-1 — не защёлкиваться без проверки доставки вообще; БЛОКЕР-3 — не
   требовать доставки ВСЕМ, постоянный отказ у одного не должен стопорить машину). Одиночный
   сетевой сброс не будит. Восстановление — отдельное сообщение, только после **15 минут
   непрерывной зелени** (анти-флаппинг). `flock -n` на state-файле — два прогона в одну минуту не
   должны терять обновление.
5. Раз в сутки, **два подмножества** (развилка §8.3 решает, строю ли второе):
   - **без нового доступа, строю всегда**: свежесть офсайт-копии на bcv2 (≤26ч, читаю свой же диск,
     она же свежесть локального дампа — см. §2) · срок сертификата `app.biotact.uz` (<14 дней —
     предупредить, внешний TLS-хендшейк) · финальная строка «сторож жив, N/N ок» — **шлётся
     всегда**, даже когда всё зелено (M-8). **Персональные отказы доставки — без отдельного файла**
     (МИНОР, раунд 3): `grep "delivery failed" /var/log/biotact-sentry.log` за последние 24ч,
     свернуть в одну строку, если что-то нашлось. Файл уже в §5, читается не портя, гонки с
     минутным путём нет (append vs read — не конфликтуют так, как read-then-clear конфликтовал бы).
   - **требует решения §8.3, формат — вердикты, не сырые числа** (Ревьюер, условие 2): прод пишет
     `expire_log_ok=yes|no`, `disk_ok=yes|no` (+`disk_pct` для контекста в сообщении),
     `stale_orders_ok=yes|no` (+ счётчик), и `generated_at`. Не «возраст в часах» — снятый в 03:10
     возраст лога устаревает предсказуемо (expire-крон бежит дальше, в 03:20 и т.д.), и арифметика
     «добавить прошедшее время» на bcv2 расходится с реальностью каждый час после снимка. Прод
     знает правду в момент записи — bcv2 доверяет вердикту РОВНО потому, что отдельно проверяет
     свежесть самого файла (≤26ч по mtime), а не потому что что-то досчитывает.
6. Один Telegram-бот (`packages/bot` BOT_TOKEN), рассылка **каждому** id из `admin_ids`, **plain
   text**, без `parse_mode`. Переход состояния — по **≥1** подтверждённой доставке, не по всем
   (БЛОКЕР-3); неудавшийся получатель — строка в лог, не блокировка машины. Тексты — см. §4.
7. State-файл минутки, атомарная запись (`tmp` → `mv`) + `flock -n` **на своём отдельном файле**;
   лог в `/var/log/biotact-sentry.log`. **Суточный прогон НЕ делит ни state, ни lock с минутным**
   (M-10) — отдельный, полностью не пересекающийся путь; если бы делил — `flock -n` молча ронял бы
   суточную проверку почти каждый раз, потому что минутный прогон занят практически всегда, а
   M-8-«сторож жив» замаскировал бы эту пропажу под обычную тишину. Пути state/конфига —
   переопределяемые переменной окружения (§6 тест не пишет в боевое состояние).

## 4. Дизайн проверки живости — State machine (раунд 3: фикс БЛОКЕРА-3)

```
поля state-файла (если файла нет/битый — холодный старт РОВНО с этих значений, не крашимся):
  fail_count = 0, alert_state = ok, green_since = пусто

каждый прогон (раз в минуту, под flock -n на СВОЁМ файле — занят → выходим тихо, не ждём):
  health = curl --connect-timeout 5 --max-time 10 health == 200 AND products?size=1 == 200
  (таймаут/не-200/DNS-обрыв — всё считается провалом, исключений нет)

  если health == false:
    fail_count += 1
    green_since = пусто
    если fail_count >= 2 и alert_state == ok:
        (ok_count, failed_ids) = send_to_all_admins("🔴 app.biotact.uz не отвечает (health/products, N провалов подряд)")
        # БЛОКЕР-3: переход по ≥1 подтверждённой доставке, НЕ по всем — постоянный отказ
        # (403 bot was blocked) у ОДНОГО получателя не должен стопорить машину навечно
        если ok_count >= 1:
            alert_state = error
            если failed_ids не пусто:
                залогировать "delivery failed for {failed_ids}" (греплено суточным — §3.5, отдельного файла нет)
        иначе:
            залогировать "alert send FAILED for ALL admins, will retry next minute"
            # alert_state остаётся ok — следующий провал (fail_count=3) попробует снова

  если health == true:
    fail_count = 0
    если alert_state == error:
        если green_since пусто: green_since = сейчас
        если сейчас - green_since >= 900с:
            (ok_count, failed_ids) = send_to_all_admins("🟢 app.biotact.uz восстановлен, 15 минут стабильно")
            если ok_count >= 1:
                alert_state = ok; green_since = пусто
                если failed_ids не пусто: залогировать "delivery failed for {failed_ids}"
            иначе:
                залогировать "recovery send FAILED for ALL admins, will retry next minute"
                # alert_state остаётся error, green_since НЕ сбрасывается — retried следующей минутой
        # иначе — тихо ждём, ещё не набежало 15 минут
```

**Почему именно так.** БЛОКЕР-1 (раунд 1): без проверки доставки вообще состояние переходит в
`error`, даже если Telegram ответил 429/5xx/сеть отвалилась/токен отозван — второго шанса позвать
на помощь уже не будет. БЛОКЕР-3 (раунд 2, внесён фиксом БЛОКЕРА-1): правило «доставлено, только
если ВСЕ подтвердили» ломается о постоянный (не временный) отказ — `403 bot was blocked by the
user`. Если хоть один админ когда-либо замьютит бота, «все подтвердили» не наступит никогда: либо
второй админ получает алерт каждую минуту весь простой (мьютит бота сам — сторож глушится живым
человеком), либо, на восстановлении, `alert_state` застревает в `error` навсегда и на СЛЕДУЮЩЕЙ
настоящей аварии алерт не уходит вообще — тот же отказ №2, другой вход. **Правило «≥1» закрывает
оба класса причин без необходимости различать 403 от 429/5xx**: сообщение дошло хотя бы одному
человеку — функция выполнена; кто не получил — тихий факт в лог и суточный дайджест, не повод
крутить машину вхолостую.

Повторный провал ДО истечения 15 минут восстановления не шлёт новый алерт (мы уже в `error`) и сбрасывает
`green_since` — счётчик стабильности начинается заново. Это и есть анти-флаппинг.

**Push — правка `/usr/local/sbin/biotact-pg-backup.sh` (уже отревьюен), четыре условия обязательны:**

1. **Сбор фактов — строго ПОСЛЕ финальной `logger … "ok …"`, каждая команда с `|| true`.** Скрипт
   идёт под `set -euo pipefail` — упавшая команда сбора (тот же `df`, севший `psql` для счётчика
   заказов) убьёт `pg_dump`/валидацию/офсайт, если стоит раньше или без `|| true`. Мониторингу
   запрещено ломать бэкап — за его надёжность только что заплачено отдельной аркой.
2. **Прод пишет вердикты, не сырые числа** — формат и обоснование в §3.5.
3. **Суточный прогон на bcv2 — строго ПОСЛЕ 03:10** (например 04:00), иначе читает вчерашний
   `prod-facts.txt` — снимок ещё не подъехал.
4. **Шаг 0 реализации, ДО любого кода сторожа: доказать, что `rrsync -wo` принимает перезапись
   файла с тем же именем.** Дампы всегда уникально названы по времени — перезаписи в этом канале
   ещё ни разу не было, а `prod-facts.txt` перезаписывается ежедневно под одним именем. Не
   предположение «rsync обычно так умеет» — тест тем же ключом/командой, до постройки остального.

`prod-facts.txt` уезжает на bcv2 **тем же** `rrsync -wo`, что и дамп. Новых ключей и открытых
портов на проде — ноль.

## 6. Acceptance criteria — «сдано, когда…»

**Шаг 0, до всего остального:** тестовый файл дважды под одним именем через реальный
`backup_bcv2`-ключ/`rrsync -wo` на bcv2 → вторая копия **перезаписывает** первую, не падает, не
плодит дубликат с суффиксом. Без этого доказательства весь вариант Push не начинается. **Имя —
узнаваемое** (`TESTFILE-overwrite-proof.txt`, не похоже ни на дамп, ни на `prod-facts.txt`), и
**убрать его вручную root'ом на bcv2 после теста** (нит: `rrsync -wo` — write-only, этим же каналом
файл не удалить; забытый тестовый файл иначе так и останется лежать в боевом каталоге офсайта).

- [ ] Скрипт на bcv2, cron стоит: `cat /etc/cron.d/biotact-sentry` показывает обе строки **с полем
      пользователя** (не `crontab -l` — M-9, разные механизмы).
- [ ] Живое **доказательство красного→зелёного**, на **переопределённых** state/config-путях (не
      боевых): намеренно указать проверке на несуществующий адрес → приходит алерт после 2-го
      провала, не после 1-го. Возврат → восстановление **не раньше** 15 минут.
- [ ] **Доказательство БЛОКЕРА-1**: намеренно сломать доставку ОБОИМ (кривой `chat_id` у обоих на
      время теста) при живом провале → `alert_state` **остаётся `ok`**; в логе — «FAILED for ALL».
- [ ] **Доказательство БЛОКЕРА-3 отдельно** (это два разных сценария, не один): (а) сломать доставку
      только ОДНОМУ получателю (второй — рабочий) → состояние **переходит** в `error`/`ok` как
      обычно, строка «delivery failed» в логе, видна в суточном грепе (§3.5); (б) сломать доставку
      ОБОИМ → состояние не переходит, как в БЛОКЕР-1.
- [ ] Дневная проверка прогнана руками один раз — «сторож жив, N/N ок» пришло **даже когда всё
      зелено** (M-8), ни одного ложного предупреждения по пунктам, которые реально построены.
      **Холодный старт дневного пути**: `prod-facts.txt` отсутствует/не читается → сообщение прямо
      называет «факты недоступны», а не молчит как при «ок» (нит).
- [ ] Суточный прогон запущен вручную ОДНОВРЕМЕННО с живым минутным (имитация гонки) → не падает на
      `flock`, потому что не делит с ним файл (M-10) — доказательство, не только чтение кода.
- [ ] Секрет-файл `600`, вне git, содержит `BOT_TOKEN` + `ADMIN_IDS="id1 id2"` (не JSON-копию из
      прод-`.env` — M-6), ничего больше.
- [ ] Два прогона минутного пути подряд в одну минуту (имитация гонки cron) под `flock` — второй
      выходит тихо, state не портится, алерт не дублируется.
- [ ] Холодный старт минутного пути: state-файл удалён/битый → скрипт не падает, стартует с
      `fail_count=0, alert_state=ok`.
- [ ] (Push) `biotact-pg-backup.sh` с добавленным сбором фактов прогнан руками, дамп/офсайт
      по-прежнему проходят валидацию — сбор фактов доказуемо не может их сломать даже при
      намеренно упавшей команде сбора (`|| true` проверен, не только прочитан).
