## Цель

Пользователь мини-аппа видит три юридических документа (Публичная оферта
Biotact Club, Политика конфиденциальности, Условия продажи) нативными
экранами внутри приложения; согласие с офертой/политикой и согласие на
обработку ПД фиксируются двумя чекбоксами при вступлении в Клуб с записью
реальной редакции документов; условия продажи акцептуются строкой на
чекауте; член Клуба управляет маркетинговым согласием из профиля. Действующие
члены получают одноразовое уведомление о публикации документов (п. 13.2
оферты). Всё — без миграций БД, за выкаточным флагом: релиз пользователям —
только после утверждения финальных текстов юристами.

## Подход

Нативные страницы в существующем роутинге мини-аппа; тексты — типизированные
TS-контент-файлы, версия документа живёт только в контент-файле и присылается
клиентом при записи согласия (бэк не знает версий). Расширение существующего
loyalty-контура API (тот же dark-гейт, та же initData-аутентификация, та же
идемпотентная запись). Выкат — за build-time флагом `VITE_LEGAL_DOCS`:
флаг OFF = поведение пиксель-в-пиксель текущее (старый одиночный чекбокс,
старый consent-запрос без версии — обратная совместимость М2), флаг ON =
новая механика. Это снимает противоречие «код сейчас, релиз после
утверждения текстов» при merge=deploy: код мержится и деплоится в любой
момент, пользователи видят новое только после подмены контент-файлов на
финальные редакции + включения флага одним релизом.

## Допущения

- Тексты документов — проекты от 20.08.2026 (`~/Documents/Документы Биотакт
  Клуб/`), версии контент-файлов `draft-2026-08-20`; подмена на финальные
  редакции = правка только контент-файлов (бамп версии в том же коммите).
- Публикация draft-текстов пользователям = действующая редакция → любая
  правка потом требует 30-дневного лага (п. 13.2). Поэтому флаг OFF до
  утверждения текстов (см. Подход), причём флаг закрывает и роуты, и UI
  (Finding 1: «недостижимы из UI» ≠ недоступны — прямой URL тоже закрыт).
  Ставим на: юристы пришлют финал до включения флага.
- Может убить: Telegram-кэш мини-аппа у части пользователей → старые клиенты
  после релиза. Закрыто М2: бэк принимает запрос без `doc_version`
  (дефолт `"1.0"`), старый клиент работает без регрессии бессрочно.
- Осознанно игнорируем: гейт по активному гранту не смотрит версию гранта
  (смена редакции — через уведомление п. 13.2, не повторный чекбокс);
  отзыв основного согласия — не самообслуживание (влечёт удаление аккаунта,
  политика 16.3), в UI строка «через поддержку».

## Контракты

### Контент (фронт)
```ts
interface LegalDocSection { id: string; heading: string; paragraphs: string[] }
interface LegalDoc {
  slug: 'offer' | 'policy' | 'terms';
  title: string;       // юридический заголовок (RU-контент, не i18n)
  version: string;     // ЕДИНСТВЕННЫЙ источник версии; бамп = тот же коммит, что и текст.
                       // Бюджет: ≤ 18 символов (Finding 5 — композит обязан влезать в 50)
  updatedAt: string;   // ISO-дата редакции
  sections: LegalDocSection[];
}
// buildConsentVersion(): `offer:${offer.version}+policy:${policy.version}` (≤ 50 chars)
```

### API
- `POST /loyalty/consent` — body: `{ source, doc_version? }`. `doc_version`:
  опционален (М2, при отсутствии поля в БД пишется `"1.0"` — текущее
  поведение старых клиентов); при наличии валидируется (М1): `max_length=50`,
  паттерн-union (Finding 4): `^(offer:[A-Za-z0-9._-]{1,18}\+policy:[A-Za-z0-9._-]{1,18}|1\.0)$`
  — явный `"1.0"` легален наравне с пропущенным полем, асимметрии
  «прислано → 422 / пропущено → записано» нет. Невалид → 422.
  Бэк пишет значение в `consent.version` как есть; константа
  `DATA_PROCESSING_CONSENT_VERSION` удаляется.
- `POST /loyalty/consent/marketing` — body: `{ granted: bool, doc_version? }`
  (та же валидация, тот же дефолт). Ответ: `{ marketing_active: bool }`.
  Семантика append-style (модель `Consent`, `models.py:36-64`): grant —
  вставка `granted=True`, если активного гранта нет (идемпотентно); revoke —
  вставка `granted=False`, если грант активен. Активность = последняя строка
  по (user, MARKETING) имеет `granted=True`. **Сериализация (Finding 3):**
  проверка-и-вставка выполняются под тем же `SELECT … FOR UPDATE` по строке
  `customer_profile`, что сериализует `record_consent` (`service.py:476-478`),
  — два конкурентных grant не могут создать две активные строки
  (unique-констрейнта нет, замок — единственная защита, и она общая).
- `GET /loyalty/me` — ответ += `consents: { data_processing: bool,
  marketing: bool }` (активные гранты; read-only endpoint остаётся read-only,
  не-member получает false/false).
- Событие: `CustomerEventType.CONSENT_RECORDED = "consent_recorded"` (колонка
  — свободная строка `String(40)`, `models.py:136,165` — миграция НЕ нужна,
  проверено). Пишется при каждой реальной записи согласия; payload:
  `{ purpose, granted, doc_version, source, user_agent }`, где
  `user_agent: str | None` (Finding 7 — заголовок может отсутствовать,
  пишем null). Политика п. 9.3 — дата/время/версия/техданные сессии.

### Флаг
`VITE_LEGAL_DOCS` (build-time, фронт). OFF: ActivationPage/JoinCard — текущий
одиночный чекбокс и consent-запрос без версии; меню «Документы», блок
«Согласия», строка чекаута, баннер — не рендерятся; **роуты `/legal*` не
регистрируются** (прямой URL → редирект на HOME). ON: вся новая механика.
Доступ из кода — через единый хелпер `isLegalEnabled()` (читает
`import.meta.env.VITE_LEGAL_DOCS`), чтобы тесты и рантайм смотрели в одну
точку.

## Команды гейтов

Гейты прогоняются в ОБОИХ состояниях флага (Finding 2 — ON-сьют встроен):
- Фронт OFF (дефолт): `cd packages/frontend && npm run test && npm run lint && npx tsc -b && npm run build`
- Фронт ON: `VITE_LEGAL_DOCS=true npm run test && VITE_LEGAL_DOCS=true npm run build`
  (vitest подхватывает переменную в `import.meta.env` из process env;
  хелпер `isLegalEnabled()` читает её же — механика воспроизводима локально
  и в CI одной командой)
- API: `cd packages/api && ruff check src/ && ruff format --check src/ && mypy src/ --strict --ignore-missing-imports && pytest tests/ -v`
- Тесты по тронутым файлам: `grep -rl <файл> packages/frontend/src packages/api/tests`
- Гейты — последнее действие перед коммитом (Л5).

## Критерии приёмки

PR готов, когда:
1. С флагом OFF все существующие тесты зелёные без правок их ожиданий
   (регрессионный щит); новые тесты новой механики зелёные с флагом ON;
   оба прогона — в выводе гейтов.
2. С флагом ON `/legal` показывает три документа с редакциями; экран
   документа — с оглавлением и uz-плашкой; неизвестный slug → редирект на
   `/legal`. С флагом OFF прямой URL `/legal/offer` → редирект на HOME,
   тексты недоступны.
3. При вступлении в Клуб (оба пути: QR и direct) два не предзаполненных
   чекбокса; кнопка активна только с обязательным; маркетинг опционален;
   переход на документ и возврат состояние галочек не сбрасывает.
4. Член с активным грантом при повторном QR видит кнопку «Активировать»
   сразу, без чекбоксов.
5. consent-запрос несёт композитную версию из контент-файлов; в БД —
   строка как прислана; невалидная версия → 422; запрос без версии и запрос
   с явным `"1.0"` → `"1.0"` в БД.
6. `/loyalty/me` отдаёт `consents`; маркетинг grant/revoke идемпотентны и
   race-safe (FOR UPDATE), состояние в тоггле профиля совпадает с ответом.
7. На чекауте строка акцепта видна в блоке итога до нативной MainButton.
8. Баннер члену показывается один раз на версию; после закрытия не
   появляется; смена `buildConsentVersion()` → появляется снова.
9. Событие `consent_recorded` пишется с payload (purpose, granted,
   doc_version, source, user_agent); отсутствие User-Agent → null, не ошибка.
10. Гейты обоих крыльев зелёные ПОСЛЕ последней правки, вывод приложен.
