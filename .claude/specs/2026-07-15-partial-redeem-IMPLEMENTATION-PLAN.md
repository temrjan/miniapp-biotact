## 4. Бэкенд: правила списания (`orders/service.py`)

Константы (из стратегии §8.8 + решение Капитана 2026-07-14):
```python
MIN_REDEEM = 500          # минимум одного списания (подтверждён Капитаном: остаётся 500)
REDEEM_STEP = 100         # кратность, округление вниз
MIN_CARD_REMAINDER = 5000 # ← решение Капитана: остаток = 0 ЛИБО ≥ 5000 (мёртвая зона запрещена)
```

**Функция расчёта максимума** (чистая, легко тестируется — вынести отдельно):
```python
def max_redeemable(*, balance: int, subtotal: Decimal, total: Decimal) -> int:
    """Наибольшая допустимая сумма списания. 0 = списание недоступно."""
    eligible = subtotal                       # доставка баллами НЕ гасится
    candidates = []
    # Кандидат «полное покрытие товаров»: остаток = delivery_fee (сегодня 0)
    if balance >= eligible and eligible == floor100(eligible):
        remainder = total - eligible
        if remainder == 0 or remainder >= MIN_CARD_REMAINDER:
            candidates.append(int(eligible))
    # Кандидат «частичное»: остаток ≥ MIN_CARD_REMAINDER
    partial = floor100(min(balance, eligible, total - MIN_CARD_REMAINDER))
    if partial >= MIN_REDEEM:
        candidates.append(partial)
    return max(candidates, default=0)
```
⚠️ `eligible = subtotal`, **не `total`** (Ревьюер Раунд 2: иначе будущая платная доставка тихо
погасится баллами вопреки правилу).

**Валидация запроса** — новая ошибка `InvalidRedeemAmountError(OrderValidationError)` → **422**,
если `points_to_apply != 0` и нарушено любое из:
`< MIN_REDEEM` · не кратно 100 · `> max_redeemable(...)` · остаток попадает в мёртвую зону.
В теле ответа отдать вычисленный `max` — фронт сможет clamp'нуть без гадания.

**Удаляется:** `TotalNotPayableWithPointsError` + `_points_total` (`orders/service.py:45-67`) —
защищали модель «покрыть ВЕСЬ total целыми баллами», которой больше нет. Их тесты — переписать.
⚠️ При написании нового кода **не повторять overclaim старого докстринга** («схема гарантирует
целые цены») — это неправда: `products/schemas.py:17` = `gt=0, decimal_places=2`. Писать честно:
«сегодня на проде цены целые» (факт, проверен SELECT'ом).

    #   Вся денежная защита PR-6.3 (доказана 4 мутациями) работает для частичной суммы as-is.

**Гонка (зафиксировано текстом, Ревьюер Раунд 1):** форма-валидация читает баланс БЕЗ лока (это
UX-фильтр), авторитетная проверка — внутри `redeem_points` под `FOR UPDATE`. Два конкурентных
заказа сериализуются на локе; проигравший перечитывает закоммиченный баланс и получает честный
409. Баланс в минус не уходит. Худший случай — UX (409 после успешной формы), не деньги.

### 6a. 🔬 ФИСКАЛЬНАЯ ЧАСТЬ — то, что проверяем эмпирически (`payments/service.build_ofd_items`)

Модель «скидка»: **`Σ ofd[].total` должна равняться `amount`** (иначе чек разойдётся с платежом,
а как Multicard реагирует на расхождение — неизвестно, доки молчат, поддержка не отвечает).

Реализация: распределить скидку по позициям пропорционально, **последняя позиция добирает
остаток округления** (стандартный приём против копеечного расхождения):
```python
def build_ofd_items(order_items, *, amount_tiyins: int) -> list[OFDItem]:
    """Позиции для фискального чека. Σ total ДОЛЖНА == amount_tiyins (модель «скидка»)."""
    # 1. посчитать полные total_tiyins по каждой позиции
    # 2. если Σ == amount_tiyins → вернуть как есть (карточный заказ без баллов — сегодняшний путь)
    # 3. иначе (частичное списание) — масштабировать каждую позицию: total_i * amount / Σ,
    #    price_i = total_i / qty_i (целочисленно, вниз), последняя позиция добирает разницу,
    #    чтобы Σ сошлась ТОЧНО. Ассерт на выходе: sum(i.total) == amount_tiyins.
```
⚠️ **Инвариант-ассерт обязателен** — если суммы не сходятся, лучше упасть громко, чем отправить
кривой фискальный документ в налоговую.

**Замечено, НЕ чиню (в бэклог, rules #3):** `build_ofd_items` при отсутствии ИКПУ подставляет
нули-заглушки (`mxik="00000000000000000"`) — молча шлёт мусор в налоговую вместо явной ошибки.
На проде у всех активных товаров ИКПУ заполнены (проверено), сегодня не стреляет. Там же: `vat`
у всех товаров NULL → в OFD не уходит вовсе.

3. **Смотрим фактический фискальный чек** (`receipt_url` приходит в success-колбэке — для этой

   НДС посчитан от 5 000.
5. Чек кривой → правим `build_ofd_items` ДО того, как покупатели увидят кнопку.
   Чек верный → показываем бухгалтерии → «го» на PR-6.4 (фронт).

## 9. Тест-план (строгость PR-6.3: мутации обязательны)

**Расчёт лимитов** (чистая функция — дешёвые unit-тесты):
- баланс 93 920, товар 94 000 → `max = 89 000` (НЕ 93 900! остаток обязан быть ≥ 5000).
- остаток ровно 5 000 → проходит; остаток 4 900 → **422**; остаток 0 → проходит.
- `subtotal < 5 500` (напр. 3 000) → частичное невозможно вообще, только 0% или 100%
  *(следствие двух порогов — запинить явно, Ревьюер Раунд 2)*.
- доставка > 0 → баллами не гасится: пин **на ОБЕ ветки** — `partial` И `full`.

**Денежный путь** (интеграционные, против реальной PG):
- частичное списание → заказ `unpaid/pending`, ОДНА строка `redeem`, `/payments/create` шлёт
  счёт РОВНО на `total − points_applied` *(мутация: вернуть `int(order.total*100)` → красный)*.
- полное покрытие → `paid`+`CONFIRMED`, `/payments/create` → 400.
- `points_to_apply = 0` (и отсутствие поля) → карточный путь не изменился *(регресс)*.
- гонка: два одновременных частичных заказа, сумма которых > баланса → баланс не уходит в минус,
  проигравший 409 *(мутация: снять `.with_for_update()` → красный; barrier-паттерн из
  `test_loyalty_activation.py`)*.
- `< 500` / не кратно 100 / `> max` / мёртвая зона → 422 с `max` в теле.

**OFD (новое):**
- `Σ ofd[].total == amount_tiyins` для частичного заказа *(мутация: убрать масштабирование →
  красный)*; для карточного заказа позиции не изменились *(регресс)*.

**Уведомления:**
- partial + успешный колбэк → сообщение содержит «💎 Списано баллов» и сумму остатка
  *(мутация: не передавать `points_applied` → красный)*.
- partial при создании инвойса → «НОВЫЙ ЗАКАЗ» с суммой к оплате = остаток.

## 10. Открытый риск (назван честно, НЕ блокирует код)

Чек в модели «скидка» покажет товар по сниженной цене (BIFOLAK за 5 000 при каталожных 94 000), и
**НДС будет посчитан с 5 000**, а не с 94 000. Korzinka решает это иначе (полная цена + строка
«оплачено бонусами» + корректировка НДС `Tuzatish QQS`), но их модель требует СВОЕЙ кассы —
Multicard такого поля не имеет.

Бухгалтерия Капитана сказала «оформляем как скидку хоть 100%» → это и есть выбор Модели 1.
**Если после реального чека бухгалтерия скажет «НДС должен идти с полной суммы»** — фискальную
часть придётся переделывать на собственную фискализацию (§6.6 API Multicard: `PATCH
/payment/{uuid}/fiscal` — «фискализация на стороне партнёра»), это отдельный крупный проект.
Именно поэтому чек смотрим на ОДНОМ тестовом заказе ДО раскатки на покупателей.
