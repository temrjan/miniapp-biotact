# PR-5.3 — Подсчёт билетов + заморозка розыгрыша (Этап 5)

> Дата: 2026-07-27 · Кресло: КОМАНДА (Claude=Инженер + отдельный Ревьюер) · Гейт-1: развилка формулы закрыта Капитаном 27.07 (возраст — не обязательное поле анкеты)
> Эпик-спека: `.claude/specs/2026-07-24-stage5-lottery.md` (§PR scope → PR-5.3)
> Самый рискованный PR эпика: честность розыгрыша + гонки + арифметика времени в одном.

## Goal

Дать администратору один необратимый шаг — **заморозить список участников месяца**: посчитать
билеты по утверждённой формуле, записать их снимком со сквозной нумерацией и опубликовать SHA-256
канонического списка. После этого шага состав участников не может измениться ничем: ни снятием
галки 18+, ни потерей статуса «Друг», ни новой активацией. Победителей этот PR НЕ трогает — жребий
тянет человек вживую через random.org, запись победителей это PR-5.4.

## Approach — chosen + why

Снимок вместо пересчёта. Билеты материализуются строками `lottery_tickets` в момент `commit_draw`;
всё, что читается позже (мои билеты, выгрузка, сверка хеша), читает строки, а не считает заново.
Это единственная конструкция, при которой опубликованный хеш обязан сойтись у постороннего:
пересчёт на чтении зависит от текущего состояния профилей, а они меняются каждый день.

## Шесть критериев Гейта-1 — решения

### 1. Побайтовый контракт хеша

Посторонний обязан пересчитать опубликованный SHA-256 по опубликованному списку. Поэтому
сериализация фиксируется до байта, а не «списком через запятую»:

| Свойство | Решение |
|---|---|
| Единица | одна строка на билет |
| Порядок | по `ticket_number` ВОЗРАСТАНИЮ (не по user_id, не по времени вставки) |
| Формат строки | `{ticket_number};{user_id};{source}` |
| Разделитель полей | `;` (U+003B) |
| Разделитель строк | `\n` (LF, U+000A) |
| Финальный перенос | **отсутствует** |
| Кодировка | UTF-8 |
| Числа | десятичные, без ведущих нулей, без разделителей разрядов, без знака |
| `source` | значение енума в нижнем регистре: `survey` \| `friend` |
| Хеш | `hashlib.sha256(payload.encode("utf-8")).hexdigest()` — hex в НИЖНЕМ регистре |

**Почему `user_id` внутри хеша:** номер обязан быть связан с участником. Если хешировать только
номера, после публикации их можно переставить между людьми и хеш не изменится — доказательство
перестанет что-либо доказывать.

**Почему именно внутренний `user_id`, а не телефон/имя:** внешняя сверка требует публикации
списка. `user_id` — идентификатор строки, а не личность: он позволяет пересчитать хеш и не
раскрывает персональные данные. (Публикация — PR-5.4; здесь фиксируется только контракт.)

**Функция:** `canonical_snapshot(tickets) -> str` — чистая, без БД, тестируется независимо.
`participant_hash = sha256(canonical_snapshot(...))`.

### 2. Повторный `commit_draw` — ОТКЛОНЯЕТСЯ (не идемпотентен)

Выбран один исход, без «или».

- **Поведение:** второй вызов на периоде со `status != open` → `ConflictException` (409),
  ничего не пишет.
- **Почему отклоняем, а не возвращаем существующий:** снимок — публичный артефакт с опубликованным
  хешем. «Молча вернуть прежний» скрывает операционную ошибку (администратор думает, что
  переснял список после правок — а он заморожен). 409 сообщает правду.
- **Кто создаёт строку розыгрыша:** сегодня — НИКТО (`grep "LotteryDraw("` по `src/` и `tests/`
  даёт только объявление модели; PR-5.1 был схема-only, эндпоинтов у него нет). Значит строку
  создаёт сам `commit_draw`, первым же оператором транзакции, сразу со `status=committed`.
- **Сериализаторов ДВА, для двух разных случаев** (поправка Ревьюера, проверена по коду):
  - **первый commit периода** — сериализует **`UNIQUE` на `lottery_draws.period`**
    (`models.py:375`), а НЕ `FOR UPDATE`: заблокировать несуществующую строку нельзя, два
    параллельных первых вызова оба прошли бы проверку `status`. Проигравший получает
    `IntegrityError` на уникальном индексе → перехватываем и отдаём **409 с доменным detail**
    («розыгрыш за период уже заморожен»).
    ⚠️ **Поправка само-проверки:** ранее и в моей спеке, и в вердикте Ревьюера стояло «иначе
    вернётся 500». Это неверно — `src/main.py:210-217` содержит ГЛОБАЛЬНЫЙ
    `@app.exception_handler(IntegrityError)`, отдающий 409 с текстом
    `"Data conflict: duplicate or constraint violation"`. Локальный перехват нужен ради понятного
    сообщения, а не ради кода ответа; и мутация обязана проверять **detail**, иначе она не может
    покраснеть (тест на один лишь статус останется зелёным и без перехвата).
  - **повторный commit** (строка уже есть) — `SELECT … WHERE period = :p FOR UPDATE` + проверка
    `status` под локом → 409. Прецедент — `submit_survey`.
- **Мутационно-тестируемо, по одному на случай:** убрать локальный перехват `IntegrityError` →
  detail становится generic (`"Data conflict…"`) → первый-commit тест краснеет **по телу ответа**;
  снять `.with_for_update()` → повторный-commit тест краснеет.
- **Пустой снимок — тоже 409.** Если подходящих участников ноль, `commit_draw` НЕ замораживает
  период: `canonical_snapshot([])` даёт `""`, а `sha256("")` = `e3b0c442…` — валидный хеш пустоты,
  и период оказался бы заморожен со `status=committed`, `total_tickets=0`, после чего повторный
  commit (когда участники появятся) отклонится по §2 и месяц будет потерян необратимо.
  Override не строим: администратору нужен не «заморозить пустоту», а понять, почему пусто.
- **Атомарность:** снимок + `total_tickets` + `participant_hash` + `status=committed` —
  одна транзакция. Частичного снимка не бывает.
- **Состояние `open` не материализуется** (нит Ревьюера). `commit_draw` создаёт строку сразу со
  `status=committed`, поэтому писателя у `open` сегодня нет вовсе, хотя докстринг модели
  (`models.py:340-343`) описывает переход `open → committed → drawn`. Это не дефект: `open`
  понадобится, когда появится «открыть розыгрыш заранее» (кандидат в PR-5.7). В том же PR, где
  пишется `commit_draw`, добавить в докстринг модели одну строку: «`open` пока не используется —
  единственный писатель статуса создаёт строку сразу `committed`», чтобы следующий читатель не
  искал несуществующего писателя.

### 3. Время — матрица, а не «tz-aware»

- Хранение: `timestamptz` (уже так в PR-5.1).
- Вычисления: `datetime.now(UTC)`; наивный `utcnow()` запрещён.
- Границы календарного месяца и всё, что показывается человеку, — через явную конверсию в
  `ZoneInfo("Asia/Tashkent")`. В репозитории пояс Ташкента ещё нигде не использовался — это первое
  место, поэтому константа заводится один раз в `loyalty/lottery.py` и переиспользуется дальше.
- **Окно «активация за последние 30 дней» отсчитывается от `as_of` = момента заморозки**
  (`commit_draw`), а не от границы календарного периода — унаследованный НИТ Ревьюера, фиксируется
  в коде и в тесте.
- **Тест-план обязателен под не-UTC поясом ПРОЦЕССА:** фикстура `prod_timezone`
  (`tests/conftest.py:89`, ставит `TZ=Europe/Berlin` + `tzset()`). Урок PR-6.5-B: сдвиг задаёт пояс
  процесса приложения, а не PostgreSQL, поэтому зелёный прогон на UTC-раннере ничего не говорит про
  прод. Матрица: `TZ=UTC` × `TZ=Europe/Berlin` × граница месяца (последняя секунда месяца по
  Ташкенту) — результат обязан совпадать.

### 4. «Галка есть, а возраст 15» — записанное решение

**Известный возраст решает; галка говорит только когда возраст не заполнен.**

| `age` | `is_adult` | итог |
|---|---|---|
| ≥ 18 | любое | участвует (грандфазер действующих) |
| < 18 | **true** | **НЕ участвует** |
| < 18 | false | не участвует |
| NULL | true | участвует |
| NULL | false | не участвует |

Формула: `adult = (age >= 18) if age is not None else is_adult`.

- **Почему строгое чтение:** возраст — данные, которые человек сообщил о себе; галка — заявление.
  Когда они противоречат, допускать несовершеннолетнего в розыгрыш нельзя. Позиция Ревьюера та же.
- ✅ **Уточняет формулу эпик-спеки** («adult = `is_adult` ИЛИ `age>=18`»), которая случай
  противоречия не разбирала. Ратифицировано Капитаном 27.07; эпик-спека §Assumptions поправлена.
- **Цена ошибки:** взрослый, опечатавшийся в возрасте, исключён из розыгрыша до исправления анкеты.
- **Факт-переключатель:** юрист скажет, что галка — юридически значимое заявление, а сохранённый
  возраст неавторитетен → правило переворачивается.

### 5. Заморозка — свойство снимка

После `commit_draw` ни один путь чтения не пересчитывает состав. Проверяется тестом: заморозить →
снять галку 18+, обнулить статус «Друг», добавить активацию → снимок, `total_tickets` и
`participant_hash` не изменились.

### 6. Авторизация админ-эндпоинта

`POST /api/v1/admin/lottery/commit` вешается на **`require_admin`** (`analytics/router.py:21`:
`type="admin"` + поход в БД + проверка `User.is_admin`), **не на `verify_admin_jwt`**, который
роль не проверяет вовсе. Заморозка розыгрыша — необратимая операция, она не может висеть на
зависимости слабее, чем чтение дашборда.

**Где она живёт — принят средний путь Ревьюера (лучше моего исходного компромисса):** объявляем
**каноническую `require_admin` в `src/auth/dependencies.py`** и подключаем к ней ТОЛЬКО новый
эндпоинт. Пять существующих копий (`analytics/router.py`, `crm/router.py`, `crm/admin_router.py`,
`broadcasts/admin_router.py`, `users/admin_router.py` — счёт проверен) не трогаем.

- Изменение **аддитивное**: ни один работающий роутер не меняется, скоуп PR не растёт.
- Loyalty не начинает зависеть от `analytics` — импорт зависимости из чужого роутер-модуля был бы
  худшим из вариантов.
- У бэклог-пункта «свести пять копий» появляется цель, к которой сводить. Ревьюер проверил: пять
  копий функционально идентичны, расходятся только докстрингом и `from exc` / `from None` — то
  есть косметический дрейф уже начался.

Тесты: не-админ (пользовательский токен) → отказ; админ → допущен; отсутствие токена → 401.
Дарк-гейт `require_loyalty_enabled` — как на остальных loyalty-маршрутах.

## Формула билетов — юнит-матрица (прозой не принимается)

`compute_ticket_count(profile, as_of) -> int`, чистая функция, без БД.

Условия участия (все обязательны): член клуба · **анкета заполнена = `gender` И `city` не null
(возраст НЕ обязателен)** · adult по таблице §4 · активация за 30 дней до `as_of`.
Билеты: базовый = 1; статус `biotact_friend` = +1; **потолок 2**.

⚠️ **Возраст убран из обязательных полей решением Капитана 27.07** — иначе профиль без возраста
отсеивался бы проверкой полноты РАНЬШЕ, чем дело доходило до предиката adult, и галка 18+ не
влияла бы ни на один исход (блокер Гейта-1, пойман Ревьюером). Теперь возраст решает, когда он
известен, а галка — когда нет. Поправка внесена и в эпик-спеку §Assumptions.

| # | анкета (пол+город) | возраст / галка | активация ≤30д | статус | ожидание |
|---|---|---|---|---|---|
| 1 | заполнена | age 25 | да | newbie | **1** |
| 2 | заполнена | age 25 | да | friend | **2** |
| 3 | заполнена | age 17 + галка | да | friend | **0** — возраст побеждает галку |
| 4 | заполнена | age NULL + галка | да | newbie | **1** — галка решает, возраста нет |
| 5 | заполнена | age NULL, без галки | да | friend | **0** |
| 6 | нет города | age 25 | да | friend | **0** |
| 7 | нет пола | age 25 | да | newbie | **0** |
| 8 | нет пола и города | age NULL + галка | да | newbie | **0** — галка анкету не заменяет |
| 9 | заполнена | age 25 | 31 день назад | friend | **0** |
| 10 | заполнена | age 25 | ровно 30 дней | newbie | **1** (граница включительно) |
| 11 | заполнена | age 25 | никогда | friend | **0** |
| 12 | заполнена | age 18 (граница) | да | newbie | **1** |
| 13 | нет профиля (не член) | — | — | — | **0** |

⚠️ **Матрицу диктует спецификация, а не прод.** Замер 27.07: 7 профилей, из них 6 уходят в
грандфазер-ветку по возрасту. Комбинации 3/4/5/8 на проде сегодня не встречаются — и именно поэтому
они обязаны быть в тестах: их отсутствие в данных не означает недостижимость в коде.

## Acceptance criteria

- [ ] `compute_ticket_count` даёт 0/1/2 по ВСЕЙ матрице выше (число случаев не фиксируем здесь —
      оно живёт только в самой матрице и меняется вместе с ней).

      `hash_published_at` — tz-aware.
- [ ] Повторный commit того же периода → 409, снимок не тронут.
- [ ] Два параллельных commit'а → ровно один снимок (гонка серилизуется, мутация краснит).
- [ ] Хеш воспроизводим независимым пересчётом по опубликованному списку; изменение любого билета
      меняет хеш.
- [ ] Заморозка держит: правки профилей после commit не меняют снимок и хеш.
- [ ] `POST /admin/lottery/commit`: не-админ → отказ, админ → работает, без токена → 401,
      при выключенном `loyalty_enabled` → 404.
- [ ] Результаты совпадают под `TZ=UTC` и `TZ=Europe/Berlin`.

## Test plan

1. **Юнит-матрица** — каждая строка отдельным `pytest.param` с говорящим id; чистая функция, без БД.
2. **Хеш-контракт:** (а) снимок → строка → SHA-256 совпадает с независимо посчитанным в тесте;
   (б) смена одного `ticket_number`/`user_id`/`source` меняет хеш; (в) порядок строк не зависит от
   порядка выборки из БД (перемешанный вход даёт тот же хеш).
3. **Гонка — ДВА разных теста, случаи не взаимозаменяемы:**
   (а) **первый commit периода**: два параллельных вызова, когда строки розыгрыша ещё НЕТ →
   ровно один снимок, проигравший получает 409 (не 500). Сериализует `UNIQUE(period)`;
   (б) **повторный commit**: строка есть, два параллельных вызова → 409 у второго, сериализует
   `FOR UPDATE`.
   Оба — через реальные сессии Postgres, барьер + сон (как
   `test_race_survey_barriered_committed_profile_dedup`). Тест только на (б) пропустил бы гонку
   первого commit'а целиком — именно там `FOR UPDATE` бессилен.
4. **Идемпотентность:** повторный commit → 409, `total_tickets` и хеш не изменились.
5. **Заморозка:** commit → мутировать профили → снимок и хеш прежние.
6. **HTTP:** дарк-гейт 404 · без токена 401 · пользовательский токен отказ · админ 200.
7. **Время:** вся матрица под `prod_timezone` (Europe/Berlin) и под `TZ=UTC`; отдельный кейс —
   активация ровно на границе 30 дней и последняя секунда месяца по Ташкенту.
8. **Мутации** (гард `git diff HEAD --quiet || стоп`): снятие `FOR UPDATE` · `>=` → `>` на границе
   30 дней · потолок 2 → 3 · сортировка снимка по `user_id` вместо `ticket_number` · `age`-ветка
   заменена на «галка побеждает».
