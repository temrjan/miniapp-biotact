# Спека PR-6.4 — фронт мини-аппа: степпер частичного списания баллов (Этап 6)

**Создан:** 2026-07-16 · **Кресло:** Инженер · **Стек:** React 19 / Vite / TS / Zustand / TanStack Query
**Бэкенд-контракт:** уже на проде (PR-6.3-v2, `c51ad55`) — `POST /orders` принимает `points_to_apply:int`.

## Цель
Дать покупателю-участнику Клуба на чекауте выбрать, сколько баллов списать: степпер режет «к оплате картой» вживую, остаток уходит в Multicard. Полное покрытие баллами → заказ оплачен сразу, без карты. Правила списания энфорсит сервер; фронт зеркалит их для UX.

## Скоуп PR — что входит
- Степпер выбора баллов на **шаге `confirm`** чекаута (гейт: только участник Клуба с баллами и подходящим subtotal).
- Живой пересчёт «Списано баллов» / «К оплате картой».
- `points_to_apply` в `CreateOrderRequest` (`buildOrderRequest`) — **всегда присутствует, default `0`** (не «0/absent»; бэкенд ест оба, но тип FE фиксируем однозначно — НИТ Ревьюера).
- Ветка `handlePayment`: полное покрытие (`payment_status:'paid'`) → `navigate(ROUTES.PAYMENT_SUCCESS + '?order_id=…')` (переиспользуем существующий `PaymentSuccessPage`, БЕЗ Multicard и БЕЗ нового UI); частичное/карта → `/payments/create` на остаток → `WebApp.openLink` (как сейчас).
- 🔴 **Синхронный ре-энтри-гвард в `handlePayment`** (БЛОКЕР Гейт-1): `useRef` `isProcessingRef` — **первая строка** хендлера `if (isProcessingRef.current) return; isProcessingRef.current = true;`, сброс в `false` в `catch`. Синхронный, не зависит от React-рендера и от JS→native моста Telegram `MainButton.disable()` (round-trip latency; быстрый двойной тап пальцем 50–150мс успевает войти дважды до реального disable). `isProcessing`-стейт остаётся для UI-спиннера. **Почему в скоупе, а не бэклог:** `handlePayment` прямо в правках PR-6.4, и цена ошибки меняется качественно — сегодня (карта) двойной тап = два висящих unpaid (самоограничивается через ручной Multicard ×2); после полного покрытия баллами = ДВА реальных paid-заказа + двойное списание баллов тихо, без доп. действия юзера. `UNIQUE(order_id,reason)` не спасает — два РАЗНЫХ order_id.
- TS-утиль `maxRedeemable`/`clampRedeem` — **точное** зеркало правил бэкенда (см. Развилку 1), юнит-тесты.
- Обработка ошибок сервера: 422 (`invalid_redeem_amount` + `max_redeemable`) → клэмп+тост; 409 (`insufficient_points`) → «не хватает баллов».
- i18n ru+uz для новых строк.

## 🔀 Решения к ратификации (Гейт-1)

**Развилка 1 — где живёт формула `max_redeemable`. РЕКОМЕНДУЮ: зеркало в TS.**
- Степперу нужен валидный диапазон ДО отправки; готового `GET`-эндпоинта нет.
- Рекомендация: `src/utils/redeem.ts` — **точная** копия бэкенда, не упрощение (МИНОР Ревьюера). Обязательно:
  - **Обе ветки-кандидата, берётся `max()`** (как в `orders/service.py:max_redeemable`): (а) **full-cover** = `subtotal`, но ТОЛЬКО если `subtotal` сам кратен шагу 100 И остаток картой (`total − subtotal`) равен 0 либо ≥ 5000 И `balance ≥ subtotal`; (б) **partial** = `floor100(min(balance, subtotal, total − 5000))`, если ≥ 500. Нельзя схлопнуть в одну ветку.
  - **`subtotal` и `total` — ДВА раздельных параметра с первого дня**, НЕ один «раз доставка=0 они равны». Иначе тот же дремлющий landmine на платную доставку, что уже закрыт комментарием в `payments/service.py`. Комментарий в `redeem.ts` ссылается на ОБА места: формулу `orders/service.py` И landmine-коммент `payments/service.py`.
  - `clampRedeem(desired, {balance, subtotal, total})` — снап на шаг 100, min 500, перепрыг мёртвой зоны (1–4999), ≤ `maxRedeemable`.
  - Сервер остаётся авторитетным (422 с `max_redeemable` — бэкстоп).
- Контраргумент: дублирование денежной логики FE/BE = дрейф. Не перевесил: формула маленькая и замороженная; альтернатива (эндпоинт) = отдельный PR + раунд-трип на каждый тик. **Цена ошибки:** рассинхрон → сервер отобьёт 422, покупатель увидит клэмп (UX-шум, не деньги). **Факт-переключатель:** правила станут динамическими → в эндпоинт.

**Развилка 2 — где степпер. РЕКОМЕНДУЮ: шаг `confirm`.**
- `confirm` — финальный шаг, где уже показан total и кнопка оплаты; «срезать до оплаты». Альтернатива (CartPage) — до phone/delivery, сумма может измениться правками корзины. Рекомендую `confirm`.

**Развилка 3 — контрол степпера. ✅ РАТИФИЦИРОВАНО Капитаном 2026-07-16: слайдер + «Максимум».**
- Слайдер (Bellissimo-стиль: тянешь — «К оплате картой» режется вживую) + кнопка «Максимум». Снап на шаг 100, перепрыг мёртвой зоны (1–4999) — в логике `clampRedeem`, наружу невалидные значения не выходят. Отклонённые варианты (не строим): `+/−` кнопки · чипы-пресеты.

## Критерии приёмки — «PR готов, когда…»
- Участник с баллами на `confirm` видит степпер; не-член / без баллов / subtotal < порога → степпера нет, путь карты не изменён.
- Двигая степпер, «К оплате картой» и «Списано баллов» пересчитываются; невалидные значения недостижимы (снап), мёртвая зона перепрыгивается.
- Полное покрытие → «Оплатить баллами» → заказ `paid` → success без Multicard.
- Частичное → «Оплатить {остаток}» → `/payments/create` на остаток → Multicard.
- 422/409 с сервера обработаны (клэмп/тост), не белый экран.
- **Двойной тап оплаты создаёт РОВНО ОДИН заказ** независимо от виджета (нативная `MainButton` / web-кнопка) — за счёт синхронного `isProcessingRef`, не только `disabled`. После ошибки ref сброшен → повтор возможен.
