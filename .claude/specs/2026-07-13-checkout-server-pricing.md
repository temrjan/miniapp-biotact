# PR-6.0 — Серверный расчёт цены заказа (предусловие Этапа 6)

**Дата:** 2026-07-13 · **Статус:** ЧЕРНОВИК плана, на Гейт-1 не подан.
**Природа:** закрытие живой дыры на проде (деньги + ПДн) + фундамент под трату баллов.

## 1. Проблема (код-проверено 2026-07-13)

Чекаут целиком доверяет клиенту:

- `POST /orders` принимает `product_price`, `subtotal`, `total` от клиента и пишет их в БД как есть
  (`orders/service.py:62-94`, схема `OrderCreate` — `orders/schemas.py:36-51`). Каталог не читается.
- `POST /payments/create` выставляет счёт Multicard на `order.total` из БД (`payments/router.py:57`).
- `POST /orders` **не требует авторизации** (`get_optional_user`; без initData заказ пишется на
  `user_id=1`, `orders/router.py:51`).
- `GET /orders/{id}` — **IDOR**: проверка владельца стоит под `if user and ...` (`orders/router.py:80`),
  без initData она пропускается → любой читает любой заказ (адрес, телефон, имя, состав).
- `GET /orders` без авторизации отдаёт заказы `user_id=1`.
- Фискальный чек (OFD) строится из клиентских цен (`payments/service.py:186-204`) → в налоговый чек
  уходит то, что прислал клиент.

**Эксплуатация:** `POST /orders` с `product_price: 1` → счёт Multicard на 1 сум → оплата проходит →
заказ `paid`+`confirmed`, админ видит его как обычный.

**Проверено на проде:** 68 заказов, 20 оплачено, min total 61 000 сум — следов эксплуатации НЕТ.
Дыра открыта, но не найдена. 20 заказов на `user_id=1` — исторический фолбэк, суммы нормальные.

**Связь с Этапом 6:** план v4 (§Трата) требует «сервер сам считает скидку и total — клиентскому
`total` не доверяем». Списание баллов поверх чекаута, который верит клиенту, бессмысленно.

## 2. Факты из документации Multicard (изучено 2026-07-13)

- **Invoice:** `amount` — целое в тийинах; минимальная сумма и нулевые суммы не документированы →
  нулевой счёт не выставляем (важно для будущего «100% баллами»). Есть `ttl` (по умолчанию 1 сутки).
- **Success-колбэк:** `sign = MD5(store_id + invoice_id + amount + secret)` — совпадает с нашим кодом.
  Партнёр обязан ответить 200 + `success: true`; **любой другой ответ = отмена платежа с возвратом**.
  Колбэк **может прийти повторно** — партнёр обязан ловить дубль по `uuid` и отвечать успехом,
  не переобрабатывая. *(Сегодня мы переобрабатываем; для баллов это = двойное списание.)*
- **Вебхуки (мы их НЕ реализовали):** статусы `draft/progress/success/error/revert/hold`,
  `sign = SHA1(uuid + invoice_id + amount + secret)`, retry ×5, IP `195.158.26.90`.
  → Сегодня мы **не узнаём о неуспешной оплате и о возврате**. Для траты баллов это критично:
  списанные баллы некому вернуть.
- **Возвраты:** есть DELETE-эндпоинты полного и частичного возврата.

## 3. Решение — PR-6.0 (только этот PR; следующие — отдельно)

### Бэкенд

1. **Схема входа (обратно совместимая):** `OrderItemCreate` = `product_id: int` (обязателен) +
   `quantity: int = Field(ge=1, le=99)`. `OrderCreate` = адрес/телефон/имя/заметка + `items`.
   Поля `product_name`/`product_price`/`total`/`subtotal`/`delivery_fee` из входа **убираются**;
   Pydantic по умолчанию игнорирует лишние поля → **старый фронт продолжает работать** в окне деплоя.
2. **Сервер считает всё сам** (`orders/service.create_order`):
   - один `SELECT ... WHERE id IN (...)` по каталогу;
   - неизвестный `product_id` → 422; `is_in_stock = false` → 422; пустой `items` → 422;
   - снимок в `order_items`: `product_name = product.name`, `product_price = product.price`,
     `total = price × quantity`;
   - `subtotal = Σ item.total`; `delivery_fee = 0` (сегодня доставка бесплатна — сервер это и
     фиксирует; правил доставки в проекте нет); `total = subtotal + delivery_fee`.
3. **Авторизация — переиспользуем существующее, не изобретаем** [check-F1]: `POST /orders`,
   `GET /orders`, `GET /orders/{id}` переводим на **`Depends(get_current_user)`** из
   `src.auth.dependencies` (`dependencies.py:20` — валидирует initData, кидает 401, создаёт юзера).
   Локальный `get_optional_user` (`orders/router.py:28`) после этого **удаляем** — вызовов не остаётся;
   именно он и породил дыру. Владелец на `GET /orders/{id}` проверяется **без** `if user` → чужой = 403.
4. **Платежи — тот же класс дефекта, закрываем в этом же PR** [check-F2]: `POST /payments/create`
   (`payments/router.py:29`) сегодня **без авторизации вообще** — любой выставляет инвойс на чужой заказ
   и триггерит телеграм-уведомление админам (`payments/router.py:93`, спам-вектор). Ставим
   `Depends(get_current_user)` + проверку `order.user_id == user.id` → иначе 403.
   `GET /payments/status/{uuid}` оставляем открытым **осознанно** (uuid неугадываем) — записано как решение.
5. **Платёж:** guard `order.total <= 0` → 400 (нулевой счёт Multicard не документирован).
6. **`quantity: ge=1, le=99`** [check-F6] — страховка от абсурдного инвойса (без неё `quantity: 1000000`
   даёт счёт на миллиарды). Это **НЕ контроль остатков**: `stock_quantity` не проверяем, оверселл
   возможен и сегодня (вне скоупа). Проверяем только булев `is_in_stock` (на проде 0 из 57 товаров
   не в наличии → сегодня это никого не заблокирует).

### Фронт (мини-апп)

**НЕ в этом PR.** Новый фронт, отправляющий только `product_id`+`quantity`, сломается на старом API
в окне деплоя (старая схема требует `product_price`). Порядок: сначала бэк (толерантный),
потом отдельным PR чистка фронта. Сегодняшний фронт с новым бэком работает без изменений.

## 3a. Осознанно принятые последствия

- **Цена может измениться между корзиной и оплатой** [check-F4]. После фикса сервер берёт цену из
  каталога — если админ поменял её, пока товар лежал в корзине, на странице Multicard человек увидит
  новую сумму, а не ту, что была в корзине. Принимаем: платить по устаревшей клиентской цене — это
  ровно та дыра, которую мы закрываем. Механику «клиент шлёт ожидаемую сумму → 409 при расхождении»
  в v1 **не строим** (rules #5 — не под гипотетику); фронт уже получает пересчитанный `order` в ответе.

## 4. Тест-план (red→green + мутации)

**Тестов на заказы и платежи в проекте НЕТ вообще** [check-F7] — `tests/test_orders_pricing.py` станет
**первым тестом денежного пути** (как `test_crm_customers_loyalty.py` стал первым для CRM). Сиды товаров
+ initData-фикстура по паттерну `conftest.py`.

- Подделка цены: `product_price: 1` при каталожной 69 000 → в БД и в ответе **69 000** (мутация:
  убрать пересчёт → красный).
- Подделка `total`/`subtotal` в теле → игнорируются, считается сервером.
- Несуществующий `product_id` → 422. `is_in_stock=false` → 422. `items: []` → 422.
- **Границы `quantity`:** невалидные `0` и `100` → 422 **И валидные `1` и `99` → 201**
  [Гейт-1 МИНОР-3: без верхнего валидного кейса граница может «съехать» вниз незамеченной].
- Без initData: `POST /orders` → 401; `GET /orders` → 401; `GET /orders/{id}` → 401 (IDOR закрыт;
  мутация: вернуть `if user` → красный). Чужой заказ с валидным initData → 403.
- **`POST /payments/create` — та же IDOR-дыра, отдельным кейсом** [Гейт-1 МИНОР-1]: чужой `order_id`
  с валидным initData → **403** (мутация: убрать `order.user_id == user.id` → красный);
  без initData → 401. §3.4 сам называет это «тем же классом дефекта» — значит и тест обязан быть явным,
  а не подразумеваемым.
- Математика: 2 позиции × разные qty → subtotal/total сходятся; OFD-чек строится из БД-цен.
- Платёж при `total = 0` → 400 (сид: товар с ценой 0 → заказ на 0).

## 6. Риск, откат и прод-проверка

Главный риск — **сломать живой чекаут** (единственный источник выручки мини-аппа). Снимается:
(1) толерантная схема — старый фронт продолжает работать в окне деплоя (Pydantic 2.12.5 игнорирует
лишние поля, проверено экспериментом); (2) тесты выше; (3) `client.ts:48` шлёт initData на ВСЕ запросы,
а `PaymentSuccessPage` API не дёргает → требование авторизации ничего не ломает (проверено чтением).

**Прод-проверка — бесплатная и не создающая мусора** [check-F3]. НЕ прогоняем пробу подделки цены на
проде (она создаст фальшивый заказ) и НЕ платим реальных денег как гейт. Проверяем:
`POST /orders` без initData → **401** (до фикса вернул бы 201 и создал заказ) · `GET /orders` без
initData → **401** · `GET /orders/{id}` без initData → **401** (IDOR закрыт) ·
**`POST /payments/create` без initData → 401** [Гейт-1 МИНОР-2: зависимость авторизации срабатывает
раньше поиска заказа, поэтому подойдёт любой `order_id` — мусора не создаст] · health 200.
Живой заказ на реальные деньги — по желанию Капитана, глазами, не как гейт.
