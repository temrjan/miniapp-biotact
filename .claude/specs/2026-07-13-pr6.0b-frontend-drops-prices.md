# PR-6.0b — Фронт перестаёт слать цены (чистка после PR-6.0)

**Дата:** 2026-07-13 · **Природа:** фронт-only, удаление мёртвого контракта. 0 миграций, 0 бэкенда.

## 1. Цель

После PR-6.0 (#79) сервер сам считает деньги по каталогу и **игнорирует** ценовые поля из запроса.
Мини-апп до сих пор их шлёт: `product_price`, `total` на позицию и `subtotal`/`delivery_fee`/`total`
на заказ. Это мёртвый контракт — он врёт читателю кода («клиент участвует в ценообразовании»)
и оставляет соблазн однажды снова начать ему верить. Убираем.

**Порядок соблюдён:** бэк уже на проде (`82b50d5`), он толерантен к обеим формам. Обратный порядок
(фронт первым) сломал бы чекаут: старый API требовал `product_price`.

## 2. Факты (код-проверено 2026-07-13)

- Все типы заказа объявлены **локально** в `packages/frontend/src/pages/CheckoutPage.tsx`
  (`OrderItem` :20, `CreateOrderRequest` :28) — общих типов заказа в проекте нет, grep подтверждает
  единственного строителя запроса (`CheckoutPage.tsx`).
- Тела запроса собираются в `handlePayment` (:157–174).
- Тестов у `CheckoutPage` нет (есть `ActivationPage.test.tsx` — паттерн для нового теста).
- `totalAmount` из стора корзины используется **и** для показа суммы в UI — остаётся, убираем только
  его отправку на сервер.

## 3. Решение

1. `OrderItem` → только `{ product_id: number; quantity: number }` (переименовать в `OrderLine` —
   «item» с ценой ушёл, имя должно отражать смысл).
2. `CreateOrderRequest` → `{ items: OrderLine[]; delivery_address; delivery_phone; delivery_name;
   customer_note }`. Ценовых полей нет.
3. Вынести **чистую функцию** `buildOrderRequest(items, { deliveryAddress, phone, name })` из
   `handlePayment` — единственная причина: без неё контракт «в запросе нет денег» нечем закрыть
   тестом (страница тянет Telegram WebApp, роутер и сторы). Функция экспортируется из того же файла.
4. `handlePayment` зовёт `buildOrderRequest` и дальше как было (POST /orders → POST /payments/create).

## 4. Тест-план (правило №0)

Новый `CheckoutPage.test.tsx` (vitest, паттерн `ActivationPage.test.tsx`) на `buildOrderRequest`:
- [ ] позиции корзины → `[{product_id, quantity}]`, `product_id` — число (в сторе строка);
- [ ] **в payload НЕТ ни одного денежного поля** — проверка по ключам объекта
      (`expect(Object.keys(req)).not.toContain('total')` и т.д. для `subtotal`/`delivery_fee`,
      плюс по ключам позиции: нет `product_price`/`total`) — это и есть закрепляемый контракт;
- [ ] адрес: `delivery` → строка, `pickup` → `null`;
- [ ] **red→green:** вернуть ценовые поля в билдер → тест red.

**Гейты (точь-в-точь CI):** `npx tsc --noEmit` · `npm run lint` · `npm run test` · `npm run build`.

## 5. Не в скоупе

Бэкенд (не трогаю), админка, `OrderResponse` (сервер по-прежнему отдаёт `total` — фронт его
показывает), рефактор корзины, PR-6.1 (жизненный цикл платежа).

## 6. Риск и откат

Чекаут — единственный источник выручки мини-аппа, поэтому риск ненулевой, хотя диф — удаление.
Снимается: (1) бэк принимает и старую, и новую форму → даже при ошибке в лишних полях заказ пройдёт;
обязательны только `product_id` + `quantity`, а их фронт слал и раньше; (2) тест на билдер;
(3) после деплоя — живой клик Капитана: корзина → страница Multicard с верной суммой.
Откат = revert одного PR.
