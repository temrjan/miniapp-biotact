# PR-5.4a — Выгрузка снимка для внешней сверки (Этап 5)

> Дата: 2026-07-28 · Топик: `stage5-lottery` · Кресло: КОМАНДА (Claude=Инженер + отдельный Ревьюер)
> Родительская спека: `.claude/specs/2026-07-24-stage5-lottery.md` (эпик Этапа 5).
> Предыдущий PR: PR-5.3 `#101 1d81b53` — подсчёт билетов + заморозка, на проде.

## Goal

После заморозки розыгрыша (PR-5.3) на проде лежит опубликованный SHA-256 снимка участников — и **нет
способа его проверить**: списка, над которым взят хеш, наружу не отдаёт ничто. Commit-reveal без
reveal доверия не создаёт. Этот PR отдаёт администратору файл, который является *ровно теми
байтами*, над которыми взят опубликованный хеш, — так что внешняя проверка сводится к одной команде
`sha256sum`, без переизобретения нашего формата на чужой стороне.

## Approach — chosen + why

**Отдаём канонический список дословно, `text/plain`, ничего не добавляя.**

Альтернатива — JSON-конверт (`{period, hash, tickets: [...]}`) — отклонена: тогда проверяющий обязан
сам собрать каноническую строку из массива (`{number};{user_id};{source}`, `\n`, без завершающего
перевода строки) и любая его ошибка в реконструкции выглядит как **наша** нечестность. Хеш должен
браться от того, что скачали, а не от того, что удалось восстановить.

⛔ **Главный инвариант PR:** тело ответа — **байт-в-байт** аргумент `sha256`, использованный при
заморозке. Ни заголовочной строки, ни самого хеша, ни метаданных, ни BOM, ни завершающего `\n`.
Любая «полезная» добавка в тело ломает саму проверку, ради которой всё делается.

Где проверяющий берёт опубликованный хеш — вне этого PR: хеш публикует администратор (пост в канале /
экран PR-5.7), тело файла его не несёт **намеренно**.

⚠️ **`PlainTextResponse` — новый для проекта паттерн ответа.** `grep` по `packages/api/src/` даёт
**ноль** вхождений `PlainTextResponse` / `StreamingResponse` / `FileResponse` / `Content-Disposition`:
до сих пор каждый эндпоинт возвращал Pydantic-модель. Отступление сознательное и проверенное —
маршрут с `response_class=PlainTextResponse`, аннотацией возврата и кастомными заголовками проходит
`mypy --strict` (проба, `Success: no issues found`). Альтернатива-«как везде» (JSON) отклонена выше
по существу, а не по вкусу.

## Решения Гейта-1

### 1. Источник данных — замороженные строки, не пересчёт

Читаем `lottery_tickets` по `draw_id` и сериализуем **той же** `lottery.canonical_snapshot`. Eligibility
не пересчитывается: профили меняются после заморозки, а опубликованный хеш — нет. Это уже записанное
решение (докстринг `lottery.py:1-9`), здесь только исполняется.

**Сортировку в SQL не добавляем.** `canonical_snapshot` сортирует по `ticket_number` внутри себя
(`lottery.py:136-139`) — `ORDER BY` в запросе был бы декорацией: его снятие не покраснило бы ни один
тест. Ровно тот класс мёртвых конструкций, что мутационный прогон вскрыл в PR-5.3 трижды.

### 2. Гард целостности — пересчитанный хеш обязан сойтись с опубликованным

Перед отдачей сравниваем `snapshot_hash(rows)` с `draw.participant_hash`. Не сошлось → **409** с явным
сообщением, тело не отдаётся.

Единственный путь в это состояние — строки снимка изменили после заморозки. Отдать такой файл =
опубликовать список, который не сходится с нашим же хешем; наружу это неотличимо от подлога. Гард
превращает публичный провал репутации во внутреннюю тревогу.

**Пустой снимок отдельным гардом НЕ обкладываем.** Розыгрыш с нулём билетов недостижим:
`commit_draw` отбивает пустой снимок 409 (`lottery.py:241-243`), поэтому строки без билетов не
существует. Побочный эффект принят осознанно: попади мы в это состояние, ответом было бы 409
«целостность нарушена» — диагноз неверный, но гард под недостижимое состояние запрещён правилом #6.

⚠️ **Это НЕ защита от невозможного состояния** (правило #6) и должно быть доказано как таковая:
обязателен тест, который **краснеет при снятии гарда** — прямой `UPDATE lottery_tickets` → export → 409.
Если такой тест написать не удастся, гард снимается: непроверяемая защита в этом модуле уже
отбраковывалась (`FOR UPDATE`, потолок билетов).

### 3. Авторизация — `require_admin`, как у `commit`

`dependencies=[Depends(require_loyalty_enabled), Depends(require_admin)]` — тот же порядок, что у
`POST /commit` (`admin_router.py:17-21`).

Эндпоинт read-only, и формально хватило бы лёгкого `verify_admin_jwt`. Берём канонический `require_admin`
(ходит в БД, видит отозванный аккаунт) сознательно: два разных гейта в одном роутере из четырёх строк —
это готовый дрейф, а «пять копий `require_admin`» уже висит в бэклоге именно как последствие такого
расползания.

### 4. Несуществующий розыгрыш → 404

`draw_id` приходит снаружи, это граница — валидируем. **404 поднимает `export_draw` (сервис), не
роутер** — единообразно с `commit_draw`, где все отказы живут в сервисе (`lottery.py:205,218,243`).
Требует добавить `NotFoundException` в импорт `lottery.py:20` (сейчас там только
`BadRequestException, ConflictException`).

Состояния `open` в проверках **не** трогаем:
строка создаётся сразу `committed` (`lottery.py:245-253`), `open` не материализуется никогда — гард под
него был бы защитой от недостижимого. Когда PR-5.7 введёт настоящий `open`, вопрос вернётся вместе с
падающим тестом.

### 5. Приватность файла — что в нём есть и почему

В строке: `ticket_number;user_id;source`. `user_id` — **внутренний id таблицы `users`**, не `telegram_id`,
не телефон, не имя. Опознать по нему человека снаружи нельзя.

`user_id` внутри строки — не наша вольность, а уже выкаченный контракт хеша: без него номера можно
переставить между людьми после публикации, не тронув хеш, и доказательство перестаёт что-либо
доказывать (`lottery.py:131-135`). Не переоткрываем.

### 6. Операционная заметка (не код)

Файл отдаётся вложением (`Content-Disposition: attachment`). Публиковать его нужно **файлом**, не
копипастом: редактор/мессенджер дописывает завершающий `\n`, и `sha256sum` перестанет сходиться —
внешне это выглядит как расхождение, хотя список верен. Записать в инструкцию администратора (PR-5.7).

## Scope PR

**IN**
- `lottery.export_draw(db, *, draw_id) -> ExportOutcome` — читает билеты, сериализует канонически,
  сверяет хеш; dataclass **`ExportOutcome(period, body)`** — ровно два поля, оба потребляются
  роутером (`body` = тело ответа, `period` = имя файла).
  ⚠️ `participant_hash` и `total_tickets` в результат **не кладём**: в ответ они не попадают,
  заголовков с ними нет — это были бы мёртвые поля ровно того класса, что мутационный прогон
  вскрыл в PR-5.3 трижды. Критерий «строк в теле == `total_tickets`» остаётся **тестовым**
  assert'ом, читающим колонку из БД напрямую; поля в dataclass он не требует.
- **Чтение строк — три колонки, не сущности:**
  `select(LotteryTicket.ticket_number, LotteryTicket.user_id, LotteryTicket.source)` и **явная**
  сборка кортежей `[(r.ticket_number, r.user_id, r.source) for r in result]`.
  ⚠️ Передавать результат `.all()` в `canonical_snapshot` напрямую **нельзя** — проверено пробой:
  `error: Argument 1 to "canonical_snapshot" has incompatible type
  "Sequence[Row[tuple[int, int, str]]]"; expected "list[tuple[int, int, str]]"` (`mypy --strict`).
  Загружать ORM-сущности вместо колонок — второй проходящий типы путь, но он тащит по объекту на
  билет ради трёх полей.
- Строка `*.egg-info/` в корневом `.gitignore` — **сознательно внутри этого PR**, а не отдельным
  chore-коммитом: `.gitignore` не подпадает под `paths-ignore` (`ci.yml:4-11`), поэтому отдельный
  коммит стоил бы полного редеплоя прода ради одной строки. Здесь деплой происходит всё равно.
- `GET /api/v1/admin/lottery/{draw_id}/export` → `PlainTextResponse`,
  `text/plain; charset=utf-8`, `Content-Disposition: attachment; filename="draw-<period>.txt"`.
- Тесты: `tests/test_lottery_export.py`.

**OUT (явно)**
- `record_winners` и `POST /admin/lottery/{id}/winners` → **PR-5.4b**, гейтится Open Q5
  (множественный выигрыш, ждёт «да» руководителя).
- Фронт мини-аппа, экран админки, публикация списка/хеша куда-либо.
- Любые персональные данные в выгрузке (телефон, имя, telegram_id).
- Публичный (неадминский) доступ к выгрузке.

**Отклонение от эпик-спеки:** там PR-5.4 назван цельным и в затронутых файлах числился `schemas.py`.
Разрез на 5.4a/5.4b ратифицирован Капитаном 2026-07-28 (Q5 блокирует только запись победителей).

## Acceptance criteria — «PR готов, когда…»

- [ ] `sha256` **тела HTTP-ответа** совпадает с `participant_hash` замороженного розыгрыша.
- [ ] В теле ровно `total_tickets` строк, порядок по возрастанию `ticket_number`, разделитель `;`,
      завершающего перевода строки нет, BOM нет, кодировка UTF-8.
- [ ] Испорченная после заморозки строка снимка → **409**, тело не отдаётся.
- [ ] Несуществующий `draw_id` → **404**.
- [ ] Без токена → 401; юзерский токен → 403; админ-типизированный токен не-админа → 403;
      настоящий админ → 200.
- [ ] `loyalty_enabled=false` → 404 (эндпоинта как будто нет).
- [ ] Каждая мутация из тест-плана даёт RED; факт отката проверен `git diff HEAD --quiet` после каждой.

## Test plan

**Хеш-контракт (ядро PR)**
1. Заморозить розыгрыш → `GET .../export` → `sha256(resp.content).hexdigest() == participant_hash`.
   Считать **от байтов ответа**, не от внутреннего объекта — иначе тест проверяет сам себя.
2. Байт-форма: число строк == колонки `lottery_draws.total_tickets` (читать из БД — в
   `ExportOutcome` этого поля намеренно нет); номера строго 1..N по возрастанию; в строке 3 поля
   через `;`; `resp.content` не оканчивается на `\n`; не начинается с BOM.

**Целостность**
3. Прямой `UPDATE lottery_tickets SET user_id=…` по одной строке → export → 409.
4. Прямой `UPDATE lottery_tickets SET ticket_number=…` → export → 409.
   (`is_winner`/`prize_rank` в хеш не входят — их изменение хеш менять **не** должно; это станет
   важно в PR-5.4b, проверяем уже здесь.)

**Границы и доступ**
5. `draw_id`, которого нет → 404.
6. Без `Authorization` → 401 · юзерский токен → 403 · админ-типизированный токен не-админа → 403 ·
   реальный админ → 200 (позитив-контроль). Зеркалим `test_lottery_commit.py:315-370`.
7. `monkeypatch` `loyalty_enabled=false` → 404.

**Мутационная верификация (обязательна, RED у каждой)**
- **M1** снять гард целостности → падает (3).
- **M2** дописать `\n` в конец тела → падает (1) и (2).
- **M3** заменить `require_admin` на `verify_admin_jwt` → падает (6, случай «админ-типизированный
  токен не-админа»).
- **M4** отдать `application/json`/обернуть тело в JSON → падает (1).
- **M5** 404 → пустой 200 при отсутствующем `draw_id` → падает (5).
- **M6** сортировать по `id` вместо номера в `canonical_snapshot` → падает (2).

Прогон под `TZ=UTC` (правило Этапа 5). Перед мутационным циклом — всё в коммит и гард
