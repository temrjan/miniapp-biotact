## Цель
Член клуба может опционально прислать пол/возраст/город на карте лояльности — без давления и без
блокировки чего-либо. Первое непустое сохранение анкеты пишет событие `survey_done` ровно один раз.

## Контекст (проверено чтением кода)
- `customer_profile` уже содержит `gender`/`age`/`city` (+ `purchase_goal`/`purchase_for_whom`, вне
  скоупа) со времён Stage-1 миграции `c7cb4807f4ba` — **новая миграция НЕ нужна**.
- `CustomerEventType.SURVEY_DONE` уже в словаре (models.py) — константа готова, только использовать.
- Паттерн race-safe idempotent-guard уже есть в `record_consent` (service.py): лочим
  `customer_profile FOR UPDATE`, затем guard-check-then-insert событие. Переиспользую тот же приём.
- `LoyaltySection` → `data.isMember ? <LoyaltyCard/> : <JoinCard/>` (PR-4.4a). Анкета — карта членам,
  не-членам её показывать не нужно (нечего анкетировать до вступления).
- `useLoyalty` / `loyaltyApi` / `types/index.ts` — паттерны DTO↔camelCase, `retry:false`, established.

## Скоуп PR — что входит

### Backend (API)
- `src/loyalty/schemas.py`:
  - `SurveyRequest` — `gender: Gender | None`, `age: int | None` (`ge=1, le=120`),
    `city: str | None` (`StringConstraints(strip_whitespace=True, min_length=1, max_length=100)`).
    `model_validator(mode="after")`: как минимум одно поле не-`None`, иначе `ValueError`
    (→ 422) — «анкета» из пустого тела бессмысленна (спека: «непустая анкета»).
  - `SurveyResponse` — `updated_fields: list[str]` (какие поля записала ИМЕННО эта попытка),
    `survey_done: bool` (True только если ИМЕННО этот вызов впервые выставил событие).
- `src/loyalty/service.py` — `submit_survey(db, *, telegram_user, payload) -> SurveyOutcome`:
  - Резолвит юзера через `get_user_by_telegram_id` (**без** `get_or_create_user` — анкета НЕ точка
    входа в клуб; лениво создавать профиль здесь означало бы «вступление» в обход чекбокса согласия).
  - Юзер не найден ИЛИ `customer_profile` не найден (не член) → `NotFoundException` (404) —
    тот же класс, что уже используется в модуле.
  - Иначе: `async with db.begin()`, `SELECT customer_profile ... FOR UPDATE` (лочит + резолвит id),
    `UPDATE` только присланных полей (не `COALESCE` — присланное поле явно перезаписывает старое,
    анкета «прогрессивная» = можно дозаполнять/поправлять по одному полю), затем guard-check
    `CustomerEvent(event_type=SURVEY_DONE)` под тем же локом → если не найдено, `INSERT`
    `payload={"fields": [...]}`.
- `src/loyalty/router.py` — `POST /loyalty/survey` на `summary_router`, тот же
  `dependencies=[Depends(require_loyalty_enabled)]` + `get_init_data_user`, как `/consent`/`/me`.

## Критерии приёмки — «PR готов, когда…»
- `POST /loyalty/survey`: пишет только присланные поля; `survey_done` — истина только на первом
  непустом сохранении, повтор (тем же или другим набором полей) НЕ дублирует событие.

- Frontend: карта члена показывает анкету; кнопка «Сохранить» disabled с пустыми полями;
  успешная отправка → подтверждение; не-член анкеты не видит.
- Гейты: api (`ruff`/`ruff format`/`mypy --strict`/`pytest`/parity no-op) + front
  (`tsc`/`eslint`/`vitest`/`build`) зелёные локально; i18n ru/uz паритет.

## Ключевые решения Гейта-1 (на утверждение Капитана)

1. **Анкета требует существующего членства, без ленивого создания профиля.**
   Рекомендация: `submit_survey` резолвит юзера/профиль read-only (`get_user_by_telegram_id` +
   `SELECT ... FOR UPDATE`), отсутствие профиля → 404. Почему: анкета — не точка входа в клуб
   (в отличие от consent/activate); лениво создать профиль здесь означало бы тихое «вступление»
   в обход обязательного чекбокса согласия — юридическая дыра (тот же принцип, что закрывал
   consent-эндпоинт в PR-4.2). Цена альтернативы (lazy-create): пользователь становится «участником»
   без согласия — недопустимо.

2. **Присланные поля перезаписывают, не `COALESCE`.**
   Рекомендация: значение в теле запроса всегда побеждает старое (не «пишем только если было
   `NULL`»). Почему: анкета «прогрессивная» = пользователь может передумать/поправить город без
   обходного пути; `COALESCE` заблокировал бы редактирование навсегда. Цена альтернативы: юзер не
   может исправить опечатку в городе — хуже UX без выигрыша в безопасности (это не денежное поле).

3. **`survey_done` — тот же race-safe guard-под-локом, что и `phone_shared`/`consent_recorded`
   в `record_consent`.** Переиспользую проверенный примитив вместо изобретения нового — консистентность
   кодовой базы, ноль нового риска гонки.

4. **Frontend без pre-fill и без «done»-состояния** (не добавляю `surveyDone`/значения полей в
   `GET /loyalty/me`). Рекомендация: `SurveyCard` — всегда пустая форма, всегда видна и активна
   членам; сохранение просто перезаписывает (п.2), бэк идемпотентен для события. Почему: спека
   требует «пишет поля + событие», не UX-полировку; pre-fill добавил бы 3 новых поля в самый частый
   read-эндпоинт (`/me`) и логику восстановления состояния формы — стоимость выше пользы на этом
   шаге (риск: низкий PR должен таким и остаться). Цена ошибки: если Капитан хочет pre-fill/скрытие
   после заполнения — тривиально добавить отдельной маленькой дельтой (плюс 3 поля в `/me`), без
   переписывания survey-эндпоинта. Факт-переключатель: если окажется, что членов раздражает
   постоянно пустая форма (или они массово шлют анкету повторно по ошибке) — добавляем pre-fill
   следующим PR.

5. **Скиллы ДО кода:** `/python`+`/codex` (backend) и `/typescript`+`/codex` (frontend) — оба в
   контексте PR (полустек-PR, как 3.3/4.2/4.3/4.4a).
