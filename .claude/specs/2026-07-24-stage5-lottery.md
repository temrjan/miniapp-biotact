## Goal

Дать программе ежемесячный доказуемо-честный розыгрыш: участник, заполнивший анкету и активировавший QR за последние 30 дней, автоматически попадает в розыгрыш этого месяца; администратор замораживает список участников с публичным SHA-256 отпечатком, жребий тянется вживую через random.org, победители записываются и список публикуется для сверки. Билеты — бесплатные автоматические лотерейные входы (не тратятся, не выбираются, не переносятся на след. месяц).

## Approach — chosen + why

**Реюз-first + минимальный внешний RNG.** Билеты считаются из УЖЕ собираемых данных (анкета пол/возраст/город + статус «Друг»), новые поля минимальны (18+ чек-бокс). Жребий — внешний (random.org вживую), наш код НЕ выбирает победителя: только (1) замораживает снимок и нумерует билеты, (2) считает SHA-256 хеш, (3) записывает победителей, (4) отдаёт список на сверку. Это дословно стратегия §10.3 (сильнее по доверию, чем §12 «система выбирает»; ратифицировано руководителем, Решение 4).

Отклонения от стратегии, утверждённые руководителем (HTML-план, блок «Требуется ваше решение», Решения 1–4):
- Решение 1 — Формула билетов: 2 источника вместо 4 (анкета=1, Друг=+1, макс 2).
- Решение 2 — Подписка на канал (+1) — убрана.
- Решение 3 — 18+ чек-бокс в анкете; действующих участников с `age>=18` засчитываем без пере-опроса.
- Решение 4 — жребий внешним random.org вживую (см. выше).

⚠️ **Множественный выигрыш** (один человек — несколько призов, если выпали несколько его билетов): ратифицирован Капитаном в обсуждении, но в утверждённый руководителем HTML НЕ входил и в стратегии §10.1–10.4 отсутствует. → перенесён в Open questions, нужно явное подтверждение руководителя ДО PR-5.4 (поймано Ревьюером на факт-чеке спеки).

## Components

- **БД (модуль `loyalty/models.py`):**
  - `lottery_draws` — розыгрыш: `id`, `period` (YYYY-MM, unique — **календарный месяц, который разыгрывается**; эфир 1-го числа СЛЕДУЮЩЕГО месяца, заморозка снимка за 24 ч до эфира), `prize_label`, `status` (open→committed→drawn), `total_tickets`, `participant_hash` (SHA-256), `hash_published_at`, `committed_at`, `drawn_at`, `created_at`.
  - `lottery_tickets` — билеты снимка: `id`, `draw_id` (FK), `user_id` (FK), `ticket_number` (порядковый в рамках draw), `source` (`survey`/`friend`), `is_winner` (bool), `prize_rank` (null/1..4). `UNIQUE(draw_id, ticket_number)`.
  - `customer_profile.is_adult` — новое поле `bool` (nullable/server_default false), 18+ чек-бокс.
- **Сервис (`loyalty/service.py` / новый `loyalty/lottery.py`):**
  - `compute_ticket_count(profile, as_of)` — чистая функция: eligibility + число билетов (0/1/2). **«Активация за последние 30 дней» отсчитывается от `as_of` = момент заморозки (`commit_draw`)**, НЕ от границы календарного периода — зафиксировать явно в PR-5.3 (NIT Ревьюера; формулировка унаследована из плана v4, была неявной).
  - `commit_draw(period)` — атомарно: снимок подходящих участников → строки `lottery_tickets` со сквозной нумерацией → `total_tickets` → SHA-256 хеш канонического списка → `status=committed`, `hash_published_at`.
  - `record_winners(draw_id, winning_numbers[])` — по номерам от random.org помечает `is_winner`+`prize_rank` (1=главный, 2..4=утешительные), `status=drawn`, `drawn_at`. Правило повторного выигрыша одним человеком — по **Open Q5** (пока разрешено, но PR-5.4 не мержим до подтверждения руководителя).
  - `export_draw(draw_id)` — канонический список (для публикации/сверки хеша).
  - **Время (tz-aware, урок `jwt_router`/PR-6.5-B):** вся period-арифметика (эфир 1-го числа, заморозка −24 ч, «последние 30 дней», отсчёт в UI) — через `datetime.now(UTC)` + явную конвертацию в `Asia/Tashkent` для отображения даты; хранение `timestamptz`; **наивный `utcnow()` запрещён**, не полагаемся на пояс процесса/БД. (Проактивный флаг Ревьюера — закладываем в дизайн сразу.)
  - `get_my_tickets(user)` — билеты пользователя в текущем/последнем розыгрыше + приз + отсчёт + итог.
- **Роутеры:**
  - Мини-апп: `GET /api/v1/loyalty/my-tickets`.
  - Анкета: расширить `POST /api/v1/loyalty/survey` полем `is_adult` (+ «Правила акции» согласие — см. Open questions).
  - Админ: `POST /admin/lottery/commit`, `POST /admin/lottery/{id}/winners`, `GET /admin/lottery/{id}/export`.
- **Фронт мини-апп:** экран/карточка «Мои билеты» (число, приз, отсчёт до 1-го числа, «как получить ещё», итог), 18+ чек-бокс в `SurveyCard`.
- **Админка:** экран розыгрыша (заморозить список → показать хеш → ввести выигрышные номера → выгрузка).
- **Уведомления:** пуш за сутки до розыгрыша («завтра розыгрыш, у вас N билетов») + пуш победителю.

## Assumptions

**Ставим на:**
- Жребий тянет человек вживую через random.org; наш код случайность не генерит (стратегия §10.3, ратифицировано).
- Билет = автоматический вход, автоучастие всех билетов (ратифицировано).
- Согласие на обработку ПД УЖЕ собирается при вступлении (`record_consent`, `DATA_PROCESSING`) — переиспользуем, не дублируем.
- **«Анкета заполнена» для базового билета = `gender` И `city` не null. Возраст НЕ обязателен**
  (правка Капитана 2026-07-27, Гейт-1 PR-5.3). Было «`gender` И `age` И `city»`, и при таком
  чтении профиль без возраста отсеивался проверкой полноты РАНЬШЕ, чем доходило до предиката
  adult, — галка 18+ не влияла тогда ни на один исход, то есть PR-5.2 собирал бы контрол-
  украшение. Блокер пойман Ревьюером на Гейте-1 PR-5.3.
- **Adult = `age >= 18`, если возраст известен; иначе — `is_adult`** (правка Капитана 2026-07-27).
  Формула: `adult = (age >= 18) if age is not None else is_adult`. Было «`is_adult` ИЛИ
  `age >= 18`» — при противоречии (галка стоит, а возраст 15) это правило впустило бы
  несовершеннолетнего. Известный возраст побеждает заявление; галка решает только там, где возраста
  нет. Грандфазер действующих сохранён и работает: у кого возраст ≥18 — проходят без галки,
  миграции-бэкфилла по-прежнему нет (он фабриковал бы юридическую декларацию, которой человек не
  давал).
- **18+ не считается ответом анкеты (решение Капитана 2026-07-27, PR-5.2).** Событие `survey_done`
  пишется только если вызов принёс хотя бы одно демографическое поле (пол/возраст/город); одна
  галка 18+ флаг записывает, но событие не тратит. Причина: `survey_done` — 4-й шаг воронки
  регистрации на админ-дашборде (`analytics.get_loyalty_stats` → `RegistrationFunnel`), и зачёт
  одинокой галки завысил бы число «заполнивших анкету». Тем же правилом живёт фронт: карточка
  схлопывается в «Анкета заполнена» только по демографии. Поймано Ревьюером на факт-чеке границ.

**Может убить фичу / переключить решение:**
- Юрист РУз потребует явное согласие НА КАЖДЫЙ розыгрыш → вернуть кнопку «Участвовать» как момент согласия (сейчас — разовое согласие с «Правилами акции»).
- Юрист потребует иную квалификацию акции/иные правила → правки в «Правилах», не в коде розыгрыша.

**Сознательно игнорируем (и почему это ок):**
- Покупка доп.билетов за баллы — за рамками (утверждено, отдельная фича).
- Реферальные билеты, Уровень 3 анкеты, подписка на канал — не Этап 5.
- Резидентство РУз как жёсткий тех-гейт — телефон уже `+998` через бота; резидентство остаётся условием «Правил», не кодовой проверкой.
- Логистика вручения приза — ручная/маркетинг; в софте только контакт победителя (телефон уже verified).

## Acceptance criteria (эпик готов, когда…)

- [ ] Участник с полной анкетой + активацией за 30 дней + 18+ имеет 1 билет; «Друг» — 2; иначе 0.
- [ ] `commit_draw` замораживает снимок, нумерует все билеты сквозно, пишет стабильный SHA-256; повторный commit того же периода идемпотентен/отклоняется.
- [ ] `record_winners` помечает победителей по номерам random.org; правило повторного выигрыша одним человеком — по Open Q5 (подтверждение руководителя до PR-5.4).
- [ ] `export_draw` даёт список, по которому внешне пересчитываемый хеш совпадает с опубликованным.
- [ ] Экран «Мои билеты» показывает число билетов, приз, отсчёт до 1-го числа, итог после розыгрыша.
- [ ] Пуш-напоминание за сутки + пуш победителю уходят.
- [ ] Всё тёмное под `loyalty_enabled`, деньги/леджер не тронуты.

## Test plan

- **Юнит (чистые функции):** `compute_ticket_count` — матрица (анкета полн/частично × 18+ да/нет/по возрасту × активация свежая/старая × newbie/friend) → 0/1/2.
- **Гонки/идемпотентность:** двойной `commit_draw` одного периода не даёт двойных билетов/номеров (под lock/`UNIQUE(period)`).
- **Хеш-контракт:** тест «сериализация снимка → SHA-256 стабилен и воспроизводим независимым пересчётом»; изменение любого билета меняет хеш.
- **record_winners:** номера вне диапазона отвергаются; один user с 2 выигрышными билетами получает 2 записи; ранги 1..4 назначаются по порядку.
- **API:** `my-tickets` self-scoped (чужие билеты не видны); админ-эндпоинты под авторизацией.
- **Фронт:** SurveyCard 18+; карточка «Мои билеты» состояния (0 билетов / N билетов / после розыгрыша).
- Все — мутационная верификация RED→GREEN; прогон под `TZ=UTC` (розыгрыш 1-го числа — даты по Ташкенту).

- **✅ Q5 — Множественный выигрыш: ЗАКРЫТ Капитаном 2026-07-28. Гейт снят.**
  Решение: **один человек — один приз**; выигравший **ИСКЛЮЧАЕТСЯ из последующих раундов —
  именно человек, а не только его номер.** Уточнение получено явным вопросом: две формулировки
  Капитана («один человек — один приз» и «выигравший номерок не участвует дальше») расходятся для
  владельца двух билетов; ратифицирован человек, иначе первое правило не выполнялось бы.
  На эфире: номер уже выигравшего **отклоняется** с явным сообщением, ведущий крутит снова.
  ⛔ Автопропуск отклонён — зал слышал названный номер, его отсутствие в результате нельзя
  объяснить иначе как «поверьте нам». Детали → `.claude/specs/2026-07-28-pr5.4b-record-winners.md` §1.
