## Цель — один абзац
Закрыть **дыру честности тестов** на денежном инварианте конкурентности, которую нашёл аудит: прод-код
сегодня верен (все три `SELECT customer_profile … FOR UPDATE` замка на месте), но **тесты и комментарии
лгут о том, ЧТО именно защищает от гонок** — так что будущий рефактор может тихо снять реальную защиту, а
вся сьюта останется зелёной (staging нет → уедет в прод). PR приводит тесты и докстринги в соответствие с
доказанной реальностью и **делает главный денежный замок (`activate` :390) пуленепробиваемо-тестируемым**
детерминированным race-тестом. **Ноль изменений поведения прод-кода** — только тесты, докстринги и
комментарии.

## Ground truth (проверено чтением кода; будет пере-доказано мутацией при реализации)
Три замка, три разных статуса:

1. **`activate_code` :390 — НЕСУЩИЙ и денежно-критичный.** Единственный per-user сериализатор для гонки
   РАЗНЫМИ кодами на границе (две активации на 9→10 без замка обе флипают +5000; две первые активации обе
   пишут welcome). Атомарный claim (:398) дедупит только ОДИН И ТОТ ЖЕ код — не разные. Снятие замка = реальная
   переплата. **Аудит-динамика: снятие → race-тесты падают** (замок работает), но текущие race-тесты сидят на
   `first_name="Seed"` при `TelegramUser.first_name="BoundaryRace"/"DoubleScan"` → `get_or_create_user`
   (auth/service.py:44-52) ВСЕГДА пишет `UPDATE users` (name меняется) и берёт users-row лок, который тоже
   сериализует racer'ов. То есть гарантия замка сегодня **завязана на побочный эффект** `get_or_create_user`
   (ровно риск SEED-2 аудита: «оптимизируют» этот UPDATE → защита частично слетит незаметно).

2. **`record_consent` :174 — ИЗБЫТОЧНЫЙ (defense-in-depth).** Реальный сериализатор дедупа consent/phone_shared
   — обязательный `UPDATE customer_profile SET registration_source=COALESCE(...)` на :179 (плюс users-row лок
   `get_or_create_user`), который лочит строку профиля ДО guard'ов. **Снятие :174 → тесты зелёные (маскируется).**
   Изолировать замок нельзя без переупорядочивания прод-кода (вне скоупа PR-A).

3. **`submit_survey` :284 — ИЗБЫТОЧНЫЙ (defense-in-depth).** Реальный сериализатор — обязательный
   `UPDATE customer_profile SET **updates` на :290, лочит строку до guard'а `survey_done`. **Снятие :284 →
   тесты зелёные (маскируется).** Тот же расклад, что consent.

Ложь, которую чиним:
- `test_race_two_consent_on_existing_profile_dedup` докстринг (`test_loyalty_consent.py:291-293`):
  «Removing `.with_for_update()` makes this test fail with two consent / two phone_shared rows» — **НЕВЕРНО.**
- `test_race_two_survey_calls_write_survey_done_once` докстринг (`test_loyalty_survey.py:252-253`):
  «removing it lets both racers … both insert» — **НЕВЕРНО.**
- `test_loyalty_handler.py:3` (bot): «The bot CI only runs `ruff check bot/` (no pytest job)» — **НЕВЕРНО**,
  `ci.yml:238-239` гоняет `pytest tests/ -v --no-header`.
- Комментарии в `service.py` (:169-172 consent, :278-279 survey) приписывают защиту `FOR UPDATE`, тогда как её
  даёт последующий обязательный `UPDATE`.

## Скоуп PR
**Входит (тесты + докстринги + комментарии, ПОВЕДЕНИЕ прод-кода не меняется):**
1. **Новый детерминированный race-тест** `activate` в `test_loyalty_activation.py`: новый seed-хелпер сидит
   юзера с полями идентичности (`first_name`/`username`/`last_name`/**`language_code`** — НИТ ревью), ТОЧНО
   совпадающими с приходящим `TelegramUser` (у racer'ов `username=last_name=None`, `language_code=None`, как в
   существующих тестах) → `get_or_create_user` не даёт net-change → **не пишет `UPDATE users`** (нет
   users-row маскировщика). **ОБА сценария сидятся с УЖЕ ЗАКОММИЧЕННЫМ профилем** — иначе
   `INSERT customer_profile … ON CONFLICT DO NOTHING` сам сериализует racer'ов (в PG конфликт с незакоммиченной
   вставкой блокирует второго до коммита первого) → welcome/flip дедупится и БЕЗ замка :390 → мутация не
   покраснеет, критерий приёмки завалится (**МИНОР-1 ревью**):
   - **welcome-гонка:** сид профиля `lifetime=0` (реалистично: consent-first юзер, обычный бот-флоу) → две
     первые активации разными кодами → ассерт ровно ОДИН welcome-row.
   - **boundary-гонка:** сид профиля `lifetime=9` (как `test_race_at_boundary_flips_exactly_once`) → ассерт
     ровно ОДИН +5000 / один `status_friend`.
   При закоммиченном профиле `ON CONFLICT DO NOTHING` бьёт по живой строке (не лочит, не блокирует) →
   **единственный сериализатор = `FOR UPDATE` :390** → его снятие ОБЯЗАНО открыть гонку. Делает гарантию замка
   независимой от побочного эффекта `get_or_create_user` (закрывает SEED-2 для денежного пути).
2. **Правка лживых докстрингов** двух race-тестов (consent :291-293, survey :252-253) → описать РЕАЛЬНЫЙ
   сериализатор (обязательный `UPDATE customer_profile`), убрать ложное «removing FOR UPDATE fails this test».
3. **Правка докстринга бот-теста** (`test_loyalty_handler.py:3`) → CI гоняет bot pytest (`ci.yml:238`).
4. **Правка комментариев в `service.py`** (consent :169-172, survey :278-279; при желании тон коммента :386
   activate) → честно: где сериализация происходит на самом деле; `FOR UPDATE` на consent/survey помечен как
   **избыточный defense-in-depth**, `FOR UPDATE` на activate — как несущий и покрытый детерминированным тестом.
5. **Мутационное доказательство** (харнесс backup→снять замок→прогнать→restore, md5-verified): снятие :390 →
   новый детерминированный тест КРАСНЕЕТ; снятие :174/:284 → зелёные (избыточны) — зафиксировать таблицу в отчёте.

**ЯВНО НЕ входит (→ рекомендованный отдельный follow-up PR, решение Капитана):**
- Любое **удаление/переупорядочивание** прод-замков или обязательных `UPDATE` (сделать consent/survey замки
  единственным тестируемым сериализатором = переносить `UPDATE` после guard'ов). Это поведенчески-смежная
  правка money-adjacent кода → НЕ в «нулевом по поведению» PR-A. Моя рекомендация follow-up: **реордер
  (сделать `FOR UPDATE` первичным сериализатором и покрыть детерминированным тестом)** — но это Гейт-1 отдельно.
- Любые правки логики начисления/флипа/консента.

## Открытая рекомендация Капитану (follow-up, НЕ блокирует PR-A)
consent :174 / survey :284 замки **избыточны** сегодня (реальную защиту даёт обязательный `UPDATE`).
Два честных финала — (i) **удалить** мёртвый defense-in-depth, (ii) **реордер** (перенести `UPDATE` после
guard'ов → `FOR UPDATE` станет единственным сериализатором → покрыть детерминированным тестом).
**Моя реко — (ii) реордер:** явный интенциональный замок под падающим тестом надёжнее, чем защита-как-побочный-
эффект `UPDATE` (тот же класс хрупкости, что SEED-2). Контр-довод: (ii) трогает money-adjacent прод-код возле
go-live — но реордер внутри одной транзакции даёт идентичный итог (те же коммиты), покрывается мутационно-
доказанным тестом, а оставить защиту-побочку хуже. Цена ошибки (ii) низкая (реордер в одной tx, полное
покрытие). Что изменит выбор: если хочешь абсолютный zero-touch прод-кода до флипа — тогда (i)/док-онли и
реордер после go-live. **Отдельный Гейт-1, не сейчас.**
