## 1. Что делает шаг

Убирает последние следы отменённой календарной модели. Ни одного нового поведения: после него
розыгрыш работает ровно так же, но в схеме и коде не остаётся конструкций, описывающих механику,
которой нет с 30 июля.

| Удаляется | Почему живо до сих пор |
|---|---|
| колонка `lottery_draws.period` + её `UNIQUE` | шаг 1 не мог её тронуть — 60 живых чтений; шаг 3 их перевёл |
| `DrawPeriod` (валидатор `^\d{4}-(0[1-9]\|1[0-2])$`) | валидировал тело заморозки, которого больше нет |
| `period_of`, `committable_periods` | мертвы с шага 3, держались ради колонки |
| статус `open` + оба его умолчания | ни один писатель его не пишет с самого начала |
| `draw_label()` | строил ярлык «№3» для поля `period` в ответе |
| поле `period` в ответе мини-аппа (2 места) | держалось ради незагрузившихся бандлов |

Добавляется ровно одно: `draw_number` в ответе мини-аппа вместо ярлыка.

🔴 **`draw_number` → `NOT NULL` из плана §6.2 исполнять НЕЧЕГО — колонка уже NOT NULL.** Проверено на
parity-БД: `pg_attribute.attnotnull` для `draw_number` = `t`. Шаг 1 добавил её `nullable=False`
вместе с `Identity` (Ревьюер ратифицировал это на его Гейте-1), отклонившись от §6.2 плана,
написанного раньше. Пункт вычеркнут, а не «выполнен»: миграция с операцией, ничего не меняющей, —
это ложь в истории ревизий.

## 2. Решения — на ратификацию

### Р-1. `period` уходит из ответа мини-аппа в этом же шаге

**Ратифицировано Капитаном 31.07** («period — удаляй»). Фиксирую цену: участник с **очень старым
закешированным бандлом** увидит «Вы участвуете в розыгрыше  — список зафиксирован» без номера.
Бандл обновляется при следующем открытии мини-аппа; новая карточка (шаг 5) уже на проде и читает
`numbers`/`clean_tickets`, то есть содержательно работает и без номера тиража.

**Что изменило бы выбор:** желание дать бандлам ещё один релизный цикл — тогда поле останется, это
ничего не стоит. Капитан выбрал удалить сейчас.

### Р-2. Ответ отдаёт `draw_number` числом, ярлык строит клиент

**Рекомендация: `draw_number: int | null` вместо `period: str | null`; «№» живёт в строке локали.**

**Почему.** Ярлык «№3» — это текст, а тексты живут в i18n, не на сервере: в узбекской строке номер
может стоять в другом месте фразы, и сервер об этом знать не должен. Сегодня `draw_label()` на
сервере собирает то, что фронт всё равно вставляет в шаблон.

**Контраргумент против себя.** Ещё одна правка фронта в schema-PR, который и без того рискованный.
**Почему не перевесил:** правка тривиальна (две подстановки, две строки локали), а альтернатива —
оставить на сервере функцию, собирающую русский текст. **Цена ошибки:** пустое место вместо номера,
ловится тестом карточки.

### Р-3. У `status` убирается умолчание, а не подменяется на `committed`

**Рекомендация: `ALTER COLUMN status DROP DEFAULT` + убрать `default=` из модели.**

**Почему.** Умолчание существует, чтобы `INSERT` без статуса что-то записал. Единственное осмысленное
значение теперь — `committed`, но тогда голый `INSERT` создаёт **живой тираж**, а это операция,
которую мы обложили подтверждением числом и уникальным индексом. Пусть лучше такой `INSERT` падает.

**Цена ошибки:** тест или скрипт, создающий розыгрыш без статуса, упадёт с NOT NULL. Это правильный
отказ; такие места правятся в этом же PR.

## 3. Миграция

Ревизия поверх `a3c7d15e9b42`:

```python
op.drop_column("lottery_draws", "period")          # UNIQUE уезжает вместе с колонкой
op.alter_column("lottery_draws", "status", existing_type=sa.String(16), server_default=None)
```

Две операции, не три: `draw_number` трогать нечего (см. выше).

`downgrade` — обратные две. ⚠️ **Значения `period` не восстанавливаются**: на проде они уже `NULL`
у всех тиражей новой модели, а у старых их не существовало никогда (таблица была пуста). Колонка
возвращается nullable и пустой; это записывается в докстринг миграции, а не подразумевается.

⚠️ `DROP COLUMN` — каталоговая операция, но `ACCESS EXCLUSIVE`: на таблице из единиц строк
мгновенна.

⚠️ **Откат глубже одной ревизии на непустой таблице не пройдёт.** CI гоняет не `downgrade -1`, а
`alembic downgrade base` → `upgrade head` (джоба `Migration parity`). Мой `downgrade` вернёт `period`
**nullable**, а следующая вниз ревизия `a3c7d15e9b42` ставит ему `SET NOT NULL` — на пустой БД (CI)
это проходит, на проде с тиражами упадёт. Ограничение записывается в докстринг миграции.

## 4. Релиз-чек-лист (перед мержем, на проде)

```sql
SELECT count(*) FROM lottery_draws WHERE status = 'open';      -- ожидание: 0
SELECT count(*) FROM lottery_draws;                            -- для протокола
SELECT count(*) FROM lottery_tickets WHERE draw_id IS NOT NULL; -- для протокола
```

Строки про `draw_number IS NULL` здесь НЕТ, хотя план её требовал: колонка уже `NOT NULL`, и такой
запрос вернёт 0 при любом состоянии данных. Гейт, который не может сработать, хуже отсутствующего —
он создаёт ощущение проверки.

**Ненулевой ответ в первой строке = стоп:** статус `open` не пишет ни один живой путь, и его
появление означает, что в базу писал кто-то помимо кода.

## 6. Тесты

- **Миграция:** вверх → вниз → вверх на чистой parity-БД; `alembic check` пуст; `\d lottery_draws`
  глазами: колонки `period` нет, `draw_number` — `not null`, у `status` умолчания нет.
- **Регрессия:** вся лоялти-сюита зелёная без правок поведения — единственные изменения в тестах
  механические (`period` → `draw_number`).
- **Новое:** `INSERT` розыгрыша без статуса падает (Р-3 — отказ, а не тихий `open`).
- **Фронт:** карточка показывает «розыгрыш №3» из числа; отсутствующий номер не рисует пустой «№».
- **Мутации:** вернуть `server_default='open'` → тест Р-3 краснеет · отдать `draw_number` строкой →
  тест карточки краснеет · снять `NOT NULL` → `Migration parity` ловит расхождение модель↔миграция.

## 7. Риски

| Риск | Митигация |
|---|---|
| Миграция роняет прод (прецедент #30) | ручная миграция против чистой parity, round-trip, `Migration parity`, релиз-чек-лист, `\d` глазами |
| `SET NOT NULL` падает на строке без номера | первая строка чек-листа; ненулевой ответ = стоп |
| Старый бандл теряет номер тиража | принято Капитаном (Р-1); карточка содержательно работает без него |
| Что-то ещё читает `period` | grep по трём пакетам до и после; админка `period` не читает вовсе (проверено) |

**Откат:** `downgrade` + revert кода. Колонка вернётся пустой — записано в докстринге.

## 8. Чего шаг НЕ делает

Никаких изменений поведения розыгрыша · ничего в админке (она `period` не читает) · история тиражей ·
уведомления · трогать `participant_hash`, штамп, отмену.
