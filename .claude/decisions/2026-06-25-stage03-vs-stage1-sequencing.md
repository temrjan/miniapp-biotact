# Решение: после PR-0.2 — PR-0.3 (dev-контур) vs Этап 1 (CRM-фундамент)
Статус: ПРИНЯТО (технически решаемо; финальный «добро» — Капитан) · 2026-06-25 · кресло Ревьюер · метод /crucible

## Вопрос и критерий «хорошо»
Что делать Инженеру следующим: **A** — PR-0.3 (dev-контур) строго по порядку Этапа 0, или **B** — сразу Этап 1 (consent/customer_profile/customer_event)?
Приоритет свойств: (1) прод-риск/безопасность (merge=deploy, класс инцидент-#30) · (2) корректность/обратимость · (3) ценность раньше (effectiveness-over-plan) · (4) «не впрок» · (5) соответствие порядку плана.

## Кандидаты
- **A** — PR-0.3 сейчас: `docker-compose.dev.yml` + `DEV.md` + vite-proxy. E2E отложить до Этапа 4.
- **B** — сразу Этап 1: первые CRM-таблицы. Dev-контур поднять перед Этапом 4.
- **C** — Deploy gate (ops) следующим. *(Не «вместо A/B», а предусловие: см. red-team — пристёгивается к пути, ведущему в Этап 1.)*

## Лидер: B — Steelman (с доказательством)
- **Аддитивно-безопасно (VERIFIED, не предположение):** прод стоит на `f1e2d3c4b5a6` (SSH read-only); откат PR-1 #31 **чист** — на проде НЕТ `consent`/`customer_profile`/`customer_event`/`point_ledger`/enum-типов, `users.phone_verified_at` отсутствует. Этап 1 = CREATE новых таблиц + nullable-колонка → не конфликтует с дивергенцией прод≠цепочка (GIN/`is_purchasable`).
- **Ценность раньше:** первые CRM-данные — это ядро программы; ценность dev-контура (туннель+тест-бот для E2E) нужна на **Этапе 4** (spec line 36 «Ops Капитана … блокирует E2E Этапа ≥4»), т.е. через 3 этапа.
- **Этапу 1 хватает имеющегося:** миграции + pytest бегут на podman `biotact-pg` + parity-гейт (verified exit=0) + postgres:17 в CI (spec Test plan line 140). Туннель/тест-бот не требуются.
- **effectiveness-over-plan:** строить dev-контур «впрок» за 3 этапа до его ценности — оптимизация не туда (rules #5).

## Red-team: что атаковал → что приземлилось
1. **deploy.yml не испытан на реальной DDL → инцидент-#30 на первой миграции Этапа 1.** PR-0.1 reconcile был verified no-op, PR-0.2 — non-schema. Первый schema-PR Этапа 1 = ПЕРВЫЙ реальный `alembic upgrade head` на прод через авто-деплой. → **ФАТАЛЬНО для «голого B»**, но не для B: чинится предусловием C (Deploy gate до первого schema-мёржа). Авторинг Этапа 1 можно начать сейчас; гейтится **merge**, не код.
2. **«Аддитивно-безопасно» — а вдруг ложь (остатки PR-1)?** → проверил read-only: residue НЕТ. Не приземлилось.
3. **dev-контур нужен раньше Этапа 4?** Миграции+pytest не требуют туннеля/тест-бота; CI = источник истины воспроизводимости. Не приземлилось.
4. **Скрытая цена B: Этап 1 без формализованного DEV.md.** Корректность Этапа 1 держится на CI (clean postgres:17 + pytest), не на локальном ad-hoc. Не приземлилось.
5. **Отложенный PR-0.3 забудут.** Self-gating: E2E Этапа 4 физически не пойдёт без туннеля → отсутствие самоочевидно; задача в плане. Не приземлилось.
6. **Steelman A: формализовать ad-hoc podman сейчас.** Реальная, но низко-срочная польза; сетап тривиально воспроизводим (документирован в CI yml). Фатальной атаки на B не даёт.

## Вердикт: ВЫСТОЯЛО → **B, скорректированный = «B + Deploy gate до первого schema-мёржа Этапа 1»**
Единственная фатальная атака (#1) не убивает B, а добавляет предусловие C (всё равно обязательная работа Этапа 0 по спеке).

## Остаточный риск (принято) + Tripwire
- **Принято:** dev-контур (PR-0.3) отложен до Этапа 4 (tracked, self-gating).
- **Tripwire-1:** B неверно, если Deploy gate НЕ может быть пройден до первого schema-мёржа Этапа 1 → тогда стоп, Deploy gate первым.
- **Tripwire-2 (RESOLVED):** был «неверно, если на проде есть остатки PR-1» → проверено read-only: чисто.
- **Дисциплина:** миграции Этапа 1 писать против чистой parity-БД + ревью вручную, НЕ автоген против прода (иначе автоген затащит «фиксы» дивергенции). Parity-гейт + ревью ловят.

## Если «ТВОЙ ВЫБОР» (остаточно-ценностное)
Рекомендую **B-скорректированный**. Единственная причина выбрать A — чистое предпочтение «закрыть Этап 0 строго по порядку»; технического основания за A нет, B доминирует по критерию. Решает Капитан.
