# Находка: шаг CI «Type check» (frontend) не может провалиться

Не часть спеки `2026-08-06-cart-not-cleared-after-payment.md` — обнаружено Инженером попутно при
внесении МИНОРа по спеке, отдельно проверено мной. Отдельный файл, потому что тема отдельная (CI
frontend-джобы), не корзина.

## Вердикт

**Подтверждено (VERIFIED, две независимые проверки — Инженер и я, разными ошибками). Не БЛОКЕР
для PR #118.** Рекомендация: почини сейчас, отдельным маленьким PR, одна строка.

## Механизм (проверено лично, `packages/frontend`)

`tsconfig.json` — solution-style:
```json
{ "files": [], "references": [{ "path": "./tsconfig.app.json" }, { "path": "./tsconfig.node.json" }] }
```
CI-шаг `frontend` (`.github/workflows/ci.yml:43-44`): `npx tsc --noEmit`. Без `-b` компилятор не
идёт по `references` и держит пустой `files: []` — проверять нечего, любой exit — `0`.

## Проверил сам, своей ошибкой (не переиспользовал пример Инженера)

Внёс пробный файл `src/ts-check-probe.ts` (`export const reviewerProbe: number[] = ['not a
number', 'also not a number'];`), прогнал, удалил, дерево чистое после:

```
npx tsc --noEmit          → EXIT 0, тишина            (ложно-зелёный)
npx tsc -b --force         → 2× TS2322, EXIT 2          (ловит)
npm run build (= tsc -b && vite build) → EXIT 2, те же 2 ошибки в выводе (ловит)
```
(Первый прогон `npm run build` через `| tail` дал мне самому ложный `EXIT=0` — склейка кода
возврата с `tail`, не с `npm`. Пересчитал без пайпа — `EXIT=2`, верно.)

На РЕАЛЬНОМ дереве (после удаления пробника) `npx tsc -b --force` → **EXIT 0** — типы проекта
сегодня чисты; шаг «Build» их и защищал всё это время.

## Контекст, которого не было в докладе Инженера

1. **Сосед по тому же файлу уже делает правильно.** `admin` job, `ci.yml:76-77`:
   `Type check: npx tsc -b` — то есть исправление не изобретает паттерн, а копирует уже рабочий
   из соседней джобы этого же файла.
2. **Дыра — с первого коммита, не регрессия этой сессии.** `git log -- tsconfig.json` →

   17.03.2026) — то есть строгость `type-check` заявлена НАМЕРЕННО, просто никогда не работала
   из-за формы `tsconfig.json`, унаследованной с самого начала.

## Рекомендация (по формату §14)

**Почини сейчас, отдельным PR, не в #118.**
- **Почему:** правка — одна строка (`ci.yml:44`: `npx tsc --noEmit` → `npx tsc -b`, вслед за
  паттерном `admin`-джобы); уже дважды проверена на реальном дереве, что не уронит текущий CI
  (типы сегодня чисты). Оставлять названный «Type check» шаг фиктивным — держать в кодовой базе
  сигнал, которому нельзя верить, ровно тот класс дефекта, о котором отдельно предупреждает
  `/rules` §10.
- **Сильнейший контраргумент против меня:** это находка, а не задача сессии — Капитан просил
  чинить корзину, а не CI; вкорачивание чужого скоупа с ходу — тоже своего рода расширение задачи.
- **Почему не перевесил:** «Build» уже ловит реальные ошибки сегодня — фикса без риска не
  сделать хуже, только явным; отложить — значит держать в репозитории шаг, чьё название лжёт, и
  чем дольше, тем больше шанс, что кто-то доверится именно ему (например, при будущей оптимизации
  `package.json`'s `build`-скрипта, если `tsc -b` из него уберут «для скорости», думая, что
  отдельный шаг `Type check` уже прикрывает типы).
- **Цена ошибки, если рекомендация неверна:** нулевая по функциональности приложения (CI-only
  правка, `tsc -b` уже используется в этом же файле для `admin`); откат — одна строка обратно.
- **Что изменило бы выбор:** явное намерение Капитана в ближайшее время делать отдельный
  инфраструктурный проход по CI целиком — тогда эта находка просто ложится в тот backlog вместо
  отдельного PR прямо сейчас.

**НИТ:** `--force`, который использовал Инженер при локальной проверке, на CI не нужен — раннер
всегда со свежим чекаутом (`cache: 'npm'` только на `node_modules`, `.tsbuildinfo` нигде не
кэшируется, проверено `grep cache ci.yml`), значит `tsc -b` и `tsc -b --force` в CI ведут себя
одинаково. Предпочту голый `tsc -b` — дословное совпадение с `admin`-джобой, а не ещё один флаг
для объяснения будущему читателю.
