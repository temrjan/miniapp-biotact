## Вердикт Ревьюера (через Капитана, 2026-06-29): ✅ APPROVED — чисто. 0 блокеров / 0 миноров.

CoVe — воспроизведено на **мигрированной схеме** (не только на модели):
- `id` → `bigint DEFAULT nextval('customer_event_id_seq')` — BIGSERIAL реально создаётся (alembic check для PK-сиквенсов это не ловит → проверено в БД; INSERT на проде не упадёт).
- FK `confdeltype=c` (CASCADE) на уровне БД → cascade-тест опирается на реальный констрейнт.
- Колонки/индексы/типы/NOT NULL — совпадают. up/down/up симметрия + паритет. `pytest -k customer_event` → 5 passed.

**Ответы на 3 вопроса (все — оставить как есть):**
1. `occurred_at` + `created_at` раздельно — **оправдано**. occurred_at = бизнес-время (бэкфилл исторических активаций из заказов — в плане Этапа ≥2 → названная будущая потребность, не гипотетика), created_at = аудит вставки. Цена — одна колонка.
2. Нет `User.events` relationship — **осознанно и корректно** (высокочастотная, читаем по user_id-индексу, удаление через DB CASCADE; ORM-коллекция = потенциальный memory-bloat).
3. `payload` JSONB nullable без server_default `'{}'` — **ок**. NULL = «деталей нет» семантически чище и отличимо от явного `{}`; тест покрывает NULL.

**Forward-notes Этапа 2 (НЕ трогать сейчас — пере­смотреть когда появятся read-пути; rules #6 — паттернов чтения ещё нет):**
- **Composite-индекс `(user_id, occurred_at)`** обслужит каноничный запрос таймлайна `WHERE user_id=? ORDER BY occurred_at` лучше двух одиночных. Сейчас добавлять = спекулятивно. **К пересмотру на Этапе 2.**
- **`event_type` без CHECK** (by design, рост словаря) — целостность держится конвенцией «сервисы всегда через `CustomerEventType`». На Этапе 2 проследить отсутствие magic-strings (free-string тест это документирует).
