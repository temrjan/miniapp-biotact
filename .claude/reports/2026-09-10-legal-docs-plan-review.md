## Зафиксированный trade-off (не находка, к сведению Капитана)

Build-time флаг не защищает от чтения текстов из JS-бандла: draft-контент физически отдаётся в чанке статикой при любом состоянии флага (content-hash URL виден из главного бандла). Для юридической публикации это несущественно (тексты-проекты и так ходят по рукам, читаемы как документы только через UI, которое закрыто), а серверный флаг противоречил бы ратифицированному подходу «build-time». Принято как предел механики; условие переоткрытия: потребность скрывать текст от детерминированного скачивания — тогда флаг уезжает на сервер.

## Новые находки (атака на механику F1)

### МИНОР (обязательные дописки, без ре-ревью)

**М1. Нет серверной валидации присланной `doc_version`.** Механика «бэк пишет строку как есть» переносит доверенную границу на клиента: в append-only юридическую запись (предъявляется участнику по п. 15.5) уйдёт произвольная строка ≤50. Строка в план/спеку: сервер валидирует ФОРМАТ (`^offer:<v>+policy:<v>$`, max_length=50). Валидация формы не второй источник версии — значения сервер не знает, что и зафиксировано планом.

**М2. Обратная совместимость `ConsentRequest` не определена.** Бэк PR-2 деплоится раньше, чем все клиенты обновятся (Telegram кэширует клиент). Если `doc_version` обязательное — вступление в Клуб для старых клиентов ловит 422 = регрессия главного сценария в проде. Строка в план/спеку: `doc_version` опционально, для клиентов без него — default (значение по умолчанию определяется в спеке; legacy-значение должно либо соответствовать формату М1, либо формат допускает legacy-значение явно).

## Находки

### БЛОКЕР

**F1. Внутреннее противоречие плана: версия документа раздвоена между бэком и фронтом.**
План одновременно утверждает три вещи:
1. «Версия — константа рядом с текстом» (фронт, `src/legal/`);
2. «`consent.version` = композит `offer:<дата>+policy:<дата>`» (бэк; сейчас бэк хардкодит `DATA_PROCESSING_CONSENT_VERSION = "1.0"`, `service.py:419`);
3. «подмена на утверждённые редакции = правка контент-файлов (**один коммит, без кода**)».

Из (1)+(2)+(3) следует: подмена текстов «без кода» оставляет в БД запись с версией «1.0» при тексте draft-2026-08-20 — то есть сведения об акцепте (15.5) будут юридически ложными. Три строки плана несовместимы без четвёртой: где единственный источник версии и кто его бампает при подмене текстов. План обязан это разрешить текстом (например: «единственная версия — константа в бэке; фронт получает её из `/loyalty/me` или дублирует под страж-тестом сверки; подмена текстов = один коммит: контент-файлы + константа версии бэка + сверка»). Механика — на выбор Инженера, отсутствие механики — блокер: это контракт данных с юридическим следствием.

### МИНОР

**F2. Команды гейтов в плане неполные.** API: `ruff check src/ && pytest` — нет `ruff format --check` и `mypy --strict`; фронт: нет `npm run build`. Репо-стандарт (`.claude/reviewer-onboarding.md` §9): все четыре API-команды + `tsc -b && lint && test && build`. Раздел плана называется «Команды гейтов (для спеки)» — занеси полный набор, чтобы спека не унаследовала воспроизводимость ниже стандарта.

**F3. Гейт по гранту молча игнорирует версию.** «Гейт показывается ТОЛЬКО при отсутствии активного гранта» — грант версии «1.0» закроет гейт при новой редакции. Если это осознанно (повторный акцепт — только через уведомление по 13.2 / баннер PR-3), зафиксируй одной строкой в плане/спеке; иначе решение будет принято неявно на коде.

**F4. Вопрос 1 Капитану недооценивает 13.2.** Уведомление о новой редакции обязано быть не менее чем за 30 календарных дней (:199). Баннер в профиле — допустимый канал («посредством Приложения»), но подмена draft→финал с мгновенной сменой версии юридически требует лага 30 дней. Это процесс заказчика, не код; рекомендация «код сейчас, релиз после утверждения» согласуется — добавь в план строку про 30-дневный срок как ограничение релиза.
