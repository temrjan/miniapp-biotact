## 1. Факт с прода: таблицы розыгрыша пусты — §11.5 закрыт

**На проде нет ни одного розыгрыша и ни одного билета.**

Доказательство (без доступа к серверу, двумя независимыми ветками):

1. Капитан подтвердил: кнопку «Заморозить» в админке на проде никто не нажимал.
2. Проверено по коду: единственный путь записи в обе таблицы — `commit_draw`
   (`lottery.py:261` — создание розыгрыша, `lottery.py:281` — создание билетов).
   Сырых INSERT и других писателей нет (grep `LotteryDraw(|LotteryTicket(|INSERT INTO lottery_`
   по `packages/api/src`).

**Следствие для шага 1:** миграция пишется в простом варианте — без бэкфилла `draw_number`,
без решения о судьбе данных в `period`. Данные-агностичный усложнённый вариант не нужен.

**Остаточное условие:** между сейчас и мержем кнопка остаётся доступной в админке. Поэтому в
релиз-чек-лист шага 1 добавляется одна строка — **перед мержем** любой, у кого есть доступ к
серверу, выполняет:

```sql
SELECT (SELECT count(*) FROM lottery_draws) AS draws,
       (SELECT count(*) FROM lottery_tickets) AS tickets;
```

Ожидаемый ответ — `0, 0`. Это формальное подтверждение, а не разведка. Если ответ другой —
стоп, миграция пересматривается.

## 2. Ратификация: состояние билета выводится, а не хранится колонкой — §11.1 закрыт

**Ратифицировано с тремя условиями:**

- **(а) Граница вывода.** Выводятся только `ЧИСТЫЙ / В РОЗЫГРЫШЕ / ИСПОЛЬЗОВАННЫЙ` — из
  `tickets.draw_id` + `draws.status`. Отметка **ПОБЕДИЛ — хранимая** (она не выводится из
  статуса розыгрыша; механика уже построена в PR-5.4b). Из ратификации не вытекает её
  удаление или «вывод». Модель гибридная, и это нормально.
- **(б) Аудиторский след отмены.** При отмене тиража снятие штампа (обнуление
  `draw_id`/`ticket_number`) стирает связку «билет побывал в тираже №N» — а это ровно тот
  след, который нужен при разборе злоупотребления «заморозил → выгрузил → отменил → переиграл»
  (подозрение Инженера №1 в ТЗ аудита §7). Вопрос **уходит Ревьюеру в Н3**: либо история
  штампов журналируется, либо Капитан отдельным решением явно принимает потерю. Умолчание
  недопустимо.
- **(в) Условие отмены ратификации.** Ратификация действует, только если аудит Н2 (полная
  таблица переходов) не найдёт клетку, где вывод состояния неоднозначен. Первый кандидат на
  проверку: момент перехода `committed → drawn` при покадровой записи победителей (после
  первого победителя или после всех?). Находка такой клетки возвращает решение Капитану.

**Почему вывод, а не колонка:** один источник истины вместо двух; отмена тиража сводится к
снятию штампа; переход «в розыгрыше → использованный» не требует прохода по строкам. Это
философия репозитория: `balance = SUM(point_ledger)`, а не колонка (CLAUDE.md).

**Сильнейший контраргумент (рассмотрен, не перевесил):** по строке билета без джойна состояние
не видно. Выборка чистых — `WHERE draw_id IS NULL`; индекс под неё планируется в шаге 1
(сегодня его нет — формулировка плана §6 верна, индекс обязателен в schema-PR).

**Цена ошибки по-честному:** если вывод окажется неудобным, возврат к колонке — полноценный
schema-PR с гейтом `Migration parity` и ручной проверкой против чистой БД (класс риска
инцидента #30), а не «обратимая миграция». Выбор всё равно остаётся: альтернатива — тоже
schema-PR, но с двумя источниками истины с первого дня.

## 3. Ратификация: последние 4 цифры телеграм-ID — только в печатный список — §11.3 закрыт

**Ратифицировано: только в печатный список. Хешируемая строка не меняется.**

- Контракт отпечатка подтверждён чтением кода: `номер;user_id;источник`
  (`lottery.py:138-140`). Он не трогается.
- **Почему:** в хеше 4 цифры ничего не доказывают — они не уникальны (~50% коллизии уже при
  ~120 участниках, §5.3 плана). А смена контракта переписывает 292 строки тестов выгрузки
  (`test_lottery_export.py`, размер подтверждён) и публикует идентификатор в доказательном
  артефакте.
- **Как участник находит себя:** по номеру билета из своей карточки (показ номеров —
  обязательная часть шага 5); 4 цифры в печатном списке — человеческая подсказка, не
  идентификатор.
- **Цена ошибки и срок принятия решения:** если публикация потребует доказуемой привязки
  номера к человеку, смена контракта бесплатна **только до первого опубликованного хеша**.
  Формат первой публикации должен быть утверждён руководителем до первого розыгрыша — это
  согласуется с §11.6 плана (юридика блокирует первый розыгрыш).
