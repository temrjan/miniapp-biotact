# Решение: бот не должен молча подменять файл

**Инженер · 2026-08-11.** Подробное решение к инциденту 5 августа (разбор —
`2026-08-11-protocols-bot-audit.md`). Правки относятся к **репозиторию бота**
(`github.com/temrjan/protocols-bot`), не к этому. Кода ещё нет — это план.

---

## 1. Задача сформулирована неверно, если считать её одним багом

Отказов **два, зеркальных**, и лечить надо оба сразу — иначе лечение снова породит противоположный.

**Отказ А (был раньше, уже «вылечен»):** оператор в середине загрузки присылает новый файл — тот
**затирает** контекст начатой загрузки. Автор закрыл это фильтром `StateFilter(None)` на входных
обработчиках. Его собственный докстринг (`upload.py:180-182`):

> «Only matches when the user is not in another FSM flow, so sending a document mid-way through
> (e.g. while waiting for a protocol number) no longer overwrites the ongoing state.»

**Отказ Б (действующий, случился 5 августа):** обратная сторона того же решения. Раз новый файл
теперь **не** начинает загрузку, он просто игнорируется — а старая, брошенная накануне загрузка
доживает до следующего дня и присваивает себе введённый номер.

> Лекарство от «новое затирает старое» дало «старое съедает новое». Оба варианта молчаливы —
> оператор в обоих случаях видит успех.

**Значит цель не «вернуть как было» и не «запретить сильнее», а СНЯТЬ МОЛЧАНИЕ:** любое
столкновение старой и новой загрузки должно быть названо вслух.

## 2. Механика отказа Б — по строкам

| Шаг | Код | Что происходит |
|---|---|---|
| 1 | `upload.py:172,229` — `@router.message(StateFilter(None), F.document / F.photo)` | вход в загрузку только при **пустом** состоянии |
| 2 | `core/loader.py:25` — `RedisStorage.from_url(settings.redis_url)` | **TTL не задан** → брошенное состояние живёт вечно |
| 3 | `upload.py:463` — `@router.message(UploadStates.waiting_protocol_no)` | ловит **любое** сообщение, без фильтра типа |
| 4 | там же: `protocol_no = (message.text or "").strip()`; если пусто — переспросить и `return` | фото попадает сюда, `text` пуст → бот молча повторяет вопрос, **оставаясь в старом контексте** |
| 5 | оператор вводит номер | сохраняется `file_id` из **старых** `state.data` |

Подтверждение из переписки: бот ответил «Файл: **5026.jpg**», хотя прислали `23.jpg`.

---

## 3. Решение — четыре изменения

### Изменение 1. Срок жизни состояния (закрывает «доживает до завтра»)

`bot/core/config.py` — новая настройка:
```python
fsm_ttl_minutes: int = 30   # брошенная загрузка умирает сама
```

`bot/core/loader.py`:
```python
from datetime import timedelta

if settings.redis_url:
    ttl = timedelta(minutes=settings.fsm_ttl_minutes)
    logger.info("FSM storage: Redis ({}), TTL {}", settings.redis_url, ttl)
    return RedisStorage.from_url(settings.redis_url, state_ttl=ttl, data_ttl=ttl)
```

**Проверено на живой библиотеке, а не по памяти:** aiogram 3.22.0,
`RedisStorage.__init__(..., state_ttl: int | timedelta | None = None, data_ttl: ... = None)`,
а `from_url(url, connection_kwargs=None, **kwargs)` пробрасывает их в конструктор.

⚠️ **TTL один не лечит.** Он убирает «через сутки», но столкновение внутри 30 минут остаётся —
а именно так выглядит обычная работа оператора. Поэтому изменение 2 обязательно.

### Изменение 2. Новый файл прерывает старую загрузку — вслух (закрывает суть)

Снять `StateFilter(None)` со входных обработчиков и добавить явную обработку столкновения.

```python
# upload.py — вместо StateFilter(None)
@router.message(F.document)
@router.message(F.photo)
async def handle_incoming_file(message, state, moderator_repo, user_repo) -> None:
    data = await state.get_data()
    stale = data.get("filename")          # был ли незавершённый файл

    await state.clear()                    # новый файл всегда начинает заново
    await state.update_data(...)           # как сейчас
    await state.set_state(UploadStates.waiting_year)

    if stale:
        await message.answer(
            get_text(lang, "admin_upload_restarted").format(old=stale, new=filename)
        )
    await message.answer(get_text(lang, "admin_start"), reply_markup=build_year_keyboard())
```

Текст (ru):
> ⚠️ Незавершённая загрузка «**{old}**» отменена — начинаем заново с «**{new}**».

**Почему «прервать», а не «спросить кнопками».** Вариант с выбором («заменить / продолжить старую»)
рассматривал и отклонил: он добавляет ещё одно состояние и ещё одну развилку в поток, где ошибка
уже один раз стоила подмены документа. Прерывание однозначно, а исходная забота автора («новое не
должно молча затирать старое») закрыта тем, что **сказано вслух**.

Оригинальный отказ А при этом не возвращается: затирание перестаёт быть тихим.

### Изменение 3. Называть файл в момент запроса номера (делает отказ заметным)

Даже если что-то пойдёт не так, оператор увидит подмену **до** сохранения.

```python
await message.answer(
    get_text(lang, "admin_ask_protocol_no_for").format(filename=data["filename"])
)
```
> Файл «**5026.jpg**». Введите серию препарата:

В инциденте бухгалтер увидела бы «5026.jpg» вместо своего «23.jpg» и остановилась.

### Изменение 4. Нетекстовый ответ на вопрос о номере — не молчать

`upload.py:463` — сейчас любое нетекстовое сообщение даёт немой переспрос. После изменения 2 фото
и документы туда уже не дойдут (их перехватит вход), но остаются стикеры, голосовые, контакты:

```python
if not protocol_no:
    await message.answer(get_text(lang, "admin_expect_number_text"))
    return
```
> Жду **номер серии текстом**. Чтобы загрузить другой файл — просто пришлите его.

## 4. Отдельно: «номер протокола» — это на самом деле серия

Поле `protocol_no` хранит **серию препарата**, а интерфейс просит «номер протокола». В сертификате
это разные реквизиты: «Протокол испытаний № 178» и «Серия препарата: 5026». Оператор в момент сбоя
ввёл `23` — серию **соседнего препарата**.

**Правка только текстов** (`bot/texts/*`), схему не трогать: «Введите номер протокола» → «Введите
серию препарата». Схему менять нельзя без миграции и без решения, нужен ли поиск по настоящему
номеру протокола — это отдельная задача.

## 5. Тест-план (правило №0: сначала красный)

| # | Тест | Красная фаза |
|---|---|---|
| Т1 | Брошенная загрузка + новый файл → сохраняется **новый** файл | на текущем коде падает: сохранится старый |
| Т2 | Брошенная загрузка + новый файл → пришло предупреждение с обоими именами | падает: сообщения нет |
| Т3 | Фото в состоянии ожидания номера → загрузка начинается заново, а не переспрос | падает |
| Т4 | Состояние старше TTL → нового файла достаточно, старого контекста нет | падает: TTL нет |
| Т5 | Запрос номера содержит имя файла | падает |
| Т6 | Обычный путь (файл → год → продукт → номер) не сломан | зелёный сейчас — регресс-сеть |

**Мутации (каждая обязана уронить именно свой тест):**
М1 вернуть `StateFilter(None)` → Т1, Т3. · М2 убрать `state.clear()` → Т1. · М3 убрать TTL → Т4. ·
М4 убрать имя файла из запроса → Т5.

CI бота уже гоняет `ruff check`, `ruff format --check`, `pytest tests/ -v` — гейты готовые.

## 6. Порядок работ и риски

1. Изменение 1 (TTL) — самостоятельное, безопасное.
2. Изменения 2+4 — вместе, это одна логика входа.
3. Изменение 3 и тексты — вместе.
4. Прогон тестов, PR, релиз бота, `systemctl restart protocols-bot`.

**Риск:** перезапуск бота **сбрасывает состояния Redis-сессий** — если в этот момент кто-то
загружает документ, ему придётся начать заново. Мелочь, но выпускать лучше вне рабочего дня.

**Откат:** правка кода, откатывается коммитом; данные не затрагиваются, миграций нет.

**Оценка:** малый круг — примерно один заход с тестами. Гейты и CI уже есть.
