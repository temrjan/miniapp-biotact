## 🔴 БЛОКЕР раунда 4 (закрыт) — `source` на файле с write-only канала → RCE root на bcv2

**Диагноз Ревьюера, принят целиком, без спора.** `source "$FACTS_FILE"` интерпретировал содержимое
как shell-код. `prod-facts.txt` едет по каналу, чья ЕДИНСТВЕННАЯ гарантия — «укравший ключ может
только писать файлы, не выполнять код» (`rrsync -wo`, обоснование прямо в `biotact-pg-backup.sh`).
`source` эту гарантию снимал: положить файл = выполнить root'ом на bcv2 в 04:00. Моя фраза в
отчёте раунда 3 «тронуть их может только тот, у кого уже есть root» была неверна ровно потому, что
путала root на ПРОДЕ (кто пишет facts) с root на BCV2 (кто их читает) — а разделение этих двух зон
и есть весь смысл офсайта.

**Фикс:** `source` заменён на whitelist-парсер (`read_yesno`/`read_num`/`read_alert` — `sed`, один
захват на вызов, значение обязано целиком совпасть с `yes|no`, `[0-9]{1,10}` или `ok|error`; всё
остальное — пустая строка, откатывается на безопасный дефолт). Применено к **обоим** файлам —
`FACTS_FILE` (сам блокер) и `STATE_FILE` (М-1, тот же приём, ниже экспозиция, но один паттерн в
скрипте, не два).

**Доказательство — не рассуждением, атакой на себя:**
```
disk_ok=yes; touch /tmp/PWNED-$(date +%s); echo pwned #
```
Подсунул этот файл суточной проверке напрямую. `exit=0`, **`/tmp/PWNED-*` не появился** — код не
исполнился. `disk_ok` корректно ушёл в `unknown` (строка не прошла вайтлист `yes|no` целиком) —
итог `4/5`, не `5/5` и не крах. Отдельно проверил вайтлист локально на вредоносной строке
`; rm -rf / #` — возвращает пусто, не проходит.

**М-2 (текстовки) закрыт тем же фиксом.** `disk_ok`/`expire_log_ok`/`stale_orders_ok` теперь
трёхветочные (`yes`/`no`/иначе), а не двухветочные (`yes`/иначе) — «неизвестно (факты недоступны)»
и «не отчитывался вовремя» больше не путаются. Сторож не утверждает то, чего не знает.

**М-3 (боевой путь под окружением cron) закрыт буквально той командой, что просил Ревьюер:**
```
env -i PATH=/usr/bin:/bin /usr/local/sbin/biotact-sentry.sh --daily
```
`exit=0`; `/var/log/biotact-sentry.log` **впервые создан боевым путём** (до этого не существовал —
Ревьюер поймал верно, все мои прежние прогоны шли с `SENTRY_LOG`): `daily: 5/5 ok, sent to 2/2`.
`openssl`/`jq` нашлись под голым `/usr/bin:/bin`. Дополнительно (не просили, но раз уж искал
хрупкость) — добавил `PATH=` явной строкой в `/etc/cron.d/biotact-sentry`, тем же приёмом, что уже
стоит у `certbot`/`staticroute` на этом хосте: снимает «сработало случайно», не только «сработало».

**Регресс после фикса** — холодный старт, полный цикл 2-провала→алерт→`error`, восстановление на
границе 901с: все три дали тот же результат, что в раунде 3. Фикс безопасности функциональность не
тронул.

## Отклонение от спеки — два, оба вынужденные

1. **`APP_HOST` сделан переопределяемым** (`SENTRY_APP_HOST`) — в спеке не было. Без этого красный
   тест писал бы в реальный Telegram текст «app.biotact.uz не отвечает» про заведомо здоровый прод.
   Тестировал на `nonexistent-test-host-xyz123.invalid`, боевой путь — на настоящем хосте, без
   переопределения.
2. **`logrotate.d`-конфиг получил `su root root`**, которого не было в спеке. `logrotate -d` сразу
   отказал: `/var/log` на bcv2 — `775 root:syslog`, ротация без `su`-директивы небезопасна. Не
   изобретал — тот же приём уже стоит в `/etc/logrotate.d/cloud-init` на этом же хосте.

## Как тестировал — каждый пункт §6 с командой и выводом

**Условие 1 (мониторинг не может сломать бэкап).** Копия скрипта с намеренно битой командой сбора
(`psql -d nonexistent_db_on_purpose`) → `exit=0`, новый дамп создан и провалидирован,
`stale_orders_count=unknown`/`stale_orders_ok=no` — безопасный дефолт, не крах. Реальный (небитый)
прогон отдельно: `disk_ok=yes disk_pct=15 expire_log_ok=yes stale_orders_ok=yes` — совпало с
известным состоянием прода.

**Три таймлайна state machine (§0.5), проверены инъекцией состояния, не ожиданием часов:**
- (а) 1 провал → `fail_count=1 alert_state=ok` — не будит.
- (б) 2 провала → алерт (реально доставлен, `alert_state=error`) → 10 мин зелени (`green_since`
  выставлен, при подмене на `now-600` восстановление не уходит, таймер не тронут) → провал
  посреди ожидания → `green_since` **сбросился** в пусто, `fail_count=1`.
- (в) `green_since=now-901` → восстановление ушло, `alert_state=ok`, `green_since` пуст. Граница
  `now-600` (<900) отдельно проверена — не уходит.

**БЛОКЕР-1** (битый токен, оба получателя недоступны, хост недоступен, 2 провала): `alert_state`
остался `ok`, лог — `alert send FAILED for ALL admins, will retry next minute`.

**БЛОКЕР-3** (реальный токен, один `admin_id` подменён на несуществующий): `alert_state` **перешёл**
в `error` (второй получатель дошёл), лог — `delivery failed for: 111111111 (alert)`.

**Гонка `flock`** — два прогона одновременно в фоне: оба `exit=0`, state не побит.

**M-10** — минутный лок держится 5с в фоне, суточный прогон одновременно: `0.542с`, `exit=0`, не
ждал, не падал.

**Суточный путь**: холодный старт фактов (`SENTRY_FACTS` на несуществующий путь) → `2/5 ok`,
предупреждение «факты недоступны». Боевой прогон на реальных данных → `5/5 ok`, отправлено `2/2`.

**Дайджест отказов доставки** — тот же `awk`-фильтр, что в скрипте, проверен отдельно на
сегодняшней и вчерашней строке: сегодняшняя проходит, вчерашняя (>24ч) корректно отсекается.

**Сквозной прогон реальным cron** (не мной вручную): состояние очищено, выждан один реальный тик
→ `/var/lib/biotact-sentry/state` создан ботом самостоятельно, `fail_count=0 alert_state=ok` —
подтверждает, что `/health` и `/api/v1/products?size=1` реально отвечают 200 на настоящем проде.

**Cold start минутного пути** — без state-файла: `exit=0`, стартовал с дефолтов.

## Само-ревью безопасности (DoD требовал ДО Гейта-2, не после — не спихиваю на тебя вопросом)

Скрипта в `git diff` нет — это ops на двух серверах, не PR. Прошёл вручную по тем же категориям:

- **Секрет**: `BOT_TOKEN` — 600 root:root, вне git. Радиус утечки — умеет только слать сообщения этим
  ботом; ни денег, ни БД, ни PII не открывает. `ADMIN_IDS` — telegram id, не секрет.
- **Новых путей доступа в прод — ноль** (весь смысл Push). bcv2 не получил ни новых портов, ни
  слушателей — только cron-триггеры.
- **Инъекции**: SQL-запрос статичный, без интерполяции пользовательских данных — инжектить нечего.
  `STATE_FILE`/`FACTS_FILE` — **раунд 3 читал их через `source` (RCE), это и был БЛОКЕР раунда 4**,
  теперь оба whitelist-парсером (`sed`, значение обязано целиком совпасть с `yes|no`/цифрами/`ok|error`),
  проверено атакой на себя (`disk_ok=yes; touch /tmp/PWNED…` не исполнился) — см. верх отчёта.
- **Facts-файл содержит меньше, чем дамп**: 6 полей вида `disk_ok=yes`, ни PII, ни секретов —
  едет тем же уже принятым риском (rrsync без шифрования, решение Капитана 18.08), не новым.
- **DoS**: `flock -n` не копит наложения, таймауты 5/10с ограничены, logrotate не даёт логу расти
  бесконечно.
- **Telegram**: `parse_mode` нигде не выставляется — целый класс инцидента 06.08 исключён архитектурно.

Известный компромисс, не блокер: сторож на bcv2 работает root'ом (нужно, чтобы читать
`biotact-backup:biotact-backup 700`-каталог facts-файла) — не сузил до отдельного пользователя,
соразмерно калибровке риска этой задачи (§0 спеки), не уровню прод-хардненинга.
