## Сделано — по пунктам спеки

- **`POST /api/v1/qr/activate`** (`src/loyalty/router.py`; смонтирован в `main.py` под `/api/v1/qr`).
- **Одна явная транзакция `async with db.begin()`** (`service.activate_code`): юзер резолвится/создаётся ВНУТРИ неё (FK-видимость нового юзера) → lazy-профиль `INSERT … ON CONFLICT DO NOTHING` → `SELECT customer_profile.lifetime_activations … FOR UPDATE` (per-user замок, читается ПОД локом) → атомарный claim `UPDATE qr_codes SET status='used',used_at,activated_by WHERE code=? AND status='generated' RETURNING id,product_id` → `get_unit_price` → INSERT cashback (+welcome) → Core-UPDATE счётчиков. Лок-ордер **профиль→код** (без дедлоков).
- **Кэшбэк 5%** (`NEWBIE_RATE_BPS=500`) + **welcome ×1.5 первая** (`WELCOME_RATE_BPS=250`, отдельная earn-строка). Снапшот `product_id`/`unit_price`/`rate_bps` на каждой строке (Q4), reconcile-совместимы.
- **Идемпотентность/гонки (Q5):** same-user replay → 200/0-начислений (пересборка из ledger); чужой → **409** generic; нет кода → **404**; партиал-`UNIQUE(qr_code_id,reason)` — DB-бэкстоп.
- **Гейт `loyalty_enabled`** (route-level dependency): false → **404 ДО auth**. initData-HMAC auth через `get_init_data_user` (переиспользует `validate_init_data`, без БД).

### Чего ты «ударишь» — закрыто

- **Гонка по-настоящему (не псевдо):** **`test_race_same_code_one_set_of_accruals`** + **`test_race_first_activation_grants_exactly_one_welcome`** — `asyncio.gather` + ДВЕ независимые сессии (2 коннекта) → реальная row-lock-контенция Postgres. **Мутационное доказательство (запускал):** убрал guard `status='generated'` из claim → same-code-гонка **ПАДАЕТ** (второй claim проходит → дубль `(qr_code_id,reason)` → `unique constraint "uq_point_ledger_qr_code_id_reason"` IntegrityError → одна корутина = exception → assert падает). Восстановил guard → зелёно. ⇒ тест ловит баг, не фейк-покрытие; партиал-UNIQUE реально бэкстопит. Итог корректного прогона: ровно 1 cashback + 1 welcome, второй = replay, без 500.
- **Атомарность tx (частичный сбой откатывает всё):** **`test_fractional_price_at_activation_returns_503_not_500`** (реальный путь, без monkeypatch): цена меняется на дробную ПОСЛЕ генерации → активация: claim проходит, потом `get_unit_price` бросает → весь `db.begin()` откат → код снова `generated`, **0 строк ledger** (не «used без баллов»). + **`test_pricing_failure_rolls_back_claim`** (monkeypatch `UnknownProductError`) — та же гарантия отката для missing/NULL-ветки.
- **welcome ×1.5 округление:** **`test_welcome_rounding_is_half_up_per_row`** — цена 20: cashback `compute_cashback(20,500)=1.0→1`, welcome `compute_cashback(20,250)=0.5→1` (ROUND_HALF_UP, в пользу клиента). Две ОТДЕЛЬНЫЕ строки, каждая округлена ОДИН раз (НЕ единый ×1.5 множитель). + границы .5 в `test_loyalty_ledger.py` (PR-2.1: 10010→501, 9990→500, 10→1).
- **FOR UPDATE scope:** `service.py` — `SELECT lifetime_activations … with_for_update()` → `lifetime_before` читается ПОД локом, до выбора ставки/welcome. Лок держится до коммита всей tx.

- **IDOR:** `activated_by = user_id` из auth-контекста (initData), никогда из тела. См. таблицу (replay/409).

## Отклонения от плана и почему

1. **Auth через НЕ-БД `get_init_data_user` (→ `TelegramUser`), не `CurrentUser`.** `CurrentUser→get_or_create_user` делает `flush` → транзакция уже открыта → литеральный `async with db.begin()` (спека §6) невозможен. Решение даёт ровно одну явную tx И FK-видимость lazy-юзера. Цена — ~10 строк локальной валидации initData (изолировано; вынос в `auth/dependencies.py` — позже, ради меньшего blast-radius денежного PR).
2. **Счётчики профиля — Core `UPDATE` (DB-time `func.now()`), не ORM-присваивание.** `func.now()` в ORM-атрибут не проходит `mypy --strict` + избегаем ORM/Core рассинхрона. Семантика идентична.
3. **🆕 Новый фикс по твоей falsification-таблице — `FractionalPriceError`→503 (был бы 500).** Дробная цена, выставленная админом ПОСЛЕ генерации QR, на активации бросала bare `ValueError`, который роутер НЕ ловил → **500** на денежном эндпоинте. Ввёл иерархию `PricingError` (база) ← `UnknownProductError` / `FractionalPriceError(PricingError, ValueError)`; роутер ловит `PricingError`→503. `(…, ValueError)` сохраняет старый тест PR-2.1 без правок. Это трогает `pricing.py` (файл PR-2.3a) — обоснованное in-scope упрочнение денежного пути (твоё «дробная цена → без 500»).
4. **Код ошибки непрайса — 503** (retryable). Спека код не фиксировала.

## /security-review — вердикт (мой Гейт-2-self-check; твой Гейт-2 = ты воспроизводишь сам)

**Чисто — 0 эксплуатируемых находок (≥0.8).** Независимый проход (security-reviewer-агент) + само-ревью по 7 векторам — каждый утверждение ниже верифицируемо (см. falsification-таблицу):
1. **Auth bypass** — `validate_init_data`: data-check-string без `hash`/`signature`, секрет `WebAppData`, `hmac.compare_digest` (timing-safe), 24h-expiry; `user.id` внутри подписи → подделать нельзя.
2. **IDOR/authz** — replay только `activated_by==user_id`; `get_balance` строго по auth `user_id`. Кросс-юзера нет.
3. **Money tampering** — клиент задаёт только `code`; ставки серверные, `product_id` из claimed-row, `unit_price` из `products.price` по PK.
4. **Гонки** — `FOR UPDATE` + атомарный claim + партиал-UNIQUE (мутационно доказано).
5. **Injection** — только bound-параметры SQLAlchemy.
6. **Info leak** — 409/503 generic, dark→404 до auth.
7. **Input** — `code` constrained (strip, 1–32) → мусор=404.

🟡 **Sub-threshold (НЕ находка, ~0.7) → решение Капитана (Вопрос 1):** активация не проверяет `user.is_active` (которую `get_current_user` гейтит как 403). `is_active=False` авто-ставится при блоке notification-бота (`broadcasts/service.py:285`) — флаг достижимости, не бан; вернувшийся покупатель по логике лояльности должен зарабатывать, тратить при inactive нельзя. Два прочтения → противоположное поведение → молча не выбираю.
