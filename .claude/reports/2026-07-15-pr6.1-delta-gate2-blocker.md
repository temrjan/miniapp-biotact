## Что сделано (4 механизма)

### 1. State-machine guard (`lifecycle.py`) — закрывает ГЛАВНЫЙ блокер
`_ALLOWED_FROM`: `success`/`error` применяются только из `{unpaid, pending}`, `revert` только из
`paid`. **Late error/revert на ОПЛАЧЕННЫЙ заказ отвергается по состоянию** — ровно ваш сценарий
(paid → late error → был failed). Плюс cancelled-заказ не воскрешается поздним success.
Мутация: снять guard → `test_cancelled_order_not_resurrected` red.

### 2. Attempt guard — но ТОЛЬКО для error/revert (важная поправка при реализации)
Изначально (`b200ddb`) сделал attempt-guard для ВСЕХ статусов. **Мутация вскрыла, что это
неверно:** тест на paid-заказе не краснел от снятия attempt-guard, потому что state-guard (п.1)
уже ловит late error на paid. Разобрал глубже — общий attempt-guard **вреден для success**:
поздний легитимный success по старой попытке (клиент оплатил A в зависшей вкладке) = реальные
деньги, а общий guard их бы отверг → потеря оплаты.

Итог (`1221478`): **attempt-guard только для `error`/`revert`**. Брошенная попытка A прислала
error — не трогаем заказ, по которому клиент ещё платит активной B. Success по любой попытке =
реальные деньги, применяется (по amount+state+trust). Тест изолирован на **pending**-заказе (где
state-guard НЕ подстрахует): late error по A на pending-по-B → остаётся pending. Мутация
attempt-guard → cancelled → red.

### 3. Trusted success (закрывает security-находку про неподписанный `status`)
Вы отметили: SHA1-вебхук не подписывает `status` → реплей валидного вебхука с подменой на
`success` = ложная оплата. **Закрыл без внешнего вызова:** `success` применяется ТОЛЬКО из
MD5-колбэка (`trust_success=True`); success из вебхука записывается для аудита, но заказ НЕ
оплачивает. У колбэка нет подменяемого поля status (это фиксированный success-эндпоинт), у
вебхука — есть, поэтому вебхуку success не доверяем. Мутация: доверять вебхуку → order paid → red.
- **Реплей error/revert-вебхука** нейтрализован комбинацией attempt-guard (не активная попытка) +
  state-guard (revert только из paid). Остаточный вектор — реплей revert по АКТИВНОЙ оплаченной
  попытке (ложный refund): требует MITM трафика Multicard-IP; `get_invoice_status`-подтверждение
  НЕ добавил (rules #3 — внешний вызов + обработка недоступности на денежном пути = отдельное
  решение). **Выношу как вопрос — см. ниже.**

### 4. TOCTOU в `create_payment` (`orders/service.try_arm_payment_attempt`)
Заменил слепой `update_order_payment` на **атомарный** `UPDATE … WHERE payment_status != 'paid'
RETURNING id`. Конкурентный success-колбэк в окне медленного вызова Multicard (30s) → arm
возвращает False → 400 «уже оплачен», заказ НЕ сброшен в pending. Мутация: снять `WHERE != paid`
→ клоббер paid → red. Добавил `except HTTPException: raise` в create_payment — иначе внешний
`except Exception` глотал бы 400 и отдавал 502.

## 🔴 БЭКЛОГ (ратифицировано Ревьюером — отдельный PR, НЕ в PR-6.1): реплей неподписанного `status`

Вебхук SHA1 не подписывает поле `status`, поэтому перехваченный валидный вебхук реплеится с
подменённым статусом. **Уязвимость симметрична для `error` И `revert`** (оба — вебхук-статусы),
формулирую оба, чтобы error-половина не потерялась в отдельном PR:
- **`revert`** по активной оплаченной попытке → ложный refund+cancelled (деньги реально не
  вернулись) — ущерб высокий (операционная путаница, заказ помечен возвращённым).
- **`error`** по активной попытке → ложный failed+cancelled на unpaid-заказе — ущерб низкий
  (просто откат в failed, денег не крадёт, клиент пересоздаст).

У `success` есть параллельный доверенный канал (MD5-колбэк), поэтому мы его закрыли
trust_success. У `error`/`revert` такого канала НЕТ — единственный полноценный фикс это
вторичное `get_invoice_status(uuid)` перед применением. Это внешний httpx-вызов на денежном пути
+ обработка недоступности Multicard = отдельное архитектурное решение (rules #3). Вектор требует
MITM трафика с Multicard-IP `195.158.26.90` — тот же IP, чей фильтр спека §6 отложила «обсудить
отдельно». **Рекомендация (ратифицирована): отдельный PR = IP-фильтр колбэка/вебхука + вторичное
`get_invoice_status`-подтверждение для error+revert** (одна тема «доверие к каналу»).
