## Находки

### МИНОР-1. «Причина в коде» не называет существующий третий путь отмены — а я уже сделал дешёвую проверку, которую плану стоит унаследовать

`payments/lifecycle.py:203-208` (`process_payment_event`, ветки `STATUS_ERROR`/`STATUS_REVERT`)
тоже переводит заказ в `CANCELLED` — по вебхуку/колбэку Multicard, а не по таймауту. Плановый
раздел «Причина в коде» этот путь не упоминает вовсе, из-за чего фраза «карточный заказ без баллов
не отменяет никто и никогда» — избыточно широкая: точнее «...если Multicard никогда не прислал по
нему ни одного события».

Я проверил это на живых данных: таблица `payment_event` — append-only лог ВСЕХ входящих событий
Multicard (идемпотентность пишется до применения статуса, значит там есть след любого колбэка,
даже отклонённого). Запрос по всем 69 текущим `PENDING`-заказам:

```
pending_orders_total | with_any_event
----------------------+----------------
                   69 |              0
```

Ни один зависший заказ не имеет ни одной строки `payment_event` — Multicard действительно никогда
ничего не присылал. Это **подтверждает диагноз плана независимо и с нулевым риском** (без единого
обращения к боевому Multicard). Практическое следствие для Ш1: локальную проверку `payment_event`
стоит сделать ПЕРВЫМ, бесплатным шагом Ш1 (она уже отвечает на «не получили ли мы событие, которое
не применили» — нет, не получали); живой `get_invoice_status` в Multicard остаётся нужен ТОЛЬКО для
второй части вопроса Ш1 («не потерян ли колбэк на стороне Multicard» — этого локальная таблица не
доказывает, отсутствие вебхука не исключает провала ДОСТАВКИ вебхука).

**Внести в спеку:** (а) строка в «Причина в коде» про существующий вебхук-путь отмены (для точности
формулировки и как ответ на собственный вопрос плана «не появилось ли второй отмены» — она уже
есть, безопасна по конструкции: обе отмены — условные атомарные `UPDATE` с одинаковым `WHERE
payment_status IN ('unpaid','pending')`, Postgres сериализует конкурентные `UPDATE` тем же row-lock,
гонки нет); (б) Ш1 начинается с запроса `payment_event` по выборке (готово, результат выше), и
только для явно интересных случаев (у которых окажется расхождение) — живой Multicard-вызов.

### МИНОР-3. Не сказано, меняется ли гейт `orders/router.py:54-56` вместе со снятием внутреннего фильтра

Ш2 снимает `Order.points_applied > 0` ВНУТРИ `expire_stale_partials`. Но реактивный вызов на
