## 2. 🔴 Два дефекта, найденных на исполнении

### 2.1 Билет за покупку выдавался тому, кто ничего не покупал

Первый прогон матрицы **покраснел**: пригодный новичок получал `survey` **и** `activation`. Причина —
я выдавал билет за покупку по СОСТОЯНИЮ («нет чистого билета этого источника»), а он зарабатывается
СОБЫТИЕМ. Состояние не знает, что покупка была.

**Исправлено:** `sources` по умолчанию — только состояние-производные (`survey`, `friend`);
`activation` обязан запрашиваться явно, и просит его единственный вызывающий, который видел покупку.
Безопасное стало умолчанием.

### 2.2 Три мутации из шести ничего не доказывали

Первый мутационный прогон: **M3, M5, M6 остались зелёными**. Разбор каждой — это дефекты моих
тестов, а не кода:

| Мутация | Почему тест не краснел | Что сделано |
|---|---|---|
| **M3** снять потолок | тест звал выдачу с источниками по умолчанию, где `activation` нет — третьему билету взяться неоткуда | тест зовёт путь, который **может** выдать третий |
| **M5** снять замок | обе активации уже сериализованы **внешним** замком `activate_code`; внутренний там не нагружен | заменён на детерминированный тест: держим замок в другой сессии, `lock_timeout`, выдача **обязана** заблокироваться |
| **M6** бэкфилл даёт `activation` | участник-«Друг» упирался в потолок раньше, чем дошло бы до третьего источника | участник-новичок, слот свободен |

По M5 отдельно: сначала я написал гоночный тест «бэкфилл против активации» — он **тоже** остался
зелёным, потому что бэкфилл каждый раз успевал закончиться первым, и нужного пересечения не
возникало. Гоночные тесты доказывают что-то только когда проигрывают. Поэтому свойство проверяется
прямо: замок держат снаружи, выдаче дают короткий `lock_timeout` и требуют, чтобы она встала.

### EXPLAIN — долг шага 1 закрыт, на объёме

Загружено **20 001 билет, из них 100 чистых** (иначе план ничего не доказывает — на пустой таблице
PostgreSQL выберет что угодно):

```
EXPLAIN (ANALYZE, COSTS OFF)
SELECT source FROM lottery_tickets WHERE user_id = 20001 AND draw_id IS NULL;

 Index Scan using ix_lottery_tickets_clean_user on lottery_tickets (actual rows=1 loops=1)
   Index Cond: (user_id = 20001)
```

Размеры: **частичный `ix_lottery_tickets_clean_user` = 16 kB** против полного
`ix_lottery_tickets_user_id` = **456 kB**. В 28 раз меньше — ровно то, ради чего он частичный.

### Замер транзакции активации

| | медиана | среднее |
|---|---|---|
| БЕЗ выдачи (базовая) | 14.22 мс | 15.74 мс |
| С выдачей | **19.11 мс** | 20.05 мс |
| дельта | **+4.89 мс (+34.4%)** | |

Первый замер дал **+6.11 мс (+43.7%)**: выдача делала четыре round-trip'а, два из которых —
отдельные запросы «что заработано когда-либо» и «что не сыграло». Оба отвечаются одними и теми же
строками, поэтому схлопнуты в один запрос — **−1.2 мс удержания замка на каждую активацию**.

⚠️ Оставшиеся +4.89 мс — это лишний `SELECT` профиля (ре-ентерабельный `FOR UPDATE`) плюс `SELECT`
билетов и `INSERT`. Убрать повторный `SELECT` профиля можно, только отдав замок на совесть
вызывающего, а это ровно то, что запретил Гейт-1. Плата принята сознательно.

## 4. Чего тесты НЕ покрывают

- **Частичный индекс** — влияет на план, а не на поведение; проверен `EXPLAIN` (см. выше), теста нет
  и не будет.
- **Согласованность SQL-детектора с Python-предикатами.** Детектор `eligible_without_survey_ticket`
  выражает `has_survey`/`is_adult` в SQL, потому что агрегат не может звать функции построчно. Это
  реальное дублирование правил. **Тест на согласие двух формулировок я НЕ написал** — спека его
  предполагала, и это мой недобор. Предлагаю добавить его первым делом в шаге 3, где предикаты
  всё равно будут трогаться.
