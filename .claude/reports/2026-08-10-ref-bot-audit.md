# Аудит `ref-bot` — отдельный проект на проде

**Инженер · 2026-08-10.** Вид задачи: Аудит (результат — отчёт, кода нет). Границы согласованы
Капитаном: что делает · работает ли · не засоряет ли · безопасность · соседство с основным проектом.
**Режим: только чтение.** Ничего не перезапускалось, не менялось, не удалялось.

Все факты получены на живом сервере в этом прогоне. Значения секретов в отчёт не переносятся.

## 1. Что это

**Реферальный бот для сотрудников BIOTACT, маркетинговая кампания «Рамадан 2026».**
[@BiotactRefBot](https://t.me/BiotactRefBot), `/var/www/biotact/packages/ref-bot/`, PM2-процесс
`ref-bot`. Стек: Python 3.12, aiogram 3, SQLAlchemy async, long polling (портов не занимает).

Схема работы (из README и кода):
```
Админ  → /generate 50 → инвайт-ссылки
Сотрудник → по ссылке → вводит имя → получает персональный QR
Клиент → сканирует → t.me/BiotactBot?start=ref_CODE → мини-апп → покупка
Сотрудник → /stats → переходы, покупки, сумма
```

## 2. Работает ли — процесс да, кампания нет

**Процесс жив:** PM2 `online`, uptime ~4 месяца, поллинг Telegram работает (в логах цикл
«timeout → Connection established», токен принимается). Свои тесты: **14 прошли, 1 упал**.

**Кампания мертва:**

| Показатель | Значение |
|---|---|
| Сотрудников зарегистрировано | 60 (последний — **16.02.2026**) |
| Инвайтов | 3 |
| Переходов по кодам (`users.referral_code`) | 121, последний — **12.03.2026** |
| Заказов с кодом | 6 |
| Помесячно | дек 4 · янв 9 · фев 82 · мар 26 · **дальше ноль** |

**И это не просто затишье — путь записи разорван.** Обход по всему дереву
(`packages/api/src`, `packages/bot`, `packages/frontend/src`) даёт **ноль** мест, где
записывается `users.referral_code` / `orders.referral_code`, и ноль обработчиков параметра
`ref_`. Единственный код, который эти колонки хотя бы читает, — мёртвая папка
`packages/api/src/referrals/` (вне git, никем не импортируется).

**Практический вывод:** если сотрудник покажет свой QR сегодня, переход **не будет засчитан** —
некому. `/stats` продолжит показывать замороженные февральско-мартовские числа, и это выглядит
как рабочий отчёт, а не как отказ. Это главная находка аудита.

## 3. Засоряет ли — операционно нет, архитектурно да

**Операционно — чисто:**
- **Логи:** единицы килобайт в день, ротация по дням настроена, `error.log` пуст (0 байт).
- **Соединения с общей БД:** 2 idle. Пула не держит, чужие лимиты не ест.
- **Диск:** 125 МБ, из них **124 МБ — `venv`**; собственный код ~1 МБ.
- **Cron:** записей нет.
- **Порты:** не слушает (long polling).

**Архитектурно — постоянная плата основного проекта:**
- Бот **делит БД** с основным API (`biotact_db`) и владеет двумя таблицами: `referrers` (60),
  `referral_invites` (3).
- Миграция `8efc0a708641_add_referral_system.py` живёт **в главном репозитории** и добавляет
  колонки `referral_code` в `users` и `orders` — то есть чужой проект расширил основные таблицы.
- `packages/api/alembic/env.py` содержит **явный список исключений** (`_REF_TABLES`,
  `_REF_INDEXES`, фильтр по колонке `referral_code`), чтобы гейт паритета миграций не пытался
  снести чужое. Это аккуратно сделано и прокомментировано — но это навсегда взятая сложность
  ради проекта, который сейчас не работает.

**Граница данных при этом чистая, и это к чести автора:** бот пишет **только в свои** таблицы
(`session.add` встречается лишь для `Referrer`/`ReferralInvite`), а `users` и `orders` —
исключительно читает (`select/count/sum` в `services.py`).

## 4. Безопасность

**Хорошо:**
- **Свой токен Telegram** (`8231095234`), отличный от мини-апп-бота (`7748404469`) и уведомителя
  (`8175184075`) — компрометация одного не тянет остальных.
- `.env` — права `-rw-------`, владелец `root:root`. Как у основного API.

**Требует внимания:**
- **Ходит в БД под тем же пользователем `biotact`, что и основной API** — то есть имеет полный
  доступ ко всей базе, включая заказы, платежи и лоялти, хотя ему нужны свои две таблицы плюс
  чтение `users`/`orders`. Отдельная роль с узкими правами была бы соразмернее.
- ⚠️ **Пароль БД лежит открытым текстом** в `/var/www/biotact/backups/backup.sh`
  (`PGPASSWORD=...`). Это скрипт основного проекта, не бота, но пользователь — тот же.
  **Отдельно предупреждаю: значение попало в вывод моей сессии, когда я читал скрипт.**
  Рекомендую ротацию пароля независимо от решения по боту.

## 5. Непрерывность — самое уязвимое место

- **Своего git у бота нет** (`.git` отсутствует, origin не существует, истории нет).
- В git основного проекта он тоже не входит — подтверждено `git ls-files`.
- В `ecosystem.config.js` основного проекта **не прописан** — поднимается независимо.
- **Бэкап покрывает только БАЗУ:** `backup.sh` делает `pg_dump` и `gzip`, файлов не архивирует
  (проверено: `tar`/`rsync`/`cp -r` в скрипте — ноль вхождений).

**Итого:** данные бота переживут потерю сервера (они в дампе БД), **исходный код — нет**.
Он существует ровно в одном экземпляре, на одной машине, без истории изменений.

## 6. Дефект в тестах бота (мелочь, но классифицирую точно)

`tests/test_handlers.py::TestCmdTop::test_admin_empty_leaderboard` падает:
`TypeError: float() argument must be ... not 'coroutine'`.

**Это дефект теста, не бота.** Прод-код корректен: `admin.py:27` делает
`entries = await get_leaderboard(session)`. Тест подменяет асинхронную функцию обычным моком
(`return_value=[]` вместо `AsyncMock`), поэтому в обработчик приезжает корутина. Команда `/top`
в бою работает.

## Рекомендации — по убыванию цены бездействия

**1. Решить судьбу кампании (ТВОЙ ВЫБОР — бизнес, не техника).**
Кампания не работает пять месяцев и структурно сломана. Три варианта:
- **Похоронить:** остановить процесс, данные оставить в БД (они уже в бэкапах). Освобождает
  память сервера и снимает вопрос «почему статистика не растёт».
- **Оживить:** вернуть запись `referral_code` в мини-апп/API. Это отдельная работа с полным
  кругом — путь записи придётся написать заново, его в дереве нет.
- **Оставить как есть:** дёшево, но бот продолжит показывать замороженные числа как рабочие.

*Моя рекомендация — похоронить или оживить, но не «оставить как есть»:* отчёт, который выглядит
рабочим и не обновляется, хуже отсутствующего — ровно тот класс, на котором проект уже горел
(мёртвый гейт CI, стейл-зелёное).

**2. Ротировать пароль БД** (`backup.sh`, открытый текст, попал в вывод сессии). Не зависит от
решения по боту.

**3. Если бот остаётся жить — положить исходники в собственный репозиторий.** Сегодня потеря
сервера = потеря кода навсегда.

**4. Удалить с прода мёртвую `packages/api/src/referrals/`** — 4 файла февраля, ноль импортов.

**5. Починить падающий тест** (одна строка: `AsyncMock` вместо `Mock`).

# Дополнение — голосовая реализация (вводная Капитана после сдачи отчёта)

Капитан указал, что «у этого бота есть голосовая реализация, там агент разговаривает голосом и это
красиво визуализировали». Проверил, а не согласился на слово.

## В `ref-bot` голоса НЕТ

Обход `refbot/` по `voice|speech|tts|stt|whisper|audio|elevenlabs|realtime` — **ноль вхождений**.
Голосовая часть к этому боту не относится.

## Что найдено вместо этого: `/opt/voice-service`

Отдельный сервис, **вне обоих известных мест** (`/var/www/biotact` и `/opt/bots`), поэтому в
основной аудит не попал. По README — «universal STT/TTS microservice for all Biotact projects»:
распознавание речи (GigaAM-v3 ONNX, CPU) и синтез (Silero бесплатный / OpenAI премиум),
самохостинг, публичная точка заявлена как `https://voice.biotact.uz`.

**Устроен заметно лучше `ref-bot`** — и это стоит сказать прямо:

| | `ref-bot` | `voice-service` |
|---|---|---|
| Свой репозиторий | нет вообще | **есть**: `git@github.com:temrjan/voice-service.git` |
| CI | нет | каталог `.github/` присутствует |
| Docker | нет | `Dockerfile` + `docker-compose.yml` |
| Документация | README | README + `CLAUDE.md` |
| Здоровье | — | healthcheck, контейнер `(healthy)` |

Риска «код существует в одном экземпляре» здесь **нет** — в отличие от `ref-bot`.

## Но по существу он простаивает

| Показатель | Значение |
|---|---|
| Аптайм контейнера | **4 месяца**, статус `healthy`, `/health` → 200 |
| Строк в логе за всё время | **432 292** |
| Из них РЕАЛЬНЫХ обращений (`transcribe`/`synthesize`) | **8** |
| Память | **1.27 ГиБ** постоянно (при 2.6 ГиБ занятых на всей машине — примерно половина) |
| Образ | **3.75 ГБ** (диск не проблема: занято 29 из 193 ГБ) |
| Лог контейнера | **55 МБ**, растёт без ограничения |

**Ротации docker-логов нет:** `/etc/docker/daemon.json` отсутствует, значит лимит размера не задан
и лог будет расти бесконечно (~165 МБ в год при текущем темпе). Сам по себе не страшно, но это
единственная неограниченная величина, которую я на сервере нашёл.

**Главная диспропорция:** 1.27 ГиБ памяти держится постоянно ради восьми обращений за четыре
месяца. Причём 99.99% лога — это собственные проверки здоровья, то есть сервис в основном
разговаривает сам с собой.

## Где «красивая визуализация» — на этом сервере её нет

Заявленные в README потребители — **AskBiotact (bcv2)** и **event-reg-bot** — на этой машине
отсутствуют: поиск по `/opt`, `/var/www`, `/root`, `/home` дал только тренировочный скрипт
`/opt/biotact-core-v2/finetuning/train_askbiotact_model.py` и текстовый файл в `/root`. Ни одного
вызова `voice.biotact.uz` или `voice-service` из кода на этом сервере нет.
Nginx здесь отдаёт только `admin.biotact.uz` и `app.biotact.uz` — домена `voice.biotact.uz` в его
конфигурации нет.

**Вывод:** визуализированный голосовой агент живёт не здесь. Где именно — вопрос Капитану;
гадать не буду.

## Что это добавляет к рекомендациям

**6. Решить судьбу `voice-service` — отдельно от `ref-bot`.** Восемь обращений за четыре месяца
при постоянной 1.27 ГиБ памяти. Если потребители переехали на другой сервер, здесь он просто
греет воздух; если ещё понадобится — вопрос снимается. **Моя рекомендация:** выяснить, кто его
реально зовёт, прежде чем что-либо останавливать — сервис общий, и остановка ударит по чужому
проекту, которого я не вижу.

**7. Включить ротацию docker-логов** (`/etc/docker/daemon.json`, `log-opts: max-size/max-file`).
Дешёво, разово, снимает единственную неограниченно растущую величину.
