### 2. Root пускают по паролю с интернета
`sshd -T`: `permitrootlogin yes`, `passwordauthentication yes`; `passwd -S root` = **P** (пароль
установлен). За 24 ч — **68** попыток подбора пароля root, fail2ban забанил **8315** адресов за всё
время. При этом **все наши входы за 7 дней — только по ключу** (151 × `publickey root`), пароль никому не
нужен. ⚠️ Ловушка порядка: `sshd_config` подключает `sshd_config.d/*.conf` **первым**, а sshd берёт
**первое** встреченное значение — `50-cloud-init.conf` и `60-cloudimg-settings.conf` (оба
`PasswordAuthentication yes`) идут раньше `hardening.conf`, поэтому правки только в `hardening.conf`
для `PasswordAuthentication` **не сработают**; `PermitRootLogin yes` в `hardening.conf` перебивает
`prohibit-password` из основного файла.
**Чинить:** файл `/etc/ssh/sshd_config.d/00-hardening.conf` (сортируется первым) с
`PasswordAuthentication no` · `PermitRootLogin prohibit-password` · `KbdInteractiveAuthentication no`;
`sshd -t`; `systemctl reload ssh`; **проверить вход из нового окна, текущую сессию не закрывать**;
`sshd -T | grep -E "permitrootlogin|passwordauthentication"` для доказательства. Деплой (`github-actions-deploy`,
ключ) не затрагивается.

## 🟠 Важно

### 3. Защита админ-логина от перебора обходится подменой заголовка
`admin_router.py:127-136` берёт IP из **первого** элемента `X-Forwarded-For`; nginx ставит
`X-Forwarded-For $proxy_add_x_forwarded_for` — **дописывает** реальный IP к присланному. Атакующий шлёт
`X-Forwarded-For: 1.2.3.4` (меняя значение) → лимит считается на выдуманный IP → перебор общего
`ADMIN_PASSWORD` без ограничений. Rate-limit есть только в коде (в nginx `limit_req` нет), fail2ban
следит только за `sshd`.
**Чинить (одна строка nginx, без кода):** `proxy_set_header X-Forwarded-For $remote_addr;` в
`/etc/nginx/sites-enabled/biotact` (перезаписывать, не дописывать); `nginx -t && systemctl reload nginx`;
проверка `curl -H "X-Forwarded-For: 1.2.3.4"` на логин → лимит срабатывает по реальному IP.
Альтернатива в коде — брать `X-Real-IP` (nginx его всегда перезаписывает).

### 4. Автообновления выключены — ✅ РЕШЕНИЕ КАПИТАНА, не дефект (уточнено 18.08)
`APT::Periodic::Update-Package-Lists "0"` + `APT::Periodic::Unattended-Upgrade "0"` — **выключены
сознательно Капитаном** (совместная сессия, конец января 2026), чтобы обновления шли **контролируемо**:
на сервере платёжный шлюз и боевая БД, и внезапный рестарт `postgresql`/`nginx` от автообновления
недопустим. Снимаю с себя пункт как «дефект»; не поднимать повторно (правило «Captain owns ops
housekeeping»).

**Фактическое состояние (для планирования ручного окна, не как претензия):**
последняя установка пакетов — **2026-01-29**, последний прогон `unattended-upgrade` — 2026-01-28
(`/var/log/apt/history.log*`); на 18.08 в очереди **204 обновления, 151 security** (`libc6`,
`python3.12`, `nginx`, ядро `6.8.0-106 → -138`), аптайм 153 дня. На `bcv2` — 64 обновления, работает
ядро `-94` при установленном `-137`, висит `reboot-required`.

⚠️ Важно: вчерашняя запись «сейчас обновлений 0» была **ошибкой пробы** — `apt list --upgradable`
выполнялся без `apt-get update`, а списки не обновляются автоматически именно из-за
`Update-Package-Lists = 0`. Тот же класс, что «бэкапов нет».

**Процедура ручного окна (по слову Капитана):** `apt-get update` → `apt-get -s upgrade` (симуляция:
показывает список и какие службы перезапустятся) → согласование списка → `apt-get upgrade` →
перезагрузка ради ядра (автозапуск PM2/nginx/PG/redis/docker проверен) → проверка health и PM2.
