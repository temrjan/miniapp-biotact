## Сделано — по пунктам спеки

- **`POST /api/v1/loyalty/consent`** (`router.py`, на `summary_router` → уже смонтирован под `/api/v1/loyalty`; `main.py` не тронут). Гейт `require_loyalty_enabled` (404 до auth) + `get_init_data_user` (initData-HMAC, без БД) — как у activate. Тело `ConsentRequest{source: qr|direct}`, ответ `ConsentResponse{consent_recorded, joined, phone_shared}`.
- **`service.record_consent`** — одна явная `async with db.begin()`; юзер резолвится/создаётся ВНУТРИ (FK-видимость lazy-юзера). Порядок: профиль `ON CONFLICT DO NOTHING RETURNING id` → `joined`-если-вставил → `customer_profile FOR UPDATE`-лок → `registration_source` COALESCE (ставится один раз) → `data_processing` consent идемпотентно (только если нет действующей: `granted AND revoked_at IS NULL`) → `phone_shared` идемпотентно (guard: `users.phone_verified_at IS NOT NULL` и нет прежнего `phone_shared`).
- **`joined` на ОБОИХ путях (МИНОР-1):** в `activate_code` профиль-инсерт получил `.returning(CustomerProfile.id)`; при реальной вставке пишется `joined` (payload `{registration_source: null}` — activate не знает источник). Инвариант «`joined` = транзакция-вставки профиля» держится и у consent, и у activate; клиент с активацией-без-consent не теряет `joined`.
- **`qr_activated`** — в `_accrue` (достижим только на реальном claim → `ACTIVATED`), payload `{qr_code_id, product_id, points_awarded}`, в транзакции claim'а. НЕ на replay (`_resolve_unclaimed` ничего не пишет), НЕ на conflict/not-found (raise → откат всей tx).
- **Идемпотентность на повтор:** второй consent тем же юзером не пишет ничего, возвращает all-False.
- **Код нигде не логируется:** consent-путь кода не касается; в payload — только `qr_code_id`/`product_id` (int).
- **`registration_source`** — `qr`/`direct` из тела, COALESCE (первый писатель побеждает; activate-first backfill'ится последующим consent).

## Замечено, не трогаю — вне скоупа (предложить отдельной задачей)
- **`get_or_create_user` не race-safe на вставке brand-new юзера** (SELECT→INSERT без ON CONFLICT) — пред-существующее, общее для всех эндпоинтов; в бот-первом потоке юзер создан до мини-аппа. Тот же коммент уже стоит в `activate_code`.
- **`FOR UPDATE`-лок consent транзитивно дублируется** UPDATE'ом строки `users` внутри `get_or_create_user` (он всегда апдейтит имя → row-lock сериализует одного юзера). Лок оставлен как **явный defense-in-depth** (корректный self-documenting guard, не завязанный на побочный UPDATE; тот же паттерн, что в `activate_code`). Детали — в разделе мутаций ниже.
- **Предсуществующие lint-замечания в `tests/test_loyalty_activation.py`** (PT018 на строках 310/394 — `assert ... and ...`) — не мои строки; CI линтит только `src/` (`ruff check src/`), тесты не линтятся. Не трогал (rules #11).

## Отклонения от плана и почему
1. **Форма `ConsentResponse` = `{consent_recorded, joined, phone_shared}`** (booleans) — спека форму не фиксировала; выбран дефолт из Гейт-1-плана (идемпотентность наблюдаема/тестируема; карта — через `GET /loyalty/me`). Капитан по форме не возразил.
2. **Версия consent = константа `DATA_PROCESSING_CONSENT_VERSION = "1.0"`** — поле `Consent.version` обязательно, дефолта в коде не было. Тест пинит литерал "1.0".
3. **`RegistrationSource` — StrEnum** (не `Literal`) — единообразие с `ActivationStatus`, ноль magic-строк; в БД/payload пишется `.value` (plain str, без StrEnum-сюрпризов в JSONB/asyncpg).
4. **Эндпоинт назван `submit_consent`** (не `record_consent`) — чтобы имя эндпоинта ≠ имени сервиса (конвенция: `activate_qr`→`activate_code`).
5. **2 предсуществующих friend-flip теста** (`…earns_8pct…`, `…race_at_boundary…`) считали ВСЕ `CustomerEvent` (когда существовал только `status_friend`). Мой PR добавил события → счётчик вырос. Ассерты сужены до `event_type == STATUS_FRIEND` (исходный смысл «один флип / нет флипа» сохранён). Прямое следствие изменения, в скоупе.

## Security-relevant surface для Ревьюера (Гейт-2)
- **Auth/dark-gate:** `/consent` под `require_loyalty_enabled` (404 до auth) + `get_init_data_user` (HMAC). `user_id` строго из валидированного initData.
- **Деньги/гонки:** трогаю денежный `activate_code` — добавлены только append-события (`joined`/`qr_activated`) в существующей tx; начисления/лок/claim не менял. Откат tx убирает события-сироты (тесты conflict/not-found).
- **PII:** `phone_shared` пишется по `users.phone_verified_at` (ставит бот); consent-эндпоинт номер не принимает/не логирует.
- **Идемпотентность:** consent-дедуп + `phone_shared`-guard + `joined`=insert-winner; мутационно доказаны (см. выше).
