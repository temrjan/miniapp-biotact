## Главное доказательство: дыра была воспроизведена ДО фикса

Красная проба «наоборот» на реальном HTTP-слое, пользовательский токен `type="access"` против
семи админских поверхностей — **все семь пропустили**:

| поверхность | user `access` | admin |
|---|---|---|
| `GET /api/v1/admin/orders` | **200** ← полный список заказов | 200 |
| `DELETE /api/v1/products/999999` | 404 | 404 |
| `DELETE /api/v1/banners/999999` | 404 | 404 |
| `DELETE /api/v1/categories/999999` | 404 | 404 |
| `POST /api/v1/uploads/products` | 422 | 422 |
| `PATCH /api/v1/orders/999999/status` | 422 | 422 |
| `PUT /api/v1/settings/some_key` | 405→**422** (см. ниже) | 422 |

**Контроль, без которого таблица ничего не значит:** мусорный токен даёт **401 на всех семи**.
Значит 404/422 у валидного пользовательского токена — это «пропущен, упал дальше», а не «отказ».
Контроль встроен в постоянный тест, а не остался разовой проверкой.

⚠️ **Проба вскрыла дефект в моём же тесте.** Для `settings_router` я взял `PATCH /settings/{key}` и
получил 405 — «метод не разрешён», то есть отказ маршрутизации, а не прохождение авторизации. Тест
был бы зелёным по неверной причине. Настоящий метод — `PUT` (`banners/router.py:139`), исправлено;
после правки поверхность честно отвечает 422 и попадает под контроль.

  чужой секрет И **админский ключ с `type="access"`**. Второй случай ловит будущее «давайте
