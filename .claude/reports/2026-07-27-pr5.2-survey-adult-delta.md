## 1. МИНОР-1 — сообщение об успехе больше не переобещает ✅

`SurveyCard.tsx`: строка выбирается по тому, что **сервер реально записал** — по
`updated_fields` из ответа, а не по локальному состоянию формы.

```tsx
{survey.data.updatedFields.some((field) => field !== 'is_adult')
  ? t('survey.success')       // «Спасибо! Анкета сохранена.»
  : t('survey.adultSaved')}   // «Спасибо! Подтверждение сохранено.»
```

Почему по ответу сервера, а не по `payload`: ответ — это факт записи, payload — намерение.
Заодно фронт и бэкенд начинают отвечать одним и тем же признаком («что записано этим вызовом»).

i18n: `survey.adultSaved` — RU «Спасибо! Подтверждение сохранено.» · UZ «Rahmat! Tasdiq saqlandi.»

Тесты — обе ветки: одна галка → «Подтверждение сохранено» (и явная проверка, что строки
«Анкета сохранена» НЕТ); галка вместе с городом → «Анкета сохранена».

## 2. Q3 — классификация полей переехала к схеме ✅

`DEMOGRAPHIC_SURVEY_FIELDS` перенесён из `service.py` в `schemas.py`, рядом с `SurveyRequest`
(владелец списка полей). Рядом появился `NON_DEMOGRAPHIC_SURVEY_FIELDS = {"is_adult"}`.
Сервис импортирует, локальной копии нет (ruff-хук поймал дубль на переносе — F811, снял).

Вычитание не используем — по твоему обоснованию, дословно записанному в комментарий: производная
`set(model_fields) - {"is_adult"}` молча записала бы будущую галку «Правила акции» в демографию и
воскресила бы баг воронки.

Пиннинг-тест `test_survey_field_classification_is_exhaustive`:
```python
assert set(SurveyRequest.model_fields) == (DEMOGRAPHIC_SURVEY_FIELDS | NON_DEMOGRAPHIC_SURVEY_FIELDS)
assert DEMOGRAPHIC_SURVEY_FIELDS.isdisjoint(NON_DEMOGRAPHIC_SURVEY_FIELDS)
```
Второй assert — сверх твоего предложения: ловит поле, по ошибке записанное в ОБА множества
(тогда первый assert остался бы зелёным).
