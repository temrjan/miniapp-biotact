## Сделано — по пунктам спеки (§PR-6.3)

1. **`POST /orders` принимает `payment_method: 'card' | 'points'`, дефолт `'card'`**
   (`orders/schemas.py`). Старые клиенты поле не шлют → падают в `card`; существующий путь
   не изменён ни на байт (регресс-тест параметризован: поле отсутствует / явный `card`).
2. **Путь `points` — одной транзакцией** (транзакция = HTTP-запрос: `get_db` коммитит в конце,
   любой raise откатывает всё; ровно так уже работает 422-путь):
   - цена считается сервером по каталогу (`_price_lines`, как с #79);
   - `SELECT customer_profile … FOR UPDATE` — **тот же per-user замок, что держит начисление**
     (`activate_code`), поэтому redeem не может переплестись ни с начислением, ни с другим
     redeem (`loyalty/service.redeem_points`);
   - баланс < total → `InsufficientPointsError` → **409** c `{error, balance, required,
     deficit}` — фронту PR-6.4 есть из чего показать «не хватает N»; **ничего не записано**
     (доказано тестом по закоммиченному состоянию);
   - хватает → строка леджера `reason='redeem'`, `amount=−total`, `order_id`; заказ
     `points_applied=total`, `payment_status='paid'`, `status=CONFIRMED`, `paid_at`;
   - уведомление в группу — **та же заявка, что после оплаты**, шапка «ОПЛАЧЕНО БАЛЛАМИ» +
     строка «Списано баллов: N» (`notify_payment_success(points_applied=…)`); сбой уведомления
     заказ не роняет (паттерн payments-роутера).
3. **Multicard не вызывается вовсе.** `POST /payments/create` на такой заказ → **400** — ловит
   СУЩЕСТВУЮЩИЙ гард `payment_status == "paid"` (payments/router.py:57); код там не менялся,
   поведение пришпилено тестом.
4. **Дробный `total` → отказ 422, не округление** [Гейт-1 МИНОР-2]:
   `TotalNotPayableWithPointsError` (подкласс `OrderValidationError` → существующий маппинг
   422). Тест сидит `price=1000.50` прямо в БД мимо админ-валидации.
5. **`OrderResponse.points_applied`** — эхо колонки (нужно фронту 6.4 и админке 6.5).

## Сверх спеки (одно, объявляю явно)

- **`total <= 0` → тот же отказ 422 для points** (внутри `_points_total`). Основание: карточный
  путь ловит нулевой заказ гардом инвойса (`payments/create` → 400), у баллов инвойса НЕТ —
  без гарда нулевая цена из-под руки (import/restore) давала бы бесплатный заказ со штампом
  «paid». Тот же класс защиты, что `NonPositivePriceError` на earn-стороне (rules #6 — граница
  с БД). Тест есть. Не согласен — уберу, одна строка.

## Отклонения от плана и почему

- Замок берётся не «шагом 1», а внутри `redeem_points` после flush заказа (нужен `order.id`
  для строки леджера). Проверка-и-списание целиком под замком — гарантия спеки не ослаблена,
  race-тест с мутацией это доказывает.

  не предписывала; у активации PricingError → 503 «retryable», но здесь retry не поможет, а
  карточная оплата того же заказа работает — 422 честнее для клиента). Микро-дефолт, легко
  сменить.
- `/review`-флот в само-ревью НЕ гонял — указание Капитана в сессии: флот и секьюрити — у
  Ревьюера (флот `model: sonnet`). Само-ревью = дифф от и до + гейты + мутации + чек секретов
  (в диффе только тестовый фейк-токен, тот же что в соседних сюитах).
- Стандарты Codex `fastapi.md`/`python.md` не грузил (дублируют persona-KB `/python`
  CORE+fastapi) — контекст-бюджет; testing/postgresql/architecture/pipeline загружены.
