# Biotact Club — ориентир по проекту

Программа лояльности/оцифровки покупателя, встроенная в этот монорепо (`miniapp-biotact`).
Если вы открыли этот файл через год и не помните контекст — начните отсюда.

## Бренд vs код — самое важное для навигации

**В коде программа называется `loyalty`, а не `club`.** «Biotact Club» — это только
бренд/маркетинговое название, используемое в UI-текстах, докстрингах и документации.
Поиск `grep -ri club` по бэкенду/фронтенду не найдёт почти ничего — ищите `loyalty`.

## Что это

Уникальный QR-код на упаковке товара → сканирование ведёт в Telegram-бота → бот забирает
телефон и открывает мини-апп → мини-апп активирует код: кэшбэк баллами, профиль клиента,
статус «Друг BIOTACT» после 10 активаций, трата баллов на кассе, в будущем — ежемесячный
розыгрыш. Полное бизнес-описание и визуальный прогресс — в [`concept.html`](./concept.html)
(открыть в браузере).

## Это НЕ отдельный проект

Club не вынесен отдельным сервисом/репозиторием — это фича, встроенная в 4 существующих
пакета `miniapp-biotact`, по тем же конвенциям, что и остальной код репо. Так сделано
осознанно: лояльность держится в собственных таблицах рядом с `users`, не трогая модель
бота и остальной мини-апп (см. «Архитектурные решения» ниже).

| Пакет | Путь | Что там |
|---|---|---|
| API (FastAPI) | `packages/api/src/loyalty/` | Все таблицы и бизнес-логика: `models.py` (Consent, CustomerProfile, CustomerEvent, PointLedger, CodeBatch, QrCode), `service.py` (активация, начисление, трата баллов — вся денежная логика), `router.py` (`POST /api/v1/qr/activate`, `GET /api/v1/loyalty/me`, консент, анкета), `pricing.py`, `codes.py` (генерация партий QR) |
| Bot (aiogram) | `packages/bot/bot/handlers/loyalty.py` | Ловит deeplink `qr_<code>` и обычный `/start`, забирает телефон, открывает мини-апп. В лоялти-таблицы **не пишет** — только запускает мини-апп |
| Mini App (React) | `packages/frontend/src/api/loyalty.ts`, `components/features/Loyalty*.tsx`, `hooks/useLoyalty.ts`, `pages/ActivationPage.tsx`, `pages/CheckoutPage.tsx` (трата баллов), `pages/ProfilePage.tsx` (карточка лояльности) | Все CRM/лоялти-записи пишутся отсюда, под Telegram initData |
| Admin (React) | `admin-panel-v2/src/features/loyalty/` (дашборд-мониторинг: активации, воронка, экономика баллов) + `admin-panel-v2/src/features/customers/` (клубный бейдж/фильтр в общем списке клиентов) | Два разных места — не ошибка, а два разных назначения (см. ниже) |

**Почему `admin/features/loyalty` и `admin/features/customers` — оба про Club:**
`loyalty/` — отдельный дашборд с графиками и сводкой по всей программе;
`customers/` — это общий список клиентов админки, куда клубным профилям просто добавили
бейдж/фильтр «Участник Клуба» / «Пришёл по QR» поверх уже существующей страницы. Разные
задачи, разные экраны — не дублирование.

**Легаси `packages/api/src/crm/`** — это отдельная, более старая подсистема (лог лидов
AI-ассистента: `crm.leads`/`family_members`). Она **не имеет отношения к Club** и
сознательно не тронута при разработке лояльности — не путайте эти две «CRM».

## Как читать код — с чего начать

1. `packages/api/src/loyalty/models.py` — вся модель данных одним файлом
2. `packages/api/src/loyalty/service.py` — вся денежная логика (активация, кэшбэк, резерв→списание баллов)
3. `packages/api/src/loyalty/router.py` — HTTP-контракт
4. `packages/bot/bot/handlers/loyalty.py` — вход через бота
5. `packages/frontend/src/hooks/useLoyalty.ts` + `pages/ActivationPage.tsx`/`CheckoutPage.tsx` — клиентская сторона

## Архитектурные решения, которые нельзя перепутать

- **Баланс баллов не хранится колонкой.** `balance = SUM(point_ledger.amount)`, вычисляется
  сервисом. Ledger — append-only.
- **Лояльность живёт в `customer_profile`, не в `users`.** У бота своя копия модели `User`
  на той же БД — трогать `users` новыми лояльность-полями означало бы задеть бота.
  Профиль создаётся лениво API при первом обращении.
- **Телефон приходит только через бота** (Telegram `contact.phone_number`), initData
  мини-аппа номер не отдаёт.
- **Активация идемпотентна**: `UNIQUE(qr_code_id)` + атомарный
  `UPDATE qr_codes SET status='used' WHERE status='generated'` — повторный скан не
  начисляет баллы дважды.
- **Трата баллов — модель «резерв → списание»**, не мгновенное списание при оформлении
  заказа. Баллы резервируются на время оплаты и либо списываются в леджер при успехе, либо
  освобождаются (сами по таймауту или вручную кнопкой). Так сделано после прод-инцидента
  с брошенной оплатой Multicard, где баллы сгорали без возврата.
- **Вся программа под общим флагом** `loyalty_enabled` (тёмный по умолчанию) — этим
  включили прод 2026-07-06.
- **`merge → main` = деплой на прод** в этом репо (CD по `workflow_run`). Перед любым
  PR, меняющим схему БД (новая таблица/колонка в модуле `loyalty`), обязателен CI-гейт
  `Migration parity` — паритет модель↔миграция на чистом Postgres.

## Статус

Актуальный прогресс по этапам — в `concept.html`, секция «Прогресс сборки», и в
`CLAUDE.md` (строка «Прогресс (план §7)»). Кратко на момент последнего обновления этого
файла (2026-08-04): этапы 0–4 и 6 (регистрация, кэшбэк, статус «Друг», трата баллов) в
проде и проверены полным циклом от скана QR до оплаты баллами; **этап 5 (розыгрыш) закрыт
по коду** — все шесть шагов на проде; этап 7 (бонусы/рефералы/сгорание) не начат.

⚠️ **«Закрыт по коду» ≠ «розыгрыш можно проводить».** Доделывать в коде нечего, но проведение
держат внешние условия: переутверждение механики у руководителя (11 расхождений с утверждённым
им документом), «Правила акции» и юрист РУз, формат первой публикации списка, а также бэкфилл
билетов существующим участникам. Действующий план и полный список —
`.claude/specs/2026-07-30-lottery-rebuild-plan.md` (§10 и §11).
